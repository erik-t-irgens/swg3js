# Lessons: Testing and tooling

How the tests run under node, driving a tab, shader text in tests, the dev server holding files.

Moved here from CLAUDE.md's "Things that took a long time to learn" on 2026-11-19, word for word and in their old order. Add a new lesson about this area here, never to CLAUDE.md. A code comment that cites "CLAUDE.md" or "the lesson in CLAUDE.md" means one of these files: grep `docs/lessons/` for its words.

- Node's type stripping runs the tests, and it does not take a TypeScript parameter property (`constructor(readonly x: X)`), nor an extensionless relative import: a runtime module that wants a node test writes its fields out and imports `'../core/physics.ts'` with the extension. `src/core/physics.ts` and Rapier itself load fine under node, so a test can build a real physics world and try the thing rather than a mirror of it. And the file that breaks need not be the test: a display file that grows an import of its own takes down whichever suite reaches it while `npx tsc --noEmit -p .` stays perfectly clean, so every value import under `src/` carries its extension whether a test names that file or not.
- `__debug.advance(s, keys, true)` keeps its keys down until a later call names them without `hold`; a test that presses a key with `hold` and then calls advance with other keys still has the first key down (a crouch held rolls, then crouch-walks; a trigger held never releases a charged shot).
- **Never tell a driven tab it is visible.** The game compiles with `compile` rather than `compileAsync` in a hidden tab because a hidden tab never reports a program linked; a harness that overrides `document.hidden` gets `compileAsync`, whose poll never finishes, and every dressed body stays `loading` and the next loading screen waits for good, which reads exactly like a hang in the looks. Stand in for `requestAnimationFrame` and the timers, never for the visibility. The stand-ins must be in place before the app boots, and an ES module already evaluated in a window is never evaluated again: so the tab goes first to a same-origin page that is not the game (any missing file under `assets-private/`), installs them, puts the address back to `/` with `history.replaceState` and only then writes the fetched `index.html` in. Written over the running game instead, the page comes up empty with the old `__debug` still answering.
- **A node test that reads a shader's text has to compile something of it too.** The blade glow pass once declared `own` twice in one scope of `bladeLight`, which every GLSL compiler refuses: the whole pass stayed unlinked in every browser, and every node test passed, because they matched expressions in the shader's source and node compiles no GLSL. `bladeGlow.test.ts` now builds the real source and scans it for a name declared twice in one scope -- following braces, and a function's parameters, which share its body's scope in GLSL ES 3.00 -- after checking the scanner on the very fault it was written for. A test that pins a shader by its text pins its words, not its program; whatever it cannot compile it should at least scan for what a compiler would refuse.
- A running Vite dev server holds the files it has served open, and on Windows that makes a conversion's swap of a pack folder fail with `EPERM` -- once it deleted a mobiles unit outright. Stop the dev server before converting anything.
- **Node's `performance.now()` allocates, so a node measure of a frame call that reads the clock reads 20 to 48 B a frame no browser would** (the GPU port's pass 1, wave 1, maker A: `ledgerFrame` in `src/core/gpu/pipeLedger.ts`, `tools/swg/tests/gpuLedger.test.ts`). Node builds `performance.now()` on `process.hrtime()`, which hands back a fresh array each call, and the twelve-process measure showed it in every process. The cure that is right for the browser too is to keep the clock out of the steady frame altogether: the frame call compares the travel's flag and stores two values, reads the clock only on the frames an arrival begins or its screen goes, and the arrival's thirtieth-second look at the warm-up's queue runs on a timer of its own, never in a frame. Measured so, every state of the call reads the harness's own floor (0.12 B) in 12 of 12 processes run at once.
- **A field begun at `-Infinity` (or `NaN`) makes every sum with it a double, and a double sum boxes in code not yet optimized: the twelve-process measure then flakes one process in two** (the GPU port's pass 1, wave 1, maker B: `ShipHud.rest` in `src/ui/shipHud.ts`, `tools/swg/tests/hudHide.test.ts`). The hide key's `rest` on the flight display first advanced its clock of seconds (`clock += dt`) and read 14 to 49 B a call in half the processes and 0.12 in the rest, even with `%GetOptimizationStatus` saying the function was optimized; moved to the page's clock in milliseconds, the same measure still read 7 to 17 B in half of them, because the window's start was declared `-Infinity`, so `now - restAt` was a double however whole the stood-in clock's numbers were. Begun at nought, as the display's own window starts, it reads 0.12 to 0.16 B in 12 of 12. The display's and the roster's `rest` were clean from the start because their windows begin at a clock reading. So for a frame call measured in node: carry the clock as the stood-in whole milliseconds (`performance.now` stood in with a function of the test's: node's own allocates, the lesson above), begin every field it is compared with at a whole number, and keep fractions out of a call that must make nothing; a fraction measured clean in one process proves nothing about the next.
- **A test holds only the forms of a fault it was handed, so it is proven by breaking the code the way the fault would, one way at a time, and watching it fail** (the GPU port's pass 1, wave 1, its review and fix round: `hudHide.test.ts` and `anchorScan.test.ts`). The hide key's test held every `refresh` by the bars and the rows that moved while hidden, and passed with six of its two-state records turned over instead of read back from the page (the very mistake the wave had made once): a turned record is wrong only when the truth turned while hidden, and the test turned only three. Each record now has a case where its truth turns while hidden, both ways, and all twenty-eight records across the display, the roster, a ship's instruments, the jobs, the minimap and the course's labels were each turned into a flip in turn, the test run and the file put back by its bytes (the fix round's script, `A:\swg3js\port\scratch\p1w1-fixer\mutate.ps1`): every flip fails. The anchor scan was a line of patterns a rule, each stopping at the first `)` or `;`, so a uniform made of `new Vector3().setFromMatrixPosition(mesh.matrixWorld)`, the camera's `.position`, an `eye.x` and a place reaching a 32-bit array a statement later all passed; it now reads each call's whole argument across lines, counts an object's place and a camera's or eye's components as world places, and follows a name filled from one to the end of the block it was filled in. Followed through the whole file instead, a name like `t` or `f` filled in one function counted in every other, and a right-hand side that was a function counted its body's reads, which over the existing world files flagged 122 lines, nearly all of them nothing; scoped, the same files give 18: fourteen of three's world nodes in the base's own programs, a world matrix set into a uniform, an instance placed at a world place, a view-space place made from a world matrix, and one distance from a world place written to a 32-bit array, the one line there that is no place at all. Every form the review found is planted in the test's own check, and every form that keeps to the rule is planted as let through.
- **The whole run is parallel, and a failure in the crowd is not yet a failure** (2026-11-19: `tools/swg/tests/runAll.mjs`, `npm run test:par`). The one-at-a-time `test:all` took 41 minutes and grew with every feature while using one core of sixteen. The runner reads the chain out of `package.json` each time (so it cannot drift from it), expands `npm run` steps in place, starts the longest suites first from the last run's times (`node_modules/.cache/swg-test-times.json`), and gives a suite that starts a relay on a fixed port (`const port = 18797`) a lock on that port, since two suites share one. The allocation measures flake under load, so a suite that fails among the others is run again alone at the end and fails the run only if it fails there too; the summary names the suites that failed only under load. Run it once at the end of a wave, never just after the groups it already covers.
- **Two game tabs at once on the card, never three; and a tab is set aside by holding its frames, not by freezing it** (the GPU port's pass 1, wave 2, browser round). A third headless Chrome arriving on Tatooine while two other game tabs stood paused lost its WebGPU device to `ID3D12Device::CreateHeap ... OutOfMemory`: its frames stopped for good while every eval still answered, and its arrival read as a short, half-built world (384 pipelines, people still loading). A device lost reads like a hang in the looks; read the tab's console before any number from it. `Page.setWebLifecycleState({ state: 'frozen' })` does not stop a headless tab (its renderer still burned a core); keeping every `requestAnimationFrame` it asks for unanswered does (`A:\swg3js\port\scratch\p1w2b-play\pause.js`, 0.2 s of CPU in 4 s), which is how two builds stand at one view and are measured in turns. Two more traps of the same round: the views measure's sun-shadow A/B (`measure.js`, `shadowMap.enabled` off and on) makes every lit pipeline again by a draw in play, about 300 at Mos Eisley's street, so a count of pipelines drawn in play is taken around the walk, the travel or the jump alone, or with `window.__mShadowAb = false`; and the machine is shared: an arrival took 179 s under the interface wave's `npm run test:par` (100% for some 15 minutes) and 126 s at a fresh Vite's first serving with that wave's review Chrome running (73%), against 27 to 30 s quiet. Look at what else runs before every timing, and take the arrival runs back to back on a quiet machine.
- **Timing a load journey: tell the owner's Chrome from yours, read a ride from its start, and know what warm means on the dev server** (the GPU port's pass 1, wave 2, browser round, `__debug.load()`). The owner's own Chrome ran his viewer at 2 to 3 cores for half the round. A WebGPU arrival took 36.6 to 40.0 s while it did and 34.2 to 35.1 s once it stopped, and the machine's total CPU did not show which Chrome was busy. So group every `chrome.exe` by its tree's root process (a driven profile's `--user-data-dir` is on the root's command line) and log each tree's cores beside every timing (`A:\swg3js\port\scratch\p1w2b-load\sampler2.ps1`). A ride's crossing begins at the take-off's cut on the shared clock, minutes after `ride({ trip })` answers. Its journey begins when the travel's flag goes up, some 80 ms before the screen shows, so the record is read from the ride's start, not from the screen first seen, or the journey is missed. The dev server answers `assets-private/` files with no `Cache-Control`, `ETag` or `Last-Modified`, so an arrival after a reload fetches every pack file again (595 MB, 3 of 1,543 from cache). On the dev server "warm" means only the GPU caches and the OS's disk cache. Two figures need reading beside every arrival. The far ground's bake decodes in a worker that no mark and no resource timing sees, so read `__debug.horizon().loadMs.arrivalJoinWait` (about 3 s of every landing on a world), or it reads as unexplained `leftS`. And the landing log's own arrival begins at the first frame that sees the flag: 0.5 to 0.8 s after Play on a first arrival from the select screen, with 26 to 39 pipelines asked in that gap filed under no arrival.
- **A picture pair is readied without breaking the game: never stop its clock, never hide what may hold a light or feed a uniform, and look at every shot before trusting a count** (the GPU port's pass 1, wave 2, browser round, its fixer: `A:\swg3js\port\scratch\p1w2b-fixer\pic.js`, `pic2.js`, `pdiff.mjs`). Three readyings each wedged a WebGL tab, on the base build as on the pin. `performance.now` held at one constant gave every frame a step of nought, and something of the game's divides by it: the lights' directions came out NaN and stayed so after the clock was given back. Hiding points, sprites and the particle batches for the shot (a light under them, or a source an array uniform is filled from) made every WebGL frame after fail in three's vec4-array upload (`firstElem.toArray is not a function`, "frame failed (the game carries on)"), so every later shot was the same stale frame, and two different views compared as identical. Hiding the skinned bodies alone, a creeping clock, or no hiding at all (`pic2.js`) left the frames alive. So read the log for "frame failed" after each readying, compare a view's shot with the one before it (identical counts across views mean a dead loop), and open the diff's mask (`pdiff.mjs`'s third argument) before calling a count a difference: at the Naboo forest 8.6 % of the pixels apart was one tab showing a building's tier the other had not yet streamed. A teleport far across a world can fall through ground not yet streamed (Bestine from Mos Eisley's street with two tabs loading): check the body's height after the view's settle. And in PowerShell a variable's name has no case, so `$V`, `$v` and a parameter `$views` are one variable: a view table named like the loop's variable is emptied by the loop.
- **An allocation measure takes the least of three clean windows in each process** (the interface rewrite's first wave: `tools/swg/tests/hudBars.test.ts`, `weatherWords.test.ts`). With twelve processes on one machine at once, one window in a dozen read 14 to 37 B a call on code that read 0.11 B in every other window of the same process: traced with `--trace-deopt`, no process deoptimized anything; the background compiler had simply not landed its code when that window opened. A real allocation shows in every window, so each child warms the call over ten turns of the event loop and reports the least of three windows no collection fell inside; one window alone flakes, and the least of one proves nothing.
- **A process with no clean window answers null, and a message that prints it as a number hides the allocation it caught** (the interface rewrite's first wave, item 6: `tools/swg/tests/weaponMark.test.ts`). With a key string made each frame on purpose, every window of every child had a collection in it, so each child's least of three clean windows stayed `NaN`, which `JSON.stringify` writes as `null`; the check failed, rightly, but its message printed `Number(null).toFixed(3)`, twelve times `0.000 B`, which reads as a pass. Say a missing window in words (`no clean window`), never through `Number()`; a real allocation big enough to collect in every window looks exactly like this.
- **A frame with a path taken on one frame in five is warmed long and measured over long windows** (the GPU port's pass 1, wave 3: `tools/swg/tests/heldCsm.test.ts --alloc`). Warmed for 5,000 frames, the held cascades' frame read 4.4 B a frame in 11 of 12 processes, every clean window alike, which looks like a real allocation: a fast mover was listed on one frame in five, and its guard's path was the last the compiler optimised. Warmed for 40,000 frames and measured over windows of 20,000 it read 0.11 B in every process, the harness's own floor at that window (`v8.getHeapSpaceStatistics()` makes about 2.3 KB a read: 1.2 B a frame over windows of 2,000, 0.11 over 20,000, so a floor is quoted with its window). Bisected first in a probe of one process with each part of the frame switched off in turn (`A:\swg3js\port\scratch\p1w3-maker\allocprobe.ts`): every variant read the same 4.4 B short and the floor long, which is what said it was the warm-up and not the code. What remained was real and in one process of twelve, which a long window then showed plainly (32 B, the guards' `lengthSq()`, `performance.md`).
- **A picture pair that must differ by one thing alone is made at one state of the world: creep the clock from the frame that is held, never stop it** (the GPU port's pass 1, wave 3, its fixer: `A:\swg3js\port\scratch\p1w3-fixer\spair.js`, `spair.mjs`). The browser round's pairs compared a held frame with the next one drawn fresh, so a frame's step (bodies, sway, the effects' eases) stood in every pair, a fresh pair at the same view put 0.004 to 0.73% of the pixels over 8 levels, and whether the hold met "within 8 levels" could not be read. From the frame read straight after the game drew it, `performance.now` is stood in by one that runs at a thousandth of real time from where it stands (the game's `THREE.Timer`, the holds' clock and three's node clock all read it), so the next frames draw the world as that frame left it: the held frame again (its ages have not moved, so it decides as it did), then two frames after `shadowPass({ redraw: true })`, and those two against each other are the floor, which read 0 to 0.004% of the pixels over 8 at every view on both renderers (worst 1 to 28 levels). A held frame within one frame of its limit is picked as read after the frame (age under the limit less half a millisecond), or the next decision, at the crept clock, finds it due. The clock is given back in a `finally`. Read beside it: a step of nought makes NaN of the lights (the picture-harness lesson above), so the clock creeps rather than stands; and a check with one cause stood still (here the WebGPU sun's direction, by handing `sun.ts`'s one `addScaledVector` the direction at the start) is an attribution control, never the pair itself.
- **A pair across a live switch compares the two pictures taken after a switch, a body is hidden from a driven tab by a property the game cannot write, and the menus are reached through their own buttons** (the GPU port's pass 1, wave 4, its prover: `A:\swg3js\port\scratch\p1w4-prove\spairw.js`, `smear.js`, `slider.js`, `doll2.ps1`, `creator.ps1`). The first switch moves something that is not its state: at Mos Eisley's street with the player running the picture before the switch read 0.87% of pixels over 8 against the one after it switched off and 0.90% against the one after it switched back on, while off against on, both after a switch, read 0.008% beside a floor of 0.003%; so the pair is the two after (C against D in `spairw.js`), and the one before against the one after back on is the switch's own disturbance. The player's figure takes `visible` back every frame, so `group.visible = false` hid nothing and a reappearing-body check compared the body with itself; an own `visible` property with a getter answering false (deleted after) hides it. On WebGPU the effects chain draws no motion blur and no velocity target (`gpu().chain.ported`), so a body reappearing cannot smear on the screen whatever its last-frame bones hold: such a check proves nothing there until a velocity pass is ported. A synthetic I opens the backpack (the last tab), not the doll: the doll is the Clothes tab, the appearance page its own tab, each opened by clicking its `button.tab` in the bar that is showing (the first button of that name in the document can be another panel's, and for Clothes it opened nothing); the character list is the menu's `.switch` after an Escape. The select screen's figure is lit differently after a play than on a fresh session on the base build too (the world adopts its materials), so a select screen is compared fresh against fresh or after a play against after a play.
- **The motion buffer is read back at the start of the next frame's motion call, held against the camera's own matrices and the depth, and a moving body is placed by three's skinning with each frame's own bind inverse** (the GPU port's pass 1, wave 5, its prover: `A:\swg3js\port\scratch\p1w5-prove\mp.js`, `mrun.mjs`, `pdiag.js`, `seethru.js`). The probe wraps `GPU.rt.motion.frame` and `GPU.rt.bones.frame` on the live runtime (each calling the game's own whole): every mesh's world matrix and a skinned one's bones are captured after the scene's walk on two frames in a row, and at the start of the third frame's motion call, before that frame's clear, frame N's depth is copied through a quad of its own into a float target and the motion and that depth are read back with `readRenderTargetPixelsAsync`, whose copy is submitted in the caller's task; so every pixel's motion is set against what a still thing at its depth reads by the cameras captured at N-1 and N, worked in doubles independently of `motion.ts`, and every moving mesh's visible vertices against its own two places. Four things cost time. **Three keeps an attached body's `bindMatrixInverse` as its world matrix's inverse, frame by frame**, so a body whose mesh moves with it (the player's; a crowd body's mesh stays at its bind place while its bones move) placed with the one bind inverse read at the analysis read 0.4 to 1.8 px off while the buffer was right to 0.01 px: capture it with each frame. **A depth match of 2 cm lets a vertex hidden just behind another part of the same body through** (a ragdoll folded on itself read 3.8 px at p90; matched within 5 mm, 0.05 to 0.3 px). **The buffer is half floats**, so its error grows as a share of the motion itself (0.1 to 0.2 px at 120 to 450 px a frame, the camera skimming a slope): quote an error beside the motion it was read at, never alone. And **the game clears the page's resource timings at a travel**, so the dev server's addresses of three's prebundled modules (needed to build a node material with the very classes the renderer runs) are read at the arrival and handed in. What it found that is the game's: a blaster bolt's core is an opaque `MeshBasicMaterial` (`src/combat/bolts.ts`), so by `motion.ts`'s rule it writes the bolt's own motion (up to 51 px a frame read where the bolt flew) and only the glow over it keeps the motion behind; the saber's ribbons are all additive and keep it to 0.03 px.
- **A thin or fast thing's motion is read pixel by pixel against the surface point under each pixel's middle, never at its vertices** (the GPU port's pass 1, wave 5's fixer: `A:\swg3js\port\scratch\p1w5-fixer\rb.js` on the prover's `mp.js`, `rbrun.mjs`). A rope's strip is a pixel or two across and its motion changes along it, so a vertex or a ring's middle projected to a pixel reads that pixel's surface point, up to a pixel off, and a rope snapping 353 px in a frame read 2.4 px off that way while the buffer was right; a bolt's core 4 cm across is under a pixel wide 50 m off and is never sampled at all. For each of the strip's triangles every pixel whose middle falls inside it is taken, its perspective-correct weights give the surface point now and the same weights of last frame's vertices its place then, and the depth there must be the strip's: 545 of a rope's pixels then read within 0.011 px. Copy the strip's positions inside the motion call of each frame (mp's `everyFrame`), where they are that frame's: by the read-back at the next frame's start the game has laid them again. And mind the game while you drive it: Escape opens the pause menu, and a turret that kills you puts up the death screen; both stop the world, and every bolt then hangs in the air reading no motion at all.
- **Chrome's CPU throttle at 2 is no factor of two on a short frame, and a setting moved through the page is moved by its control and its event, never by a field** (the GPU port's pass 1, wave 6, maker B: the quality tiers' budgets, `A:\swg3js\port\scratch\p1w6-makerB\tiers.mjs`, `tier.js`, `tmeasure.js`). Under `Emulation.setCPUThrottlingRate({ rate: 2 })`, set only around the main thread's measure and put back to 1 before the card's, the frame report's main thread at Mos Eisley's street read 25.4 ms at p50 and 31.1 at p95 where it read 6.9 and 9.1 unthrottled, three and a half times, and at the Naboo forest 10.8 and 13.3 against 4.3 and 4.9, about two and a half: the throttle suspends the renderer's thread in slices, so the shorter the frame the more it is stretched. Quote a throttled number beside the unthrottled one and the rate, never as "twice the work". The tiers were set as a player sets them (the menu's range input given its value and its `input` and `change` events, the page drawn again and read back), and each tier's curtain was waited out by watching the notice come and go before anything was timed; `gpu().warmUp.pipelinesMade.byDrawInPlay` read before and after each tier says what a curtain let through.
- **A list of suites taken out of `package.json` by a pattern takes only files under `tests/`** (the GPU port's pass 1, wave 7, maker B: `A:\swg3js\port\scratch\p1w7-makerB\runcmds.mjs` and the lists beside it). `node (flags) tools/....mjs` also matches the scripts that are no test at all -- `swg` (the converter's usage), `anims`, `launcher`, `launcher:build`, `launcher:pack`, `launcher:macos` -- and a run of every suite "reading a touched file" ran them: `build-exe.mjs` wrote an 81 MB `swg3js.exe` into the worktree's `launcher-build/`, `pack.mjs` emptied and rebuilt `launcher-build/dist` (and then refused to pack it, the owner's `.bak` files in `public/placements/` being no kind of file a page is made of), and `main.mjs` started the launcher proper for the seconds before it was stopped: it took port 47031, made `%LOCALAPPDATA%\swg3js-dev` with a `launcher.json`, ran `status` and asked Windows to open its page in the default browser. Filter a list on `/tests/`, read it once before it runs, and never hand `runAll.mjs`'s chain-reading to a script of one's own without its own filter.
- **An allocation measured in a test's own process, after heavy work, can open its window while the measured call's optimised build is still in flight: measure in fresh processes, and read the optimisation state before blaming the code** (the GPU port's pass 1, wave 7's fixer: `madeLods.test.ts`). The made chain's sweep read 776.7 B a sweep in about one run in six to fifteen alone (the review saw 3 of 6), and 0.76 B otherwise. A scratch copy of the test (`A:\swg3js\port\scratch\p1w7-fixer\mlcopy.mjs`) read `%GetOptimizationStatus` either side of the window. Every failing run had `LevelGroup.prototype.sweep` in baseline code with a TurboFan build in flight (the bits for "optimizing concurrently" and "baseline"): in one run that held for the whole window, 776.7 B being every number the sweep works boxed, and in another the build landed partway (620.8 B). Every passing run had it TurboFanned already. The test had just run the converter in child processes, read GLBs and built a flora field, so the background compiler had work queued, which a fresh process does not have. Moved into twelve fresh processes, each taking the least of three clean windows of the same 3,000 sweeps after turns of the event loop, 192 processes read 0.76 to 0.83 B, and a 57 B allocation planted in a scratch copy of the group failed all twelve. A per-call figure the same to the hundredth in two failing runs (776.71) is the unoptimised build's own cost, not a leak; a fraction of it is a build landing mid-window.
