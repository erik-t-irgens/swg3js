# swg3js: what this is and how we work on it

Read this first. It is the handoff from the sessions that built the game so far, written so a new session can carry on without the old chat.

## What we are building

A just-for-fun recreation of Star Wars Galaxies (the 2003 MMO) that runs in a browser: Three.js for rendering, Rapier for physics, Vite and TypeScript, no framework. The owner has a legal SWG install (the SWG Legends client, which contains the original SOE archives) and Jedi Academy; everything the game shows is converted from those installs on the owner's own machine into `assets-private/`, which is git-ignored. The game code is public; the assets never are.

The owner plays it on Windows, in Chrome, and tests by hand. They report what they see in words ("the cockpit is a metre too high"), paste console output, and run converter commands you give them. They cannot see your tool calls, so every reply has to stand on its own and say exactly what to run and what to look for.

## Hard rules

- Never commit, copy into the repo, or publish anything from `assets-private/`, any `.tre` archive, or anything derived from the game's files. Diagnostic output pasted into chat is fine; files are not.
- The converter must work with `--retail-only`, which mounts only the SOE-origin archives. Emulator and mod content stays out. See `docs/ASSETS.md`.
- Never put a model name or model identifier in a commit message, PR text, or code comment.
- Commit messages: a one-line summary in plain words (what changed for the player or the converter), then a short paragraph of why, no bullet lists, no file lists. Attribution trailers are whatever the current tool adds; do not invent them.
- Do not create pull requests unless asked.
- Development happens on `claude/gun-combat`. After every commit, push the branch and fast-forward `main`:
  `git push -u origin claude/gun-combat && git checkout main && git merge --ff-only claude/gun-combat && git push origin main && git checkout claude/gun-combat`
- Before pushing: `npx tsc --noEmit -p .` and `npx vite build` must be clean. `node --check` any converter module you touched. The converter tests are plain node scripts (`npm run test:converter`), not vitest suites.

## Setup on a new machine

Node 22.18 or newer, `npm install`. Copy `.env.example` to `.env` and fill in:

```
SWG=<folder holding the client's .tre archives>
JKA=<Jedi Academy's GameData folder>
```

The converter replaces `@SWG` and `@JKA` on its command line with those. Then follow "Converting your own SWG install" in `README.md` (the whole list, in order, every command with `--retail-only`), and `npm run dev`. `npm run swg -- status assets-private` says what is in place and prints the command for anything missing.

`.claude/launch.json` starts the Vite dev server for the Claude Code extension.

## How the pieces fit

- `tools/swg/cli.mjs` is the converter, one `case` per command; `tools/swg/README.md` documents every command. It reads the client's IFF-based formats (`iff.mjs`, `msh.mjs`, `appearance.mjs`, `pob.mjs`, `sht.mjs`, `dds.mjs`, `objtemplate.mjs`, `datatable.mjs`, `shipdata.mjs`), writes GLB (`glb.mjs`) plus a `manifest.json` per pack. Diagnostics that exist and are worth knowing: `list`, `dump --strings` (prints every readable string per chunk, the way to learn a file layout), `template` (an object template's parameter chain), `materials --ship=<id>` (every shader a hull uses with what the converter made of it, and its hardpoints), `shader`, `pob`.
- `src/main.ts` is the app: the game loop, input dispatch, mounting and boarding, the camera choice, the `__debug` object on `window` (every helper is documented in the README's Debugging section).
- `src/world/` streams the planet: terrain from the game's own terrain rules, placed objects, portal buildings with cells drawn through a stencil portal renderer (`portalRender.ts`), a compile queue that pre-compiles shaders so nothing stalls on first draw, cascaded shadow maps.
- `src/player/` is the character: a parts-based skinned rig, the Jedi Academy movement and saber port, the blaster carries, and the "aboard" mode (see ships).
- `src/vehicles/` is the garage (`garage.ts` reads the manifests and spawns), the vehicle physics (`vehicle.ts`), ship interiors (`interior.ts`), engine trails (`trail.ts`).
- `src/net/` and `server/relay.mjs`: a dependency-free WebSocket relay that passes player states around; other players are drawn as their own characters.

## Things that took a long time to learn (do not relearn them)

- GLTFLoader strips `:` from node names and keeps the original in `userData.name`. The converter names hardpoints `hp:<name>` and cells `cell:<index>:<name>`; read them through `hardpointName()` in `garage.ts` and `cellIndexOf()` in `interior.ts`, never by matching `o.name` for a colon.
- A ship's hardpoints live in its `.lod` appearance, not its mesh, and the appearance chain (`.apt`, `.lod`, `.cmp`) carries them through `resolveParts` onto the first part. A single-mesh ship must keep its chain when the chain has hardpoints.
- Rapier scene queries see nothing until the world has stepped once. A ray cast into a freshly built world misses everything.
- Rapier's character controller with "apply impulses to dynamic bodies" panics on a trimesh collider. The push is off (`Player.pushBodies`), and every trimesh goes through `cleanTrimesh()` with `TRIMESH_FLAGS`.
- Changing the number of lights in the scene recompiles every shader (a second each on the owner's machine). Lights are pooled and never added or removed at runtime: `effects.flash` is a pool of point lights that everything borrows, including a ship's room lights.
- Materials with `transparent` true and any opacity still cast full shadows; glass meshes get `castShadow = false`. The converter marks glass-named shaders with `userData.glass`; the game never blends them (the client did not either), it swaps in a clear copy of the material while someone is in the ship.
- The game's rooms in a portal building are often larger than the hull around them and are only meant to be seen through portals. The window openings are "invisible collidable" meshes: colliders only, never drawn, never casting.
- A cockpit frame (`cockpit/<ship>.iff`) is authored in the ship's own space: hang it on the model at its origin and it lands in the canopy. The game never drew a pilot in a fighter, so the seat is derived from the frame's middle (`SEAT_FROM_FRAME` in `garage.ts`).
- Ship attachments (wings, engines, guns, boosters) are templates under `object/tangible/ship/attachment/`, named `shared_<ship>_<kind>_<side>_s01`; the hull's client data (`clientdata/ship/client_shared_<ship>.cdf`) names the wings; the components hang on hardpoints named `engine_pos1`, `weapon1_neg1`, `booster_pos1`. Wings are modelled in the hull's frame and sit at its origin.
- A WING form's DATA is the wing template, a float open angle in degrees, a float seconds to open, then the sound; its PSOR is the hinge (position, then yaw, pitch, roll in degrees), not a placement. The wings are static meshes the client turns about the hinge's Z; the X-wing's foils are two diagonal pairs at ±14°. `dump --hex` is how that was decoded.
- Ship bolts come from `datatables/projectile/projectile.iff` (index to the bolt's `.prt`, its fire `.cef` and its hit `.cef` per surface; a `.cef` names a `.prt` and a `.snd`) and `datatables/space/ship_weapon_components.iff` (weapon name to projectile index, speed, range). Space bolts are 600 m/s, 512 m, drawn 19 m long ahead of the projectile point in local-space emitters, which `particles.ts` honours; passing effects are placed `transient`.
- A bolt is a thing in flight with a velocity: it carries the shooter's velocity (`inherit`) and its ray leads by its visual reach, so a fast ship's bolts never lag it and a long streak does not poke through what it hits.
- Normal maps are Direct3D's (green down); the converter writes them as they are and the game uses `normalScale (1, -1)`.
- An animation table's string selector (SSAT) keeps its value list in a chunk tagged `VAL ` (three letters and a space), not `VALS`: an i16 count, then each value's name and the i16 index of the branch it picks; several values share a branch. The converter names branches for their first value (`loop_riding:vehicle_speeder_bike`, `skill_action_5:dance_18`), the default branch plain, and writes every branch's values to the manifest as `variants`; `rig.variant(base, value)` resolves them in the game.
- A mobile's animations are shared: every appearance with the same skeletons and animation table plays one pack (`mobiles/anims/<pack>.glb`), so a clip is baked once for the hundreds of templates that use it, and the pack's JSON names the clip for each role rather than the game guessing by name. The tables nest their selectors (a mount's branch outside a mood's), and the shipped flattener loses the inner one, so `mobiles` has its own path-keeping flattener and picks the wild, calm, unridden branch: a bantha walks at 0.86 and runs at 3.47 m/s, not the ridden 6.93. Packs are compacted on the way out (no track for a joint that never leaves its bind pose, two keys for one that holds still), which is about half the bytes, and a one-frame pose is written twice a frame apart because three finishes a zero-length clip on its first update and poses a repeating one at NaN.
- How a rider sits comes from three mount tables (`datatables/mount/`): logical_saddle_name_map (a `.sat`, listed as its `_hue` variant, to a logical saddle), saddle_appearance_map (to the saddle's appearance), rider_pose_map (appearance and seat to the pose). The pose is the rider_pose selector's value; the hover chair is not in the tables, so unknown vehicles are tried as `vehicle_<id>`. A rideable vehicle's `pv_*.sat` is a placeholder whose body is the static appearance of the same name; the pose still keys on the `.sat`.
- A rideable vehicle's `pv_*.sat` is a placeholder only when its animation table is the shared `monstrosity.lat`; the walkers (AT-ST, AT-XT) and the basilisk carry their own table and mesh and walk with them. The game's own rider poses are what they are: the AT-ST seats its pilot as the hover chair does, the AT-XT as a pod racer.
- Three applies tone mapping only to the default framebuffer: with a render target bound the materials come out linear, so post-processing must end in an OutputPass, and toggling it recompiles every program (the tone mapping is in the program key). World warm-up binds `world.compileTarget()` (the effects' scene target) around every compile, so the programs built behind the loading screen are the ones drawn; switching Effects compiles the other variants in the background (`reconcileEffects`) and changes over when they are linked. Three's own output pass works its tone-mapping defines out on its first draw, so it is given one throw-away draw before the warm-up compiles it, or the program built there is one no frame ever uses. Every effect's settings, knobs, pass order, products and budgets live in `src/core/fxRegistry.ts`; `npm run test:fx` checks them.
- The game seats a rider at the vehicle's authored origin and the riding clip's root offset puts the pelvis in the seat: a speeder bike's `player` hardpoint is exactly its clip's root (0, 1.16, -0.04), so the rider must not be placed at the hardpoint as well. The garage recentres a model on its box, so the authored origin is `model.position` afterwards. A guessed seat (a mount's back, a cockpit frame) names the pelvis instead and takes the clip's root off (`seatPelvis`); `__debug.seat(dx, dy, dz)` nudges a seat live and prints the pose's root.
- The scene draws into `postfx.sceneTarget`, which no effect writes into; the chain ping-pongs between two buffers with no depth. A pass may sample the scene's depth texture only while a target without that texture is bound: Chrome drops the draw otherwise (INVALID_OPERATION, and silently once its error cap is hit), which is why the god rays and the speed blur never drew before. Geometry products (heat, water mask, velocity) attach the same depth texture read-only, so they never sample it; a target sharing it must be the scene target's size, and is detached before being disposed on its own, since disposing a target disposes its depth texture. `__debug.fxCheck()` names a step that errors.
- A vehicle's hull colliders leave out the terrain group (`HULL_GROUPS`): the springs hold the vehicle off the ground from their rays, and hull-versus-heightfield contact made every slope snag and jolt.
- A flying hull is driven by setting its velocity every step, so a contact the solver resolves is overridden the next step and the hull wedges into whatever it hit: `flyShip` compares the velocity it commanded with what the step left (`commanded`), takes a big loss as a hit, and then leaves the body to the contacts for a few tenths of a second. The hull collider ignores the terrain heightfield (`HULL_GROUPS`), so the ground is checked by height: below it is a crash and the hull is lifted out.
- Never give the effects' render target `samples`: three resolves a multisampled target at the end of every `render()` call, and the portal renderer makes a dozen calls a frame, so bloom alone dropped the frame from 144 to 11 a second. The target is single-sampled and FXAA smooths the edges.
- A NaN pixel from any material becomes, through the bloom's mip blur, a screen-sized black box whenever that object is in view (the owner found a plant on Tatooine that does it). The effects chain starts with a pass that zeroes NaN and Inf pixels; `__debug.blackBox()` scans the frame and names the object under the first bad pixel, which is how to find the material at fault.
- The motion blur reads the frame's depth (the scene target's `DepthTexture`) and reprojects with the last frame's camera; without a near cut-off (25 to 60 m) the ship flown, which moves with the camera, smears as much as the ground.
- Three disables an AnimationAction when its fade-out finishes (`enabled = false`); an action reused after that shows its bones in the bind pose until `reset()` and `play()`. `rig.setState` restarts a legs action that has gone dead, and a saber move chained onto one already on the upper body stays there (`play(..., { upperOnly })`) rather than taking the whole body and fading the legs out; `__debug.split('BOTH_RUN2')` shows the halves and the live weights.
- A player aboard a ship's rooms has their body in that room's own Rapier world: before any world unload (travel, switching character, removing vehicles) the player must `leave()` the room, or the body is left in a freed world. `travel` carries a ship across as a `ShipCrossing` with a `ShipCrew` record (place in the hull's frame, heading, at the controls) and boards the new hull with it.
- A space zone has no snapshot: its stations are `datatables/space/spacestation/<zone>.iff` (server names; drawn as `object/ship/shared_spacestation_<faction>.iff` by a table in `space.mjs`), its asteroid fields `datatables/space/asteroidfield/<zone>.iff` (centre, radius, count, seed, a style table of appearances with likelihoods, or a spline), and its sky is its `terrain/<zone>.trn`: SKYB names the six-sided skybox (`texture/<name>_<side>.dds`, 512 px; the ENVI cube map is what reflections see, not the sky, and drawn as the sky it is a blurry, misaligned mess), CLEA the clear colour, AMBI the ambient (alpha, r, g, b), PARA each parallel light (a byte, diffuse and specular as a-r-g-b, then yaw, pitch, roll in degrees, the same frame convention as the environment file's celestials), STAR the star ramp and count, DUST the motes' count and radius, CELE each star sprite (shader, size, a spare float, a byte, yaw, pitch, roll), PLAN the planets. In space the procedural ground must not be built at all: placed objects anchor the ground to their height, which raised a needle of terrain under every asteroid, and the ground plane three kilometres down filled the lower half of the view.
- A lightsaber's appearance is an `.lsb` (form LSAT): BASE is the hilt's `.apt`, ASND its idle sound, a BLAD form holds SHDR (the blade's shader), LGTH and WDTH (metres), OPEN and CLOS (seconds), and an optional LGHT form the light (COLR as r, g, b, a bytes, RANG and TIME two floats each). The crafted sabers are under `object/weapon/melee/{sword,2h_sword,polearm}/crafted_saber/`; there is no `object/weapon/lightsaber/`. The blade colours are `palette/wp_lightsaber.pal`.
- Jedi Academy's torso does not face the view while moving: CG_PlayerAngles puts the legs at the movement offset (45 degrees for a strafe, 22 for a diagonal) and the torso at a quarter of it, so the shoulders lean a little the way the legs go. A torso turned all the way back to the camera read as twisted the wrong way. The special moves (katas, kicks, lunges, the jump attacks) are whole-body clips and must never be split off the legs; only plain swings ride the upper body over the run.
- A mesh's BOX chunk holds its two corners with the larger first: read as min then max, every pack's `bounds` came out with min and max swapped (`readBounds` in `msh.mjs` now takes them componentwise; packs converted before carry the swap, so game code must take extents as `Math.abs(max - min)` and never trust which corner is which). The weapons rack's "far end" was on the wrong axis because of it, which is what made a measured aim correction turn the guns 90 degrees.
- The game's blaster poses point close to the view once the barrel is read along the true long axis. `correctAim` measures the barrel against the crosshair each frame and turns the spine up to `AIM_SPINE_MAX`, the body's heading beyond that; the tuned turns (`gunTune`) only apply with the correction off. Prone is left to the game's poses.
- A mount's seat rides its skeleton: `attachSeatToBack` hangs the seat on the spine bone nearest the saddle, but only after the idle clip has posed the skeleton once (`mixer.update(0)`), since a creature's rest pose can stand far from any animated one and the whole difference would land on the rider. The camera's `forward()` is the look direction, `(-sin yaw, 0, -cos yaw)`; `__debug.advance` also steps the creatures, so powers can be tried headless.
- `__debug.advance(s, keys, true)` keeps its keys down until a later call names them without `hold`; a test that presses a key with `hold` and then calls advance with other keys still has the first key down (a crouch held rolls, then crouch-walks; a trigger held never releases a charged shot).
- Anything that happens aboard a ship's rooms must live in the hull's frame: the player's `pos` already does, so bolts fired aboard carry a `frame` (the hull's live world matrix and the room's own physics), the thrown saber is fed the hand and the aim in that frame, and the world-frame sweeps skip the aboard vehicle. A transient particle effect must end on its own: many of the client's hit effects loop for ever, so `Instance.update` finishes a transient after one run (and after one life for an emitter that never runs out).
- A template's integer parameters carry a delta byte (' ', '+', '-' or '%') between the int8 data type and the int32 value: `intParam` in `objtemplate.mjs` reads offset 2. A gun's `weaponEffect` (bolt, rocket, projectile_rifle, ...) and `weaponEffectIndex` name a row of `datatables/weapon/weapon.iff`, which names the shot's `.prt`, the muzzle flash and the hit and miss client effects per surface; the weapons command converts those into the pack and writes them as each gun's `fx`. The flame throwers are bolt 21 (a fireball), the lightning rifles rocket 3 (the lightning beam), the slugthrowers `projectile_*`.
- In `iff.mjs`, `childrenOf(node, name)` needs the name and returns nothing without it; to walk every child, iterate `node.children`. A form's name is `node.type` (`node.tag` is always `FORM`).
- The number slots are the same machinery for both classes: a list of defs with id, name, cost, kind and blurb (`forcePowers.ts` for the Jedi, `gadgets.ts` for the Bounty Hunter), a loadout of ids per kit (`setLoadout`), the Skills tab (`forceUi.ts`, given `defs` for the class in play) and a field per class on the saved character (`powers`, `gadgets`). Bare hands is a toggle in both lists: `player.fists` hides what is held, and `Unarmed` in `unarmed.ts` plays the game's `unarmed_standing_ready_*` clips (or `BOTH_MELEE1/2` and the kicks) with a capsule sweep part way in. The grenade templates are the weapons pack's `thrown` class, listed on the rack but not held; a gadget names its model by substring.
- A species' `rig.glb` is animations only and about 200 MB (1228 clips): `Character.load` parses it once per URL and shares the clips (`rigClips`), or every fighter spawned stalled the frame for seconds. A wearable from one skeleton on another (the human wardrobe on a Rodian) must have its `skinIndex` re-pointed by joint name (`remapSkin`), since three computes a skinned mesh's bounding sphere from its bones every frame and an undefined bone throws. The species index records each species' wardrobe folder (`wardrobe`); `catalogue()` reads it rather than probing folders. New shader programs are main-thread work even with `compileAsync`: `World.compileReady` does a mesh at a time with a yield between, and a fighter stays hidden until then.
- A structure's portal layout comes from `portalLayoutFilename` anywhere up its template chain (`resolveTemplateString`), and many templates share one (the same cantina on three planets, `object/ship/` stations naming the hull as their appearance and the rooms as the layout): the gallery's Interiors section keys on the layout file, converting it with `resolveAppearanceToMesh` rather than the template.
- A ragdoll (`ragdoll.ts`) is built from any skeleton without a parts table: a capsule per bone long enough, ball joints at the bone origins, and the bones posed back from the bodies each frame (parents first, each local transform read under the parent's fresh world matrix). Its colliders carry `ActiveHooks.FILTER_CONTACT_PAIRS` and `Physics.hooks` keeps only their contacts with fixed or bodiless colliders, so corpses never trip the living and their own overlapping pieces never push one another; the character controller skips them by predicate. Rapier's JS `World.step(eventQueue, hooks)` runs the hooks only when an event queue is passed as well: without one they are silently skipped, which had every ragdoll piece colliding with every other and shivering for ever, whatever the springs were set to (`__debug.ragdoll().hooks` counts the calls). The engine's per-axis joint motors and limits on a ball joint were tried and dropped: the springs are torques applied in `Ragdoll.spring` each frame, fading out after the fall, and a body near still for a second (or slow for a few) is stopped and put to sleep; every number is live through `__debug.ragdoll({...})`. Aboard, the ragdoll lives in the room's physics with the hull's matrix as its frame. The terrain's `floor` reset (fallen out of the world) must not fire inside a building: dungeon rooms go far below it.
- The dances are the skill loop's third branch (`loop_skill:speed2:dance_N`, N the performance table's visual id, odd novice and even full) and the flourishes `skill_action_1..8:dance_N`; `nameLocomotion` must not re-rank loop_skill's branches by speed. Emotes are the 270 `emt_` clips; the `_ag` ones are NPC ambient idles.
- An area's environment family is painted by the terrain's AENV affectors exactly as ASCN paints shader families (DATA: int32 family, int32 use-override, float clamp; the family's own clamp from EGRP > version form > EFAM > DATA: int32 id, name, three colour bytes, float clamp), and `SwgTerrain.environmentAt` reads the map the generator fills. The environment table's family names match case-insensitively, because one planet's terrain capitalises names its table spells in lower case. Life Day's families are seasonal: one planet's Life Day layer is active in the archives and covers a town, so seasonal families are kept in a second map and only win in season, leaving the place underneath known the rest of the year. A family id outside a byte is noted and paints nothing, and a family from a building's own layer file is cleared rather than painted, since nothing remaps that file's ids onto the planet's. A cached read is free (a sixth of a microsecond); an uncached one generates the covering 64 m block on the main thread, one to four milliseconds, which is what `environmentIfCached` is for and why `environmentAt` counts itself in the "sync grids" figure.
- `convertParticle` caches per output pack. Before, a run over several planets wrote later planets' manifest entries for particle effects without their files.
- A water shader's CUBE and `_SKY` slots are never sampled by any retail effect: `water.eft` reads MAIN, NRML and an ENVM placeholder the engine filled at run time, most likely from the area's day and night map, which is what water reflects by default. The per-shader cubes are converted into `water.json` all the same; `await __debug.waterFx({ env: 'shader' })` shows them, dimmed at night by the sky's clear colour against its brightest. The client's water pixel shader is unlit, `(main·a·0.5 + spec + env) / (a + 2)` with alpha `0.5 + a/2`, which is where each body's opacity comes from; ripple is the normal map's mean slope against the reference map and drift its first TSNS scroll rate (TSNS is a form holding one 20-byte chunk: a tag, then four floats). Lava is the same data path with no colour and no cube: `isLavaWater` takes the terrain's water type, then the pack's entry, then the shader's name, because five of the lava tables are typed 0.
- `envMapCubeUVHeight` is in three's program cache key, so a reflective material whose environment changes height recompiles mid-play. Every environment a water body can see is therefore filtered from a 128 px cube (a PMREM 512 high): the water cubes, the planets' sky maps, the dome (`fromScene` with `size: 128`), and a black stand-in made at startup that every body carries from the moment it exists, so the first real map to arrive swaps a texture and nothing more. A sky map of any other height (a space zone's 256 px maps) is never given to water. `setEnvironment` also no longer overwrites each material's own `envMapIntensity` — the water's authored 0.55 was being forced to 1.
- Everything alive is one kind with one key: the player, the creatures and the fighters all implement `Living` (`src/combat/kit.ts`), the world hands out one list of them (`World.targets()`), and `damage(amount, from, push, source)` carries who struck so that what is hurt can turn on them. Keys start at 2 (`nextLivingKey`) and the player's is a named 1 (`PLAYER_KEY`), so no key is ever 0 and "nobody" can be stored as a falsy number without the player being the one thing that vanishes. Anything with a timer runs on `World.simTime`, which only `stepLiving` advances, so `__debug.advance` exercises it.
- A fighter's body is kinematic and its update writes its height from the terrain every frame, so a Force power that only set a position was undone before it was seen: holding and throwing one takes a branch in that update (held, falling, or on the ground) and a knock hard enough to lift it, not just a `holdAt` method.
- `AnimationUtils.makeClipAdditive` rewrites a clip's values in place and leaves `clip.blendMode` behind as the mark. A clip shared between rigs (the species packs have been shared since the fighters stopped parsing them each) must only be converted once, and on the rig's own path, where the clip object itself is converted, `blendMode` is the whole guard and no marker of ours is needed. It is not a guard for a caller that wraps a clip: a wrapper built from `clip.tracks.slice()` shares the track objects, so the conversion lands on the shared values while the mark lands on the throwaway clip.
- A material that is disposed must be taken out of the portal renderer's `Set` and the shadow cascades' `Map` (`World.forgetMaterials`); both are strong. The portal renderer's is the one that costs per frame -- it is walked once per stencil change, about a dozen times a frame -- and the cascades' is a leak that shows as a stutter when the shadow distance changes. A material must also join the cascades (`csm.setupMaterial`, inside `World.adoptMaterials`) before its program is compiled, because the defines and the `onBeforeCompile` are part of the program key; an unlit material (`userData.unlit`) is kept out of them altogether for the same reason in reverse.
- The colour grade (`src/core/fx/gradeMath.ts`, pass `colorGrade`) runs in linear HDR just before the OutputPass. Every tint keeps the pixel's luminance, and its contrast turns about 0.18 divided by the exposure and leaves anything below a thirty-second of that and above thirty-two times it untouched, so it cannot crush shadows or clip highlights; a raise in saturation is scaled by how grey the pixel already is, so strong colours never clip. A planet's mood (gloom, heat, warmth) is hand-set in `GRADE_LOOKS`, not read from the sky: a planet's environment blocks differ region by region (one planet's keys run from dim to bright), so a mood read from whichever block is in use is an accident of block order. The sky supplies only the hues and how hard the key stands against the fill. Rooms and ship interiors take 30% of it for the whole view, eased over a second both ways; an exits mask from the portal stencil was worked through on paper and dropped, because it dipped the street on the way out and flickered on the door plane. `__debug.gradeSelfTest()` checks the shader against the JavaScript mirror that `npm run test:grade` sweeps.
- Mustafar's lava is terrain water: a table is lava when its water type is 1, when water.json's entry says `kind: 'lava'`, or, with no entry, when its shader names lava (`isLavaWater`; all 102 of Mustafar's). World skips lava in `applySwgWater` and draws it in `loadLava` with `createLavaMaterial` (emissive, unlit, opaque, polygon offset so the ground wins ties), one merged mesh per look, never the water material. A lava shader's MATL is four ARGB groups and a power: the third is loopTime then the flow, the fourth (a, colorScale, colorBias, tcScale); flow × loopTime is a whole number, which is why the loop has no seam. Its TFNS entry BLUM (stored `MULB`) is the bloom factor; the glow is on ramp alpha × that factor, and 0.203 to 0.213 lights about the top tenth. The ramp goes inline in water.json (a PNG's alpha may lose colour in the browser's decoder); the crust and the 128³ noise volume (`water/noise_volume_lava.r8`, 2,097,152 bytes) sit under `water/`. The texture coordinate `tc0` is read as world (x, y, z), an inference (`__debug.lava({ axes })`). The noise volume is mipmapped and the index fades to its mean where the veins are sub-pixel, or kilometre-wide flows sparkle through bloom. A pack converted before the lava look draws a hand-made stand-in, and every missing piece falls back on its own. `loadLava` warns with the water command, and `status` asks for it, when an entry has a lava effect and no `lava` block. An entry whose block is null (an unreadable MATL) asks for nothing, since reconverting does not mend it. `World.leave()` bumps the load token, since it unloads with no load after it and an in-flight lava or sky load would otherwise commit into an empty scene. Lava takes no ripples or spray: `emitRipples` skips a point over a lava table, since the lava planet has a global sea (hidden) and the ripples would otherwise run over the lava.

## How to work with the owner

Give them exact commands to run and exactly what to look for, one list, every item independent of the others so they can do it all in one session. When something cannot be judged from here, ask for the one observation that separates the causes rather than guessing twice. Converter changes need a reconversion (`npm run swg -- ships @SWG assets-private --retail-only` for ships; the README's table for the rest); say so every time, and say when a change needs none.
