# swg3js: what this is and how we work on it

Read this first. It is the handoff from the sessions that built the game so far, written so a new session can carry on without the old chat.

## What we are building

A just-for-fun recreation of Star Wars Galaxies (the 2003 MMO) that runs in a browser: Three.js for rendering, Rapier for physics, Vite and TypeScript, no framework. The owner has a legal SWG install (the SWG Legends client, which contains the original SOE archives) and Jedi Academy; everything the game shows is converted from those installs on the owner's own machine into `assets-private/`, which is git-ignored. The game code is public; the assets never are.

The owner plays it on Windows, in Chrome, and tests by hand. They report what they see in words ("the cockpit is a metre too high"), paste console output, and run converter commands you give them. They cannot see your tool calls, so every reply has to stand on its own and say exactly what to run and what to look for.

## Hard rules

- Never commit, copy into the repo, or publish anything from `assets-private/`, any `.tre` archive, or anything derived from the game's files. Diagnostic output pasted into chat is fine; files are not.
- The converter must work with `--retail-only`, which mounts only the SOE-origin archives. Emulator and mod content stays out. See `docs/ASSETS.md`.
- The interface is entirely our own and none of the client's own interface art is used: no `ui_*` atlas, icon, bar, reticle, frame or colour scheme of the game's is converted, read or drawn, by the owner's decision. Everything on the screen is drawn by this game from one table of eighteen named colours (`src/core/palette.ts` and the `palette` block in `src/style.css`), the shapes in `src/ui/hudCanvas.ts` and `src/ui/hud.css`, and the marks we drew by hand in `src/ui/hud.svg`. The client's own map pictures (`texture/ui_map_<planet>.dds`) and zone-map icons are the map window's and are not the interface's art.
- Never put a model name or model identifier in a commit message, PR text, or code comment.
- Commit messages: a one-line summary in plain words (what changed for the player or the converter), then a short paragraph of why, no bullet lists, no file lists. Attribution trailers are whatever the current tool adds; do not invent them.
- Do not create pull requests unless asked.
- Development happens on `claude/gun-combat`. After every commit, push the branch and fast-forward `main`:
  `git push -u origin claude/gun-combat && git checkout main && git merge --ff-only claude/gun-combat && git push origin main && git checkout claude/gun-combat`
- Before pushing: `npx tsc --noEmit -p .` and `npx vite build` must be clean, and `npm run test:all` must pass (it runs the converter, terrain, effects, weather, first-person head, inventory, audio, display and network suites; several other suites are still separate scripts). `node --check` any converter or server module you touched. The tests are plain node scripts (`npm run test:converter`, `npm run test:net`, …), not vitest suites.

## Setup on a new machine

Node 22.18 or newer, `npm install`. Copy `.env.example` to `.env` and fill in:

```
SWG=<folder holding the client's .tre archives>
JKA=<Jedi Academy's GameData folder>
```

The converter replaces `@SWG` and `@JKA` on its command line with those. Then follow "Converting your own SWG install" in `README.md` (the whole list, in order, every command with `--retail-only`), and `npm run dev`. `npm run swg -- status assets-private` says what is in place and prints the command for anything missing.

`.claude/launch.json` starts the Vite dev server for the Claude Code extension.

## How the pieces fit

- `tools/swg/cli.mjs` is the converter, one `case` per command; `tools/swg/README.md` documents every command. It reads the client's IFF-based formats (`iff.mjs`, `msh.mjs`, `appearance.mjs`, `pob.mjs`, `sht.mjs`, `dds.mjs`, `objtemplate.mjs`, `datatable.mjs`, `shipdata.mjs`), writes GLB (`glb.mjs`) plus a `manifest.json` per pack. Diagnostics that exist and are worth knowing: `list`, `dump --strings` (prints every readable string per chunk, the way to learn a file layout), `template` (an object template's parameter chain), `materials --ship=<id>` (every shader a hull uses with what the converter made of it, and its hardpoints), `shader`, `pob`.
- `src/main.ts` is the app: the game loop, input dispatch, mounting and boarding, the camera choice, the `__debug` object on `window` (every helper is documented in the README's Debugging section).
- `src/world/` streams the planet: terrain from the game's own terrain rules, placed objects, portal buildings with cells drawn through a stencil portal renderer (`portalRender.ts`), a compile queue that pre-compiles shaders so nothing stalls on first draw, cascaded shadow maps.
- `src/player/` is the character: a parts-based skinned rig, the Jedi Academy movement and saber port, the blaster carries, and the "aboard" mode (see ships).
- `src/vehicles/` is the garage (`garage.ts` reads the manifests and spawns), the vehicle physics (`vehicle.ts`), ship interiors (`interior.ts`), engine trails (`trail.ts`).
- `src/net/` and `server/relay.mjs`: a dependency-free WebSocket server, grown in place from the relay that came before it, which passes player states around and holds the few things nobody can hold alone — one clock, and who each player is. Its sibling modules (`hash.mjs`, `clock.mjs`, `rooms.mjs`, `wire.mjs`, `store.mjs`, `identity.mjs`) are dependency-free and shared with the node tests exactly as `shipWire.mjs` is; the browser's half is `src/net/session.ts` and `src/net/hash.ts`, and `src/world/sharedClock.ts` is what the day and the weather read. Other players are drawn as their own characters. With no server address set none of it runs and the game is what it was.

## Things that took a long time to learn (do not relearn them)

- GLTFLoader strips `:` from node names and keeps the original in `userData.name`. The converter names hardpoints `hp:<name>` and cells `cell:<index>:<name>`; read them through `hardpointName()` in `garage.ts` and `cellIndexOf()` in `interior.ts`, never by matching `o.name` for a colon.
- A ship's hardpoints live in its `.lod` appearance, not its mesh, and the appearance chain (`.apt`, `.lod`, `.cmp`) carries them through `resolveParts` onto the first part. A single-mesh ship must keep its chain when the chain has hardpoints.
- Rapier scene queries see nothing until the world has stepped once. A ray cast into a freshly built world misses everything.
- Rapier's character controller with "apply impulses to dynamic bodies" panics on a trimesh collider. The push is off (`Player.pushBodies`), and every trimesh goes through `cleanTrimesh()` with `TRIMESH_FLAGS`.
- Changing the number of lights in the scene recompiles every shader (a second each on the owner's machine). Lights are pooled and never added or removed at runtime: `effects.flash` is a pool of point lights that everything borrows, including a ship's room lights.
- Materials with `transparent` true and any opacity still cast full shadows; glass meshes get `castShadow = false`. The converter marks glass-named shaders with `userData.glass`; the game never blends them (the client did not either), it swaps in a clear copy of the material while someone is in the ship.
- The game's rooms in a portal building are often larger than the hull around them and are only meant to be seen through portals. The window openings are "invisible collidable" meshes: colliders only, never drawn, never casting.
- A cockpit frame (`cockpit/<ship>.iff`, FORM CPIT > 0000: FRAM the appearance, ZOOM the camera distances, FRST the first step out, 3OFF the chase offset, 1OFF the first-person offset) is authored in the ship's own space: hang it on the model at its origin and it lands in the canopy. Every frame carries one hardpoint, `camera`, pointing down the nose: that point plus 1OFF (X mirrored), or a frame's share of it (`COCKPIT_OFFSET_SHARE`: the B-wing takes half, the owner's split between its full offset, better to fight by, and none, which looked more real), is the first-person eye hovering and flying (`Vehicle.cockpitEye`, `cockpitShare`). The game never drew a pilot. The body hangs with the seated clip's eyes exactly on that eye, in first and third person alike (`SEAT_RULE` 'eyes', the owner's call: the head lines up with the view): where the seated clip's first frame puts the eye joints (`rig.seatedPoints`; space_sitting: eyes 0.708 m over the pelvis and 0.109 ahead; skeletons without eye joints, the rodian, mon calamari and ithorian, use the head plus 0.07 up and 0.09 ahead), scaled by the figure's height. The cushion one downward ray through the frame's triangles finds is still measured (`seatDropBelow`, `Vehicle.cushionDrop`, `__debug.cockpit().seatGap`), and the older rule that moved the body onto it (the pelvis 0.10 m over it, at most 0.10 m up in first person, `bodyLift`) is `__debug.cockpit({ cushion: true })`. `Player.syncMount` hangs the body from `cockpitEye()` less `cockpitOffset` plus the file's own 1OFF, which is the view eye only while `cockpitOffset` is the whole 1OFF: a share goes in `cockpitShare`, never into `cockpitOffset`. The eyes are measured from the clip's first frame, never the live bones: the idle's fidget moves them 0.04 m.
- A hardpoint the gun patterns take is never a seat or an eye (`isSeatHardpoint`, `isEyeHardpoint` in `cockpitSeat.ts`): the gunboats' `pilotmuzzle1` is a gun. The ships without a frame are all room ships flown from their bridge, whose first-person eye is the pilot's own; seated in one (no pilot spot), the rider is not drawn. Only the ships pack's ships sit by the eye (`Vehicle.eyeSeat`); anything spawned "as a ship" keeps its own seat.
- Seated in a ship and zoomed all the way in, the view is locked to the hull hovering as in flight (`ThirdPersonCamera.cockpit`, then `chase`, both at `pos + q * eye`, so lift-off never moves it). Hovering, the mouse's sideways movement moves a heading target at most 0.6 rad ahead of the hull (`cockpitYawStep`), which also steers a bridge pilot hovering: aboard, the camera's yaw is in the hull's frame and must never be handed to `drive.heading`. Alt looks round from the eye itself (`update`'s `eyeAhead` 0), starting at the nose. A rider's spine takes no torso twist while mounted, and the on-foot twist is cleared on mount.
- Ship attachments are templates under `object/tangible/ship/attachment/`; the stock ones come from the per-hull `datatables/space/ship_chassis_<chassis>.iff` (each slot's stock component's look, `pickStock`, which on every retail hull is the column's most common `attachment:hardpoint` cell; a `modification_*` slot, whose one filled row is a reward look, has no stock part), never by name (the Jedi starfighter's parts are `jedifighter_*`, and a name search hung every X-wing gun twice). A client data file's version form also carries chunks beside its forms: HOBJ (appearance, hardpoint), IHOB (appearance, hardpoint, three floats that are non-zero only on turret barrels), CHL2 (an object template, then 17 floats, the first three its place in the parent) and CHLD (the same with an appearance): the Black Sun wing structures, the Hutt wings, turret bodies and barrels, radar dishes. A hardpoint a part's client data names is looked for on that part, then on what already hangs under it (a turret's barrels are on its body), then on the whole ship (an engine's ONOF names the hull's `engine_on1`). `yt1300_engine_none` is the empty engine slot's stand-in, the same mesh as the engine: written with `standInFor` and not hung while a component fills the slot. The ships command writes the tree (`tools/swg/shipparts.mjs`: `parent`, `hardpoint`, `place`, `turn`; `owner` on what a stock part's own client data produced; `chassis` on every ship, which is how status tells an old one; manifest `assembly: 2`); a def with no `parent` is hung by name anywhere on the ship, as before. `expandPart` (one part's own subtree, for a part swapped in) writes by name what the part does not carry itself (the Y-wing engine's "on" appearance on the hull's `engine1`, the V-wing engine's glow on the hull's `wing1`), so a part's `children` must be hung after the ship's other parts, over the whole ship, not under the part alone.
- A player hull's components are three tables: `datatables/space/ship_chassis.iff`, a row per chassis (`player_<ship>`) whose slot cells are comma lists of compatibility classes (an empty cell: no such slot); `ship_components.iff`, each component's templates, type and one class (seventeen names end in `.iff`); and `ship_chassis_<chassis>.iff`, a row per component that shows anything on that hull, each slot column's cell `attachment:hardpoint` pairs (an empty hardpoint is the hull's origin). The per-hull table is looser than the chassis both ways: a slot offers only what its classes accept, and a looks column the chassis row gives no class is a fixed part (the Star Destroyer's 92 turret bases); `buildSlots` in `shipfit.mjs` applies both. The chassis name is the template's file name without `shared_` (`chassisNameFor`: a decorated YT-1300 uses `player_yt1300`, the Corellian corvette `player_corvette`). The stock part is the modal look's best-ranked component (`pickStock`), and a `modification_*` slot has no stock part: it starts empty (`STOCK_LEFT_OUT`). The modal look over the components a slot accepts is the column's most common cell on every retail hull, so the stock parts hung and their order (the looks table's columns, `stockPairs`) did not change when the stock rule did.
- A component's name is `space/space_item:<name>_n` for most, the shared template's `objectName` for about two hundred more (the crafted ones are in `space_crafting_n`, and an unset string id must not stop the search up the template chain: `setStringId`), and nothing at all for about fifty (the collection rewards, the capital ships' turrets), which get one made from the key (`fallbackLabel`).
- An NPC ship template (`object/ship/shared_<type>_tierN.iff`) resolves to the same appearance and client data as the player ship of that family, so an NPC type is drawn with the garage hull whose template has its appearance (170 tiered types in 34 families do; the gunboats, shuttles, freighters, merchant cruisers, transports, the droid fighter, the pods, the Kessel mine turret, the smuggler warlord's ship and the `_npc` YT-1300, YKL-37R, Y-8 and Decimator have NPC-only appearances and are listed in `combat.json`'s `skipped`; `nova_orion_*`, a quest line's with tiers up to 10, is not the tier ladder and is dropped). Its chassis row in `ship_chassis.iff` drops the style (`blacksun_light_s01_tier1` reads `blacksun_light_tier1`, so the Black Sun styles share one tier fit). The per-hull tier tables (`ship_chassis_<chassis>.iff`) are look tables, not loadouts: they are the same at every tier (one family differs in a few look cells) and list every component that shows a model, from mk1 to heavy ion cannons. Which components an NPC carried was the server's choice and did not ship; the game picks them by tier (`loadout.ts`, invented) from the tier chassis's fit, which the ships command writes into `combat.json` with `buildSlots` and the same per-look conversion as a player hull's (`looksToParts` in `cli.mjs`), with no paint.
- The formation tables (`datatables/space/formation/{arrow,claw,wall}.iff`) are 20 slots of X, Y, Z metres in the leader's frame (row 0 the leader), then X2D, Z2D for the same slots on one plane. The arrow's row 1 is ahead of the leader (+25): the leader flies second. Taunt tables (`string/en/space/taunts/*.stf`) are `entercombat`, `gothit`, `hityou`, `death` 1 to 5; `%TU` and `%NU` both name the player, and the `_low` tables name nobody. `ship_target_appearance.iff` names `target_acquired_appearance` twice, and `parseDatatable` keeps only the second (a sound). The name table (`space_mobile_type.stf`) misses a few tiers (four of the Imperial Guard interceptor's five), which take another tier's name.
- The flight computers are `object/intangible/ship/shared_navicomputer_1..6.iff` ("v1 Flight Computer"); the astromechs are the pet templates in `datatables/space_command/programmable_droids.iff`, the crafted and plain ones sharing an appearance, drawn as the mobiles pack's `astromech_rN.glb` (R2-D2 has no model there and is left out). The eight hulls with `hp:astromech` take a droid there; `ship_droid_appearance_override.iff` (ship, ground appearance, space appearance) swaps in the N-1's head, which the ships command converts. A droid stands sunk in its socket so only the dome and the top of the body show (every socket's `hp:astromech` is at the hull's top surface, which covers the socket): its posed box, measured once per file in `Garage.fitPart`, puts its point `DROID_SHOWN` (0.35, invented) of its height down from the top on the hardpoint, with a share per hull where the socket lies otherwise (`DROID_SHOWN_BY_HULL`: the V-wing's hardpoint is 0.21 m under its hull's top, the Jedi starfighter's in a wing 0.67 m thick); the N-1's head is the game's own and never sunk; `__debug.droid({ shown, hull })`. Status asks for the ships again when the astromechs arrive after them.
- Ship paint is FORM CSHD: TXTR's TX1D operations pick a pattern's MAIN and HUEB textures together (`index_texture_1`), and TFAC's PAL operations set MAIN's and HUEB's colour factors from 64-colour palettes (`index_color_1`, `index_color_2`); all three are non-private, so one value per ship covers the hull, the wings, the carriers (the Black Sun wing structures, the Hutt wings) and the parts. The colours are passes two and three of the effect, so a first-pass check (`shaderNeedsBake`) misses them: the ships command bakes every pass at the shader's defaults (`paintedMain` in `cli.mjs`, through `surfaceTexture`'s `mainImage`, whose colour replaces the main's before the glow split, so the glow is split from the painted colour; its alpha, the gloss and a MAIN glow's mask, stays the chosen pattern's, since the bake's alpha is the first pass's and opaque: `withPatternAlpha`), and names the image `<pattern>#paint:<shader>`, since two paint shaders on one pattern differ by their colours. A hologram palette is not paint. A recipe's `glow` is written only when the converted material glows: seven emismap paint shaders have masks too faint to split, and a glow put on a material with no emissive map would need a new program.
- A WING form's DATA is the wing template, a float open angle in degrees, a float seconds to open, then the sound; then either PSOR (x, y, z and three angles in degrees) or HARD (a hardpoint of the part whose client data lists it). Either is where the wing object stands and its hinge: its mesh is modelled about that frame and turns about its own Z. The X-wing's PSOR is all zeros, which is why reading it as a hinge in the hull's frame looked right there and nowhere else; the ARC-170's and Jedi starfighter's PSOR places are exactly the hulls' wing1..4 hardpoints. An earlier try at placing wings failed only because it did not mirror X. The middle angle is never used and no wing uses two, so their order cannot matter; which axis each turns about is taken as yaw (Y), pitch, roll (Z): the V-wing is the only yaw, the B-wing the only roll (its body is a collar round the pod, which only a turn about Z keeps on it), each one constant in `shipAssembly.ts`. A wing's own client data can hold wings: the B-wing body's two foils hang on its `wing_l1`/`wing_r1` with HARD.
- Ship bolts come from `datatables/projectile/projectile.iff` (index to the bolt's `.prt`, its fire `.cef` and its hit `.cef` per surface; a `.cef` names a `.prt` and a `.snd`) and `datatables/space/ship_weapon_components.iff` (weapon name to projectile index, speed, range). Space bolts are 600 m/s, 512 m, drawn 19 m long ahead of the projectile point in local-space emitters, which `particles.ts` honours; passing effects are placed `transient`.
- A bolt is a thing in flight with a velocity: it carries the shooter's velocity (`inherit`) and its ray leads by its visual reach, so a fast ship's bolts never lag it and a long streak does not poke through what it hits.
- A ship in flight is flown by a cursor the mouse moves under pointer lock (`space/mouseFlight.ts`, `App.flightCursor`), which stays where it is left: inside the aim circle it aims the guns (every gun's bolt crosses under the cursor at the lead's range; within `snapDeg` of the lead the bolts take it exactly) and the ship holds its course; outside it the stick points at the cursor, full at the ring, and `flyShip` holds a given `stickX/stickY` for as long as it is given. A stick that sinks back to the middle when the mouse rests turns a fighter 36 degrees per flick, which is why the owner could never come round onto an NPC. The cursor is measured about the hull's nose from the pilot's eye (`hullRay`), never from the camera: the chase view lags a turn by up to a quarter of a second and looks 0.1 rad under the hull, and measured from it the guns could not reach what the ship was turning after (none of 24 tier-1 TIEs killed in the sim) and bolts left up to 125 degrees off the nose. The HUD draws the circle where the boresight lands on the camera's screen at the guns' range, so in the chase view it slides off the middle during a turn. Every mouse-flight shot is then kept within `SHIP_GUN_CONE` of the nose (`coneClamp`). An NPC's hand (`skillStick`, `PILOT_SKILL` in `pilot.ts`) caps the length of its stick (both sticks were clamped per axis, the player's and the NPCs', so a diagonal was 1.41 of the hull's rate; the cursor's stick is round too) and limits how fast the stick moves; an easing lag there instead sat inside the steering loop and left tier-1 pilots weaving 15 degrees either side of a heading for good. Pulling away from an obstacle, another ship or the ground takes the whole stick at once. Every number of both is invented and live through `__debug.flight`.
- Ships fight in `World.ships` (`ShipContacts`, `src/space/contacts.ts`), a list beside `World.targets()`, not in it: every member is a `Living` (key, side, damage with a source) so blame and retaliation work, but the ground brains and the Force powers never see a hull. The player in any form (on foot, or the ship they fly) is remembered as `PLAYER_KEY`, and `find(PLAYER_KEY)` answers with the ship the player flies now, else the player on foot. A ship's condition is its `ShipCombat` (shields and armour front and back, parts, chassis, from `src/space/shipStats.ts`, whose numbers are all invented), mirrored into `vehicle.hp` so a destroyed ship is what it always was to the rest of the game; its handling starts from the vehicle's own spec, kept from before the combat first wrote it, times the class (a hull over 18 m is big; a smaller one the manifest calls a bomber, except the TIE Advanced, flies at 0.82 of its speed and 0.77 of its turn) and the family's trait (`FAMILY_TRAITS`), so only a stock fighter or big hull of a family with no trait flies exactly as before (the Y-wing is slower, the TIE interceptor and A-wing faster, all invented), and a refit restats from the undamaged numbers, not the spec a downed engine left. A bolt reaches it whole through `Hittable.takeBolt`, where the game's per-layer hit effects (`ship_hit_effects.iff`) are placed at the true hit point in the hull's frame, so they ride the ship; when the combat file has none for the layer struck (or there is no combat file) it answers `'taken'` and the bolt's own burst and hit effect play as before. A combat file that arrives after a ship was adopted is given to it then (`ShipCombat.setEffects`, then a restat). A collision skips the shield (`applyCollision`) and costs the same share of the chassis it cost of `hp` before ships had a fight, the armour taking the first of it (a choice, not the client's), and one collision with another ship takes at most `COLLISION_CAP_SHARE` of the front armour and chassis.
- `DriveInput.stickX`/`stickY` hold flyShip's stick where the player's mouse cursor, an NPC pilot's hand or an autopilot puts it, for as long as it is given (x > 0 turns right, y > 0 noses down, and `steer` > 0 rolls right, the mouse's own senses; `pilot.ts` derives its stick from them) and `DriveInput.cruise` eases the speed toward a wanted one at the spec's accel and brake. `Vehicle.resumeFlight` clears `held` (the held branch of `update` already drops the collision check's memory every held frame, so the first free step is not taken for a hit).
- Every ship attachment hangs under the node it names (its parent's hardpoint, or its parent's origin at its place), a wing under a pivot turned about its own Z, so what rides a wing follows it with nothing copied: guns keep their muzzle node and are read at the shot (`Vehicle.muzzle`), glows are sprites under their hardpoints (made, with their trails, before the ship is prepared, so they are compiled with it) and trails follow the sprites. Each wing opens on its own clock (one shared counter opened four wings four times too fast). The hull colliders under a pivot are moved with it (`setTranslationWrtParent`, `setRotationWrtParent`) while it moves, and the mass sits on a piece that never moves. Hardpoints on parts never set the seat or the cockpit eye (a turret body's `turretcamera1` would). A ship is centred across on the meshes that do not ride a wing and along on the whole box (`frameExtents`): framed on its closed box, the B-wing turned about a point 7 m out along its flat wing, and centred along on its hull alone, the X-wing's turn point moved 0.77 m forward (its foils' engines reach behind the fuselage). A vehicle is prepared (`World.vehiclePrepare`: material schemes, textures, then a compile a drawable at a time) before `new Vehicle`; `World.breath` is the yield between steps (a MessageChannel when the tab is hidden), and a hidden tab compiles with `compile`, not `compileAsync`, whose link poll is a chained timer a hidden tab holds to one a minute. A travel during that wait is caught by the Terrain changing (`spawnVehicle`), and the vehicle is disposed rather than left in the next world.
- A ship converted with its fit (`fit` in its manifest entry, resolved against `components.json` by `shipFit.ts`; a pack without `components.json` is built as its stock tree) hangs its components from the fit, never from `attachments`: the garage's `assemble` drops every `kind: 'component'` def, every def with `owner` (what a stock component's own client data produced) and the stand-in of a slot the fit fills, and a def whose parent was dropped is hung by name after the fit's parts (`fitTree` in `shipMounts.ts`, tested on the X-wing's and the YT-1300's trees). The fit's parts go through `hangParts` (`shipMounts.ts`): by hardpoint name, the hull's own first, then anywhere on the ship, in repeated passes, never at the origin; each part's `children` whose chain ends at the part are hung on it with `hangAttachments`, and the ones with no `parent` (the Y-wing engine's "on" appearance on the hull's `engine1`) are pending parts marked `byName`, which `hangParts` hangs over the whole ship in a second round once every fitted part is on, never with `hangAttachments(part, …)`, which only looks on the part. `ShipBuild.fitParts` keeps each slot's top nodes (`''` for the ship's own by-name nodes), so a refit takes a slot down and re-hangs whatever rode it; `ShipBuild.standIns` keeps each empty-slot stand-in (the YT-1300's `yt1300_engine_none`), which every swap decides again (`settleStandIns`: down when a part of its slot hangs, up again when none does).
- Ship paint renders take 50 to 800 ms each, so they run in `paintWorker.ts` through the customizer's `renderOff` hook, never on the main thread. A ship wears the GLB's own materials until it is first given custom paint; then it gets its own copies (`ShipPaint`), prepared on stand-in meshes and compiled (the program is found, not built) before they go on, and a repaint swaps `map`, and on a glowing paint shader `emissiveMap` as well, between textures on the same channel (the glow is split from the painted colour in the worker, `glowSplit.ts`, byte for byte the converter's split, with the mask from the texture the pattern chose; a glow map is never added to a copy that has none). The copies leave the world's material sets through the paint's `forget` (`World.forgetMaterials`) when the ship goes or returns to stock. A render that lands after the paint changed course is dropped by a generation check made in the same step the texture would go on (`Customizer.accept`).
- A refit (`Garage.refit`, `World.refitVehicle`) stages the new parts, with spare glow sprites and trails for any engine spots the new look can bring (a part's, or the hull's thrusters when a slot is emptied) and any stand-in the slots may need, in a detached group, prepares them in their own materials (what a part wears whenever the paint is or goes back to stock: prepared only in the copies, a part would compile on a live frame when the paint went back), then lets the paint track them (which puts the ship's copies on while it is custom) and prepares again if that changed any material, and waits for their paint (`stageRefit`). One vehicle's refits run one after another (`inTurn` in `World.refitVehicle`), each staged from the fit the last one left, since two staged from the same fit leave the model and `v.fit` disagreeing. Then in one synchronous step (`refitSwap`) it moves every glow sprite to the vehicle's group, takes the old parts down and re-hangs what rode them, hangs the new ones, measures the guns and engine spots again with the wings closed (`collectMounts`, in the group's frame) and re-hangs the glows (`rebindGlows`: surplus sprites parked, hidden, under the group, their trails aged out; `v.engines` and `v.trails` rebuilt in place, so the heat shimmer follows). - Normal maps are Direct3D's (green down); the converter writes them as they are and the game uses `normalScale (1, -1)`.
- An animation table's string selector (SSAT) keeps its value list in a chunk tagged `VAL ` (three letters and a space), not `VALS`: an i16 count, then each value's name and the i16 index of the branch it picks; several values share a branch. The converter names branches for their first value (`loop_riding:vehicle_speeder_bike`, `skill_action_5:dance_18`), the default branch plain, and writes every branch's values to the manifest as `variants`; `rig.variant(base, value)` resolves them in the game.
- An animation file (`.ans`, `FORM CKAT > 0001` or `FORM KFAT > 0003`) may carry a `FORM MSGS` saying when things happen inside the clip: an `INFO` count, then one `MESG` per message, each an int16 frame count, a name and that many int16 frame numbers. 3,308 of the 8,351 retail animations carry one and every one parses to the byte, which is checked on every file of every run rather than once by hand. A clip's frames are numbered 0 to one less than its count, and 1,524 marks sit exactly on the count: one past the last keyframe, which is the clip's last instant and a looping clip's wrap, so a reader must expect it rather than call the file corrupt. The shot marks (`fire1..fire11`), the hardpoint effects, the cinematic camera cuts and the marks that put a weapon in a hand and take it away are the code's already and are left out, which leaves the footsteps, the voices and the blows landing. A mark's time is `frame / fps` from the clip's own rate, not the fraction times a glTF clip's duration, which is exact only for a looping clip. Jedi Academy's own marks are in `models/players/_humanoid/animevents.cfg`, in an `UPPEREVENTS` and a `LOWEREVENTS` block, and their frames count from each animation's own first frame and not from the shared `.gla`; both of its humanoid config files must be read from the archives the game ships and from nothing else, because any `.pk3` dropped into the folder overrides them and a mod that doubles a walk's frame count puts a footstep a quarter of a cycle out. The other direction is caught by checking every clip's frame count against the clips already converted for the player, so it shows in `status` instead of in the feet. A name written with `%d` is drawn from every index range the event lines give it, and the extension a sound is named with is not always the one in the archives -- it slips both ways -- so every lookup tries the other before calling a file missing, as Jedi Academy's own loader does. A mark's chance is Jedi Academy's own convention and not a fraction: it is out of a hundred and nought means always, so 516 of the 519 marks in the pack carry nought and reading the field as a fraction dropped every footstep, voice and effect it has, leaving only the three lines that carry 30.
- A mobile's animations are shared: every appearance with the same skeletons and animation table plays one pack (`mobiles/anims/<pack>.glb`), so a clip is baked once for the hundreds of templates that use it, and the pack's JSON names the clip for each role rather than the game guessing by name. The tables nest their selectors (a mount's branch outside a mood's), and the shipped flattener loses the inner one, so `mobiles` has its own path-keeping flattener and picks the wild, calm, unridden branch: a bantha walks at 0.86 and runs at 3.47 m/s, not the ridden 6.93. Packs are compacted on the way out (no track for a joint that never leaves its bind pose, two keys for one that holds still), which is about half the bytes, and a one-frame pose is written twice a frame apart because three finishes a zero-length clip on its first update and poses a repeating one at NaN.
- How a rider sits comes from three mount tables (`datatables/mount/`): logical_saddle_name_map (a `.sat`, listed as its `_hue` variant, to a logical saddle), saddle_appearance_map (to the saddle's appearance), rider_pose_map (appearance and seat to the pose). A rideable vehicle's `pv_*.sat` is a placeholder whose body is the static appearance of the same name; the pose still keys on the `.sat`.

The mounts the game really let players ride (`datatables/mount/valid_scale_range.iff`) are exactly those whose mesh carries a `saddle` hardpoint; for the bantha, kaadu, bol and rancor only the `_hue` appearance the mount tables list carries it (the plain one has identical geometry and none), so it is read from there when both share a skeleton. The other creatures in the saddle map have no hardpoint and get a saddle on the back as measured posed.
- Every retail saddle (`appearance/mnt_saddle_*.apt`) has one hardpoint, `player`, at (0.0002, 0.164, -0.060), and the saddle poses' clip root (`loop_riding:saddle_*` and the plain `loop_riding`) is (0, 0.165, -0.057): the game stands the rider at the saddle's origin and the clip lifts the pelvis to `player`, as with the speeder bike. Nothing in `Garage.finishSpawn` may be awaited after `new Vehicle`: the body is live, falling and unsprung until the world adds it, so the saddle model is loaded beside the creature's before it.
- A rideable vehicle's `pv_*.sat` is a placeholder only when its animation table is the shared `monstrosity.lat`; the walkers (AT-ST, AT-XT) and the basilisk carry their own table and mesh and walk with them. The game's own rider poses are what they are: the AT-ST seats its pilot as the hover chair does, the AT-XT as a pod racer.
- Three applies tone mapping only to the default framebuffer: with a render target bound the materials come out linear, so post-processing must end in an OutputPass, and toggling it recompiles every program (the tone mapping is in the program key). World warm-up binds `world.compileTarget()` (the effects' scene target) around every compile, so the programs built behind the loading screen are the ones drawn; switching Effects compiles the other variants in the background (`reconcileEffects`) and changes over when they are linked. Three's own output pass works its tone-mapping defines out on its first draw, so it is given one throw-away draw before the warm-up compiles it, or the program built there is one no frame ever uses. Every effect's settings, knobs, pass order, products and budgets live in `src/core/fxRegistry.ts`; `npm run test:fx` checks them.
- The game seats a rider at the vehicle's authored origin and the riding clip's root offset puts the pelvis in the seat: a speeder bike's `player` hardpoint is exactly its clip's root (0, 1.16, -0.04), so the rider must not be placed at the hardpoint as well. The garage recentres a model on its box, so the authored origin is `model.position` afterwards. A seat on a saddle's `player` point or on a creature's own `player` hardpoint names the pelvis instead and takes the clip's root off (`seatPelvis`); a pod racer's guessed cockpit (`podSeat`) names the pelvis and takes the root off itself; a ship's pilot is placed by the eye instead (`Vehicle.eyeSeat`, the cockpit-frame lesson), and a wild creature's bare back names neither; `__debug.seat(dx, dy, dz)` nudges a seat live and prints the pose's root.
- The scene draws into `postfx.sceneTarget`, which no effect writes into; the chain ping-pongs between two buffers with no depth. A pass may sample the scene's depth texture only while a target without that texture is bound: Chrome drops the draw otherwise (INVALID_OPERATION, and silently once its error cap is hit), which is why the god rays and the speed blur never drew before. Geometry products (heat, water mask, velocity) attach the same depth texture read-only, so they never sample it; a target sharing it must be the scene target's size, and is detached before being disposed on its own, since disposing a target disposes its depth texture. `__debug.fxCheck()` names a step that errors.
- A ship on a planet meets the ground through `src/vehicles/landing.ts`, not the springs: its foot is the hull's own `landing1` hardpoint kept between the hull's underside and `LANDING.gap` (0.3 m) below it (clamped both ways: the runtime's box is the assembled ship's, re-based so its underside is zero, and a point above that would hold the ship with whatever hangs lowest in the ground), the floor under it is a ray among what stands still (never the terrain inside a building), and the put-down fits a plane to five samples, refuses a slope past 20 degrees and eases onto the pose over 1.2 s, after which the hull is held (`Vehicle.hold`, a pose in a frame or in the world, written before every step; `release` lets go, and `teleport` and `launch` let go first). Stopped and powered a ship holds its height, but only while the pilot asks for neither up nor down: the old 1.5 m/s sink is what Ctrl still gives and what brings a hull low enough to set down, and without it a ship that has flown can never stop being airborne, so the whole spring and hover path goes unreachable. `SHIP_GROUND.rule = 'springs'` puts the old hover-only ride back for every ship and lets go of one already down. A ship in a building's rooms is followed through the portals as a mobile is (`World.trackVehicleRoom`, `LayoutStreamer.trackVehicleCell`, from the hull's middle with no walker's lift) and takes the inside filter, written into the filter half of each collider's groups so nothing loses its memberships; every number of the landing is invented and lives in `LANDING` and `SHIP_ROOM`, with `__debug.landing` as their knob.
- Another player's body is a sensor in a collision group of its own that collides with nothing (`Group.peer`, membership the peer bit and a filter of zero): the engine's rule is that a query sees a collider only when the query's filter accepts the collider's membership and the collider's filter accepts the query's, so every query that passes an interaction group misses a peer while a query that passes none is not group-tested at all and finds it — which is exactly the bolts, the blades and the aim rays. A sensor is never in the solver, so a body that teleports between messages can never shove a ship or a crate. Two things measured rather than assumed: rapier's character controller does **not** skip sensors (it stops dead on one the groups let through), so `Physics.isPeer` is a real second line and not decoration; and a capsule of zero radius does not throw but hands back a handle that is not a handle, so the live knob floors both shape numbers. The queries that pass no group at all are, almost all of them, the ones meant to find a body — a blade's sweep, an aim line, a hitscan, a flame cone — with three that are not: `Physics.groundDistance` is the one whose answer is a surface to stand on (it skips peers itself, or a peer standing under a speeder is its road), and the turrets' line of sight and `World.clearGround`'s set-down probe each pass `groups(Group.all, Group.all)` so a player standing in the way neither quiets a turret nor moves where a ship lands. Nothing on this side ever takes health off a peer: a blow goes out through `RemoteBodies.onBlow` and the player who was shot is the only one who subtracts — which is also why a peer joins `World.targets()` only while a blow struck here could reach their browser, since the local wildlife would otherwise chase a picture it can never finish.
- A vehicle's hull colliders leave out the terrain group (`HULL_GROUPS`): the springs hold the vehicle off the ground from their rays, and hull-versus-heightfield contact made every slope snag and jolt.
- An NPC ship is an ordinary garage vehicle flown by `vehicle.autopilot.drive` (`NpcBrain`, `src/space/npcBrain.ts`, every number in it invented). `World.spawnHull` builds its hull through the garage with its tier chassis's fit and `World.vehiclePrepare`, and leaves it out of `world.vehicles` hidden, held, weightless and ghosted, because nothing steps a vehicle outside the list and its live body would fall or be struck while the rest compiles; `NpcShipManager.spawnType` then compiles what the garage made after the vehicle (the clear glass stand-ins, `World.prepareExtras`), adopts its combat and puts it in the list with nothing awaited between (`ShipContacts.sync` drops a contact whose vehicle is not in the list and re-adopts it as neutral, losing its type). While play is paused (`world.simulating`, set first in `stepVehicles`, which `__debug.advance` also calls) every NPC ship is `held` and nothing thinks, fires or streams. `vehicleReach` returns Infinity for an autopilot hull, so nothing mounts or boards one, and the garage's clear leaves them. Its def is a copy of the garage hull's (same `id`), so closing the ship Edit page refits only the player's own spawned ships (`refitSpawned` skips an autopilot hull, as do `nearShip` and the console's nearest-ship picks), or every NPC X-wing would take the player's fit. `World.unload` disposes the manager before the vehicles, and a spawn still being built then finds it disposed and throws its hull away. The brain reads every ship's velocity as its nose times its speed (what flyShip sets a flying hull to), since `body.linvel()` makes an object per call.
- A flying hull is driven by setting its velocity every step, so a contact the solver resolves is overridden the next step and the hull wedges into whatever it hit: `flyShip` compares the velocity it commanded with what the step left (`commanded`), takes a big loss as a hit, and then leaves the body to the contacts for a few tenths of a second. The hull collider ignores the terrain heightfield (`HULL_GROUPS`), so the ground is checked by height: below it is a crash and the hull is lifted out.
- Two ships that meet are both hurt, whichever of them measures it. That test is each hull's own, so a hull that cannot measure (held while play is paused, when the flown ship flies on and every NPC ship is held; in its own hit's moment; hovering on its springs, where ships have no hit test) was an obstacle that took nothing. Now the hull that finds the loss asks the narrow phase which ship's collider it touched (`Vehicle.shipTouched`, through a handle-to-vehicle map the constructor fills and dispose empties) and hands that ship what the contact's momentum says it lost, this hull's loss times this mass over its own (`partnerLoss`, `Vehicle.rammed`), with the same moment to the contacts, so it never measures that contact again. A ghosted hull is in no group and meets nothing. One collision with another ship (contacts with the same ship, keyed by its body's handle, within `COLLISION_BOUT` seconds of the last: two hull shells that met stay wedged and meet again each time the contacts let go) takes at most `COLLISION_CAP_SHARE` of the ship's own full front armour and chassis (`ShipCombat.collide`), so a ship at full health lives through meeting another; both numbers are invented, in `shipStats.ts`. A station, an asteroid, the Star Destroyer or the ground hurts only the ship and is not capped: a ship held into a station face strikes again about every half second and is destroyed, as it always was.
- Never give the effects' render target `samples`: three resolves a multisampled target at the end of every `render()` call, and the portal renderer makes a dozen calls a frame, so bloom alone dropped the frame from 144 to 11 a second. The target is single-sampled and FXAA smooths the edges.
- A NaN pixel from any material becomes, through the bloom's mip blur, a screen-sized black box whenever that object is in view (the owner found a plant on Tatooine that does it). The effects chain starts with a pass that zeroes NaN and Inf pixels; `__debug.blackBox()` scans the frame and names the object under the first bad pixel, which is how to find the material at fault.
- The motion blur merges two velocities per pixel. For everything still, the camera's reprojection of the scene depth, with a cut (25 to 60 m) pushed out past the far side of whatever the camera follows (`ctx.followFar`, from `App.followFar`), so the ship flown stays sharp at any size; last frame's view is taken with this frame's projection, so aiming's zoom is not motion. For movers, a velocity product drawn only for the objects `App.collectMovers` lists, and of those only the meshes that differ from the reprojection: what the camera follows draws only parts that move relative to it (wings opening, a weapon in hand); other movers draw everything while their root moves and only such parts while it stands. Limbs are not blurred on their own: no bone history is kept. The blur is a reconstruction filter (resolve, tile max, neighbour max, a depth-tested gather), so a sharp hull leaves no ghost in the ground behind it.
- Velocity draws go through `renderBufferDirect` inside an empty proxy scene's `onAfterRender`, one material per program variant (fourteen warmed behind the loading screen; fighters, peers and new mobiles prepared before they show), and must never throw there (three's render state would stay pushed). A direct draw skips three's own checks, so each mesh is checked every frame as `projectObject` would (visible up to the scene, actor layer, frustum) and drawn only after it passed on an earlier frame: a mesh never projected has no buffers, and drawing it saves a broken VAO for good. Records are checked every frame for removal, material swaps and disposed geometry. A variant's first real draw must not work its program out again (`side` is in three's program key, and a double-sided mesh first would compile a second one mid-frame), so `compileVariant` records the material version as three does after its own first draw. Remote players are listed with the relay's smoothed velocity: their glide between messages pulses at ten a second. - Three disables an AnimationAction when its fade-out finishes (`enabled = false`); an action reused after that shows its bones in the bind pose until `reset()` and `play()`. `rig.setState` restarts a legs action that has gone dead, and a saber move chained onto one already on the upper body stays there (`play(..., { upperOnly })`) rather than taking the whole body and fading the legs out; `__debug.split('BOTH_RUN2')` shows the halves and the live weights.
- A clip's own event markers (a foot landing, a voice, a blow, a body hitting the ground) are read against the action playing the clip, never against a clock: each is a fraction of its clip and is mapped onto that action's own duration, since 863 of the packs' clips play at a time scale other than 1. Foot events come from a whole clip or a lower half and only from the one such action with the greatest weight (a walk blending into a run steps once); everything else needs a whole clip or an upper half at half weight or more. A loop's wrap, a negative time scale and a restart are each handled apart, an action met for the first time picks its clock up in silence, and a frame that crossed more than half a clip (a hidden tab, a clip shorter than a frame) moves the clock on without firing. `crossed` and `ClipWatcher` in `src/audio/clipEvents.ts` hold all of it, and the node test pins each case.
- What a foot lands on is asked in the client's own order: the water over the point (the player wades, everything else surfs; chest deep it is swimming and there are no feet at all), then the room the body is in (the interior table's surface, and a ship's deck, whose rooms are a physics world of their own that no ray of the planet's reaches), then the thing it is standing on (one ray down with the fixed-or-bodiless predicate, the streamer's collider-to-template map, and the planet pack's `surfaces`, which lists everything that is not stone), then the ground itself (the chunk's own shader-family grid, which is the array the ground mesh was painted from, never the terrain sampler, whose main-thread cache is mostly empty and would generate a whole block to answer). The surface then picks `footstep_<surface>` out of the body's own client data, falling back to the plain `footstep`, which for a creature is its size's effect and for a person the species' own boots, shoes and bare feet: nothing in the game chooses footwear, its data already did.
- A player aboard a ship's rooms has their body in that room's own Rapier world: before any world unload (travel, switching character, removing vehicles) the player must `leave()` the room, or the body is left in a freed world. `travel` carries a ship across as a `ShipCrossing` with a `ShipCrew` record (place in the hull's frame, heading, at the controls) and boards the new hull with it. A sprite is worse than that for anything that must write depth: three's sprite program moves only x and y in view space, so the whole quad takes its centre's depth, and a wide sky body far off the view axis laid a screen-filling quad across the view a few hundred metres out and hid the zone behind it. Every space zone's environment file is one 348-byte ground sky copied into 23 files byte for byte, with none at all for the orbit added last, so in space nothing is built from it. Which star is a zone's sun is ours (`pickSuns`): the brightest by the flare's own ranking, and only ever a star with a glow, since the flare draws a star from its glow; a star within six degrees is folded in as a companion that takes the flare's second slot and no light of its own, so the scene's light count never changes. `SwgSky.spaceLightDir` is that star and is the very vector the world holds as `DayCycle.fixed`, so a live change of rule re-aims the sun, the cascades and the flare with nothing rebuilt. In space there is no ground for a star to set behind, so `World.sunInfo` skips the sun's height test and the effects' horizon fade is skipped too (four of the twelve zones' stars hang above the ship's horizontal in any case); the god rays count a pixel as sky only past a share of the far plane, and each sky planet writes depth through a stand-in out there — a cap of a sphere centred on the camera, which is the one shape whose every point is the same distance off in every direction. The depth buffer holds distance along the camera's forward axis, not distance from the camera, so that stand-in writes less than it stands at towards the corners of the screen and the band between it and the sky must be many depth steps wide (about 70 m a step at 7.5 km, 24 bits, a 0.05 m near plane). Every invented number is in `SPACE_SKY_TUNE`, live through `__debug.suns`.
- A space zone has no snapshot: its stations are `datatables/space/spacestation/<zone>.iff` (server names; drawn as `object/ship/shared_spacestation_<faction>.iff` by a table in `space.mjs`), its asteroid fields `datatables/space/asteroidfield/<zone>.iff` (centre, radius, count, seed, a style table of appearances with likelihoods, or a spline), and its sky is its `terrain/<zone>.trn`: SKYB names the six-sided skybox (`texture/<name>_<side>.dds`, 512 px; the ENVI cube map is what reflections see, not the sky, and drawn as the sky it is a blurry, misaligned mess), CLEA the clear colour, AMBI the ambient (alpha, r, g, b), PARA each parallel light (a byte, diffuse and specular as a-r-g-b, then yaw, pitch, roll in degrees, the same frame convention as the environment file's celestials), STAR the star ramp and count, DUST the motes' count and radius, CELE each star sprite (shader, size, a spare float, a byte, yaw, pitch, roll), PLAN the planets (the planet appearance, then the body's place from the camera, three angles, the halo's roll and the halo's scale, then a byte: the ground environment files' layout; the eighth float is not a size: it is 0 on all of Ord Mantell's bodies and on Kashyyyk's planet, which the old reading turned into size 0, and it does not follow the appearance's HALO chunk, since Dathomir and tatooine_moon_03 have none and a non-zero value, and Ord Mantell's haloed moon has 0). A body's size is its `.pln` appearance's radius (FORM PLNT > 0000 > SURF: a float, the shader, the radius; CLOD the same for the cloud shell; HALO the halo shader and a float), in the same metres as the place: the pack's `size` is radius over distance in the game's unit (`SPACE_BODY_FRAME` in `space.mjs`, world.ts's 240 m at 2600 m). In space the procedural ground must not be built at all: placed objects anchor the ground to their height, which raised a needle of terrain under every asteroid, and the ground plane three kilometres down filled the lower half of the view. The planets and moons wait on a picture each: `loadSpaceBodies` checks the load token after every one, or a travel or jump during them added the old zone's bodies to the next zone, where nothing tracked them, and they piled up trip after trip (a Tatooine in Endor's sky).
- A station's docking lanes are hardpoints on its hull (`dock_<lane>`, `dockradius_<lane>`, `approach_<lane>_<n>`, `exit_<lane>_<n>`), written into `space.json` per model by the space command. Three things about them are not what they look like. A dock's own forward is the way a ship **parks**, not the way in: on the five hulls that carry lanes it stands between 9 and 100 degrees from the direction the lane is flown (a row of parking bays all face along the row while their lanes come in from the side, and the capital ship's face back along its hull), so the way in is always the lane's last leg, and the parked turn is the hardpoint's unless it faces back out the way the ship came (`DOCK_FACE`, `dockingMath.ts`). The numbers on the points are not an order: one station keeps two whole corridors under lane `a` with their numbers interleaved and no `approach_a_1`, so the points are chained by geometry outward from the dock. And a lane's letter is not whose corridor it is: that same station files its third dock's approach under letter `a` and its exit under letter `b`, which left that dock looking like a dock with no points and had a ship parked at it on a direction borrowed from a neighbour, and had letter `a` parking one way down one of its corridors and 138 degrees round from it down the other. So each chained corridor is put back on the dock its innermost point is nearest (`regroup` in `lanesOf`), after which every dock on every hull has a real corridor, nothing is guessed, and the hardpoint's turn is within 100 degrees of every lane. A pack gives a placed object only a place, a turn and a bounding radius -- the capital ship's is 1881 m while its lane points are 615 m from its origin -- so whether a lane can be reached without flying through the hull is two bearings in the model's frame, not a trace: the point must be on the ship's own side of the hull and the leg must not arrive against the way the corridor is flown.
- One ship clamped onto another is ours entirely: the client has no ship-to-ship docking, no hardpoint names one and its one `canDock` string is read by nothing in the archives, so every rule is in `CLAMP_TUNE` (`dockingMath.ts`) and live through `__debug.dock({ clamp: ... })`. Three things about it are not obvious. A carrier's box top is not its deck: a tall thing standing on the hull sets the box, so the clamp spot is lowered onto the skin by one ray straight down the carrier's back (`lowerOntoSkin`, kept per pair of hull models), or a fighter would ride a bridge tower's height above a capital ship. The clamp is written at the top of `stepVehicles`, before any hull has moved, so the carrier's pose is read a step ahead from its velocity and turn rate (`leadPose`), or the carried hull rides a constant 1.67 m astern at 100 m/s and swings in every turn. And the hold's frame is the carrier group's own `matrixWorld`, not a copy of where it was, because `main.ts` only steps docking while play is simulated: with a copy, a hull left the carrier behind for as long as the ship menu was open -- which is the menu the pilot must open to undock. A driven tab never draws, so the clamp works that matrix out itself each step (`updateWorldMatrix(true, false)`, parents and self only). Both hulls of a clamp answer `Docking.docked` (`carrying` for the one carried, `carries` for the one carrying, which in the two-browser case is the grant it made), so wave 3's one refusal covers the jump, both crossings and the landing for the pair with no new code: nothing carries two ships across a zone change, and a carrier that jumped would take the other ship into a world that then dropped it. An answer from another player is checked again when it arrives, since it can be twenty seconds old and the ship may have flown off or opened the throttle since; the two clocks are the step's own seconds, which stop with a panel open, deliberately, because the ship menu is the only place a request can be answered. Crossing between the two ships' rooms is only ever offered for two hulls in this world: another player's rooms are not simulated here.
- A space zone's pack is version 3: beside what it always held it carries the zone's nebulae, its asteroid fields' shapes, its stations' docking lanes and the sound a dock plays, all in the game's frame already (they are drawn rather than jumped to, so the converter mirrors X once instead of every reader doing it). The nebulae are `datatables/space/nebula/<zone>.iff` row by row, with the four colours as the table stores them (alpha first) and a row's lightning kept only when the row both names a `.ltn` and has a strike rate above zero: 171 of the 250 retail rows, from 4 of Endor's 41 to all 33 of Naboo's, and six rows name a rate with no file and do no damage. Every zone that strikes names the same appearance, `appearance/pt_nebulae_white_02.ltn` (`FORM LEFX > 0002`), whose picture is a 2x2 flip-book of four frames at ten a second; its two waveforms read as the bolt's width and alpha is ours, and the 81 bytes after the two effect names are counted and not read. Both nebula shaders and both `_no_z` shell shaders name the same two textures, so a pack writes two images and the shells point at them. A station's docking lanes are hardpoints on its model (`approach_<lane>_<n>`, `dock_<lane>`, `dockradius_<lane>`, `exit_<lane>_<n>`, the drydocks, and the `hangar*` points as `bays`; the `<name>_damage<n>` ones are damage effects, which every part of these hulls carries, and are left out) and must be read as the model is converted: a placed object is drawn as an instanced mesh with no hardpoint nodes, and a station a kilometre off may not have its detailed model at all. A point's number rises outward along a path, a lane may hold more than one path (the neutral station's lane a holds two and a stray, so its numbers run 226, 429, 576, 575, 114, 245, 441, 589, 76 metres out), so each point also carries how far it is from its own dock and where one path ends is the game's reading; a dock's `forward` is not reliably the way in, since the Imperial station's docks face its own middle while their approaches run outward. Five station models carry lanes and three carry no hardpoints at all, so Dantooine and Kessel have none. All six dock client effects name a sound and no particle, so there is nothing to draw at a dock. The field table's `Name` column is filled on 70 of the 214 retail rows and is a designer's note as often as a label, so a field is named for its place.
- `Line.computeLineDistances()` builds a whole new `Float32BufferAttribute` every call and three never disposes an attribute it merely replaces, so a dashed line worked out again each frame orphans a buffer a frame: the attribute is made once and the frame writes into it. Picking a mark on the space map is done in screen space, the nearest projected middle within a dozen pixels, because a mark is a point five or six pixels tall at any zoom and `raycaster.params.Points` is read only by `Points.raycast`, so setting it retunes the rock cloud and does nothing for anything else; the ray is still cast for the things one clicks anywhere on, a shell's wall and a belt's line. A field that runs along a spline is drawn as the belt alone: the table's radius is how thick it is, not how far it reaches. Every number the map draws and picks with is ours, in `MARK_TUNE` and `VIEW_TUNE`, live through `__debug.spaceMap`, whose `pools` counts must stop rising once a zone's marks are read.
- A space zone's nebulae are drawn from the pack's own rows as two instanced sets, the glow set added and the mist set blended, with `facingPercent` of the quads turned toward the camera in the vertex program so that nothing about them is worked out per frame. The mist is re-ordered far to near on a clock with a floor as well as a ceiling: at a jump's 900 m/s a distance test alone asks for an ordering every few frames and each one rewrites every instance buffer, and the sort is a merge sort down a scratch buffer made with the set, since a typed array's own `sort` with a comparator allocates both the closure and a working copy of the array on every call. A nebula whose middle is more than 6 km off is scaled toward the eye until that middle is 6 km away, which keeps its apparent size exactly (only the depth it is tested at changes) and is how it shows past the 9 km far plane instead of being cut by it; the price is that anything solid between 6 km and where the nebula really is now stands in front of it. From inside one almost none of its own sheets are drawn, since a sheet fades out as it fills the screen, so `alpha` moves nothing in there and the haze sphere about the camera is what is seen and what `shellAlpha` tunes. Lightning runs on the wall clock, each nebula's time line cut into slots of one over its own rate with slot n hashed from the nebula's name and n, so two browsers see the same strikes at the same moments with nothing sent between them, exactly as `weatherSchedule.ts` keeps the weather shared; the bolts are a pool built with the zone, a strike whose far end lands near the player's ship is moved onto it and hurts it through the ship's own damage path, and `__debug.nebulae({ strike: true })` fires one now, since `__debug.advance` does not move the wall clock. Everything of theirs is built while the loading screen is up, so the warm-up compiles it: the sheet buffers are made for the whole zone's cap and moving the density refills them rather than making a buffer, a material or a program, while the three numbers that are spent when the bolt pool is built (`beams`, `beamSegments`, `waveAlpha`) are named in `BUILD_ONLY_KEYS` and take effect at the next zone load. Every number that places a sheet, sizes it, fades it or times a strike is ours and lives in `NEBULA_TUNE`.
- A lightsaber's appearance is an `.lsb` (form LSAT): BASE is the hilt's `.apt`, ASND its idle sound, a BLAD form holds SHDR (the blade's shader), LGTH and WDTH (metres), OPEN and CLOS (seconds), and an optional LGHT form the light (COLR as r, g, b, a bytes, RANG and TIME two floats each). The crafted sabers are under `object/weapon/melee/{sword,2h_sword,polearm}/crafted_saber/`; there is no `object/weapon/lightsaber/`. The blade colours are `palette/wp_lightsaber.pal`.
- A lightsaber is heard from the blade renderer, not from the code that swings it: `SaberBlade.update` is the one place that knows a blade is out, where it is in the world and how fast its tip is moving, so the hum, the ignition, the shut-off, the rain hissing off it and the boil under water all hang there and the player's blades, the fighters' and the mobiles' sound the same with nothing in `player.ts`, `npcs.ts` or `mobile.ts` to say so. A blade snapped on rather than ignited (the thrown saber leaving the hand and coming back) is switched quietly. Hanging a loop on a renderer means the loop outlives anything that stops drawing without switching off: a mobile is culled as a whole group (`group.visible`), so its blade renderer simply stops being called while the blade is still lit, and a mobile that dies off screen never gets a frame in which to put it out, leaving a hum in the air where it last stood for as long as the thing lives. So every blade stamps the time it was last drawn and a sweep (`SaberSounds.tick`, from the top of `SaberBlade.update`, which the player's own blades run through on every frame) lets go of any hum undrawn for half a second, leaving the voice lit so the blade hums again the moment it is drawn once more. A blow of the player's is placed at the drawn blade rather than at the body, because aboard a ship `player.pos` is in the hull's frame and the drawn blade is always in the world's, and a Force power at `player.worldPos`, which is the body in the world either way; both are given the ear's own room (`World.listenerSpace`), or a blade in your own hand is heard through the muffle the moment you walk indoors.
- Jedi Academy marks the frames its own moves sound on (its specials, katas, back attacks, spins and kicks; every ordinary attack of every style carries nothing), so a swing asks the clip-event pack first and lays one whoosh per mark on the audio clock at its own fraction of the move's real length, speed and all, and only a move with no mark whooshes once as it starts. Scheduling beats a timer here: Web Audio honours a start time to the sample, so a kata keeps its rhythm whatever the frame rate does, and a move cut short takes its unsounded whooshes with it. Its files have no `.snd` of their own, so a template is made for each role at the game's own lightsaber templates' settings and hung in front of the bank's lookup, with the sample path written `../jka/<path>` against the bank's own samples folder.
- Jedi Academy's torso does not face the view while moving: CG_PlayerAngles puts the legs at the movement offset (45 degrees for a strafe, 22 for a diagonal) and the torso at a quarter of it, so the shoulders lean a little the way the legs go. A torso turned all the way back to the camera read as twisted the wrong way. The special moves (katas, kicks, lunges, the jump attacks) are whole-body clips and must never be split off the legs; only plain swings ride the upper body over the run.
- A mesh's BOX chunk holds its two corners with the larger first: read as min then max, every pack's `bounds` came out with min and max swapped (`readBounds` in `msh.mjs` now takes them componentwise; packs converted before carry the swap, so game code must take extents as `Math.abs(max - min)` and never trust which corner is which). The weapons rack's "far end" was on the wrong axis because of it, which is what made a measured aim correction turn the guns 90 degrees.
- The game's blaster poses point close to the view once the barrel is read along the true long axis. `correctAim` measures the barrel against the crosshair each frame and turns the spine up to `AIM_SPINE_MAX`, the body's heading beyond that; the tuned turns (`gunTune`) only apply with the correction off. Prone is left to the game's poses.
- A mount's seat rides its skeleton: `hangOnBack` (`src/vehicles/saddle.ts`) hangs a guessed saddle or a bare seat on the spine bone nearest it (never a bone of the head, a tail or a limb, by its own name or any bone's above it: by name alone the ronto's saddle rode an ear flap and the kliknik's a pincer), and the place is measured on the posed, skinned vertices (`posedBack`, `getVertexPosition`), only those whose heaviest bone is the back's by the same rule (`offBack`): the ronto, bolle bol and sharnaff hold their necks up over the middle of the body, and the highest vertex there was the neck's, a saddle 2.3 to 2.8 m up on top of the head; the vertices are read after the idle clip has posed the skeleton once (`mixer.update(0)`): a creature's rest pose can stand two metres from its idle (the condor dragon's), and a rest-pose measurement puts the saddle inside the body. The camera's `forward()` is the look direction, `(-sin yaw, 0, -cos yaw)`; `__debug.advance` also steps the creatures, so powers can be tried headless.
- `__debug.advance(s, keys, true)` keeps its keys down until a later call names them without `hold`; a test that presses a key with `hold` and then calls advance with other keys still has the first key down (a crouch held rolls, then crouch-walks; a trigger held never releases a charged shot).
- Anything that happens aboard a ship's rooms must live in the hull's frame: the player's `pos` already does, so bolts fired aboard carry a `frame` (the hull's live world matrix and the room's own physics), the thrown saber is fed the hand and the aim in that frame, and the world-frame sweeps skip the aboard vehicle. A transient particle effect must end on its own: many of the client's hit effects loop for ever, so `Instance.update` finishes a transient after one run (and after one life for an emitter that never runs out).
- A template's integer parameters carry a delta byte (' ', '+', '-' or '%') between the int8 data type and the int32 value: `intParam` in `objtemplate.mjs` reads offset 2. A gun's `weaponEffect` (bolt, rocket, projectile_rifle, ...) and `weaponEffectIndex` name a row of `datatables/weapon/weapon.iff`, which names the shot's `.prt`, the muzzle flash and the hit and miss client effects per surface; the weapons command converts those into the pack and writes them as each gun's `fx`. The flame throwers are bolt 21 (a fireball), the lightning rifles rocket 3 (the lightning beam), the slugthrowers `projectile_*`.
- What a gun sounds like is two tables, not one, and they answer different questions. `datatables/weapon/weapon.iff` carries fifteen client-effect columns a row -- the fire, the hit on a creature, on metal, on stone, on wood and on anything else, the miss in water, on terrain, on a creature, on metal, on stone, on wood, on anything else and on nothing at all, and the ricochet -- and over its 70 retail rows 1,044 of those 1,050 cells are filled, every filled one names a `.cef` the archives hold, and every one of those names exactly one sound (1,002) or none (42) and never two. `datatables/weapon/combat_effects_ranged.iff` is the other: 271 rows, 267 keyed on a template's file name and four on a kind (`pistol`, `lightRifle`, `rifle`, `heavyWeapon`), 270 naming a muzzle sound and 129 a `Hit Target Sound`, which is the blow on what was aimed at and not on any surface (its commonest values are the flesh hits), and not one of the 271 naming a miss or a ricochet. So a gun takes its muzzle and its blow on a body from the per-weapon table where that table names them, and every surface and every miss from its weapon effect's own client effects; `combat_effects_melee.iff` is thinner still, 133 rows every one of which names a swing and only six a hit (three of them the lightsabers'), so a landed sword blow takes a sound of ours chosen by the kind of thing that swung. A bolt names what it struck by the collider that stopped it (`World.footSurfaces.templateOfCollider`), never by a ray cast down from the mark, because a mark on a wall is metres above anything such a ray could name; only a blast, which has no collider, asks what a foot landing there would, through the feet's own ray. A volley is keyed on who fired as well as on what, or six troopers carrying one rifle would be heard as one shot while a scattergun's eight pellets would be heard as eight. And the guns' clock is stepped beside the feet's rather than with the shooting, because that is the one place both the frame loop and `__debug.advance` reach every step: stepped with the shooting it stands still while the player is dead, in a panel or in the map, and every shot fired in that time after the first is swallowed as one volley.
- Every sound the game can play is a template (`.snd`): `FORM SD2D > 0003` for a sound with no place in the world, `FORM SD3D > [FORM SD2D > 0003] + 0001` for one that has a place, 7,171 of them (3,115 2D, 4,056 3D), of which 528 voice-over lines carry a stray empty `0001` chunk at the top level that the generic parser refuses, so the reader takes the first root form. The `0003` chunk is an int32 sample count, that many sample paths, then exactly 112 bytes in every one of them: 28 four-byte fields (the start delay, the fades, the loop count and the gap between loops, the category, the play order, how volume and pitch vary with pitch in semitones, the priority, and the metres within which the sound plays at full volume). How loudness falls off beyond that radius is the client's audio library's and is not in the archives. The `sounds` command writes the bank under `assets-private/sounds/` (about 856 MB, every sample copied as it is; a second run copies nothing): the background score and the instrument parts are left out, but the music the world places in a room and the three sounds `scene/hyperspace.iff` names for the jump's stages are kept and marked, because those are things happening somewhere rather than a score. Where each sound is used comes with it, out of the client's own data (`clientdata/**`, `FORM CLDF > 0000`: `CEFT`, `CSND` and `EVNT` an event name then a path, `ASND` the object's own loop, a `DAMA` form a damage band, a `VTHR > VSND` a name then eight paths — idle, speed-up, slow-down and run, then four sounds of the damage that state stands for — a `VGEF > INFO` a byte that is 1 over water then the sound, and `ENGS > INTS > INFO` a slot name, a sound and six floats that are not decoded) and out of the room, interface, weapon, door, ship power and hit tables. A path may carry backslashes, one or two leading `@`s, a doubled extension, or the absolute path of the machine that exported it, whose tail from the deepest `sample/`, `music/` or `voice/sample/` folder finds 22 of those 27. 168 sounds the game names are in no archive at all and 27 more are there but left out as music; both lists are written, with the names an already converted pack asks for, and `sounds.json`'s `aliases` resolve the names that differ from a file only in where an underscore falls.
- What a ship, a ship part or a vehicle sounds like is nowhere on its object template. A part's sound belongs to the look a slot shows rather than to the component in it -- the crafted components name no client data at all -- so the key is the attachment template that both the fit and the stock tree keep: 230 of the 441 attachment templates reach a client data file, 200 of those name a sound, 61 carry an engine set and 46 a booster, and an engine's `ENGS > INTS` rows are the undamaged run loop first and the 25, 50 and 75% damage loops after it. A `FORM INTS` at the top level is not the ship's interior: all 53 in the archives name one rocket loop, on the 46 booster parts and on the eight hulls whose booster is part of the hull, so a hull's room bed is the interior table's and never that. A hull's own client data usually carries nothing but the effect it is destroyed by, so its engine comes from its own looks table's `engine` column (the modal cell, as the stock parts are picked), which is the only answer for a hull whose engines are part of its mesh -- every TIE's column names an engine attachment with an empty hardpoint, so no model is ever hung for it and looking at what hangs on the ship loses the loop -- and that reaches 62 of the 63 hulls. Nothing names a vehicle's client data either: exactly one of the 63 vehicle templates names a file and the archives do not hold it, so a vehicle is reached through the same mount tables the rider poses use (`logical_saddle_name_map` to a logical saddle, then `saddle_appearance_map`'s `client_data_filename`), which joins all 60 of them. The idle, speed-up and slow-down loops are in no table at all: a run loop is named for its family with the word `run` in it and the archives hold the same name with `idle`, `accel` or `decel` in that word's place, tried both with and without the `_lp` a loop's name usually ends in, which is ours and finds a family for 55 of the 62 loops the fleet names; a run loop with no `run` word of its own is left without one rather than guessed at.
- The mixer (`src/audio/`) is one audio context with a master and seven layer gains (ambience, effects, creatures and voices, footsteps, vehicles, interface, music) made once and never added to or removed; a voice is joined to its layer only while its slot is silent, so nothing clicks. Slots are built on first use and then kept (40 positional, 8 with no place, 4 for the interface), and the panner only pans: its own distance model is off and the whole falloff is `distance.ts`, worked from the one radius the game's templates carry. Everything inside a template — the drawn delay, the gaps, the loop count, the fades, the drift and the offset a waiting bed comes in at — runs on the audio clock, handed in as a number, so a bed keeps its place whether anyone is listening or not and a hidden tab cannot throttle it (there is no `setTimeout` anywhere in `src/audio/`; the wait for a fade is a silent source of that length). Browsers let nothing sound before the first press, so the game unlocks on the first one it sees, falls silent when the tab goes unless the setting says otherwise, and starts nothing at all while `__debug.advance` runs, counting what it would have played. Nothing can be heard from a driven tab, so the helpers report numbers instead: `__debug.audio()` gives the state, the gains, every voice with the gain the listener would hear it at, and `recent`, the last dozen sounds asked for with what became of each, and `__debug.audioSelfTest()` builds a second mixer of the same class in an offline context and checks the rendered peak against what the template, the category and the sliders ask for. Every number of ours is in `DISTANCE_TUNE`, `VOICE_TUNE`, `GRID_TUNE`, `BANK_TUNE` and `MIXER_TUNE`, live through `__debug.audio({ … })`, except the pool sizes, which are read when the mixer is made.
- The world's own sound (`src/audio/ambience.ts`) follows the sky rather than working the mix out again: `SwgSky` blends up to four environment rows a frame and the ambience plays each row's own day and night beds at the very weights the dome is drawn with (`mixLength`, `mixBlock`, `mixWeight`), which is why a storm's bed rises with its clouds and a walk over an area boundary crossfades in sound as it does in sight. A bed has no place at all: it sits wherever the ear is, so walking into a cantina crossfades the street away instead of leaving the muffling rule to cut it off at the door, and every bed therefore takes a non-positional voice slot (363 of the bank's 406 `amb_` and `wtr_` templates are 2D, and so are 41 of the interior table's 45 beds), which is why that pool is the one that fills. A room's bed is the interior table's row for the layout the building's model key names and the cell's own name, falling back to the building's `default` row and then the table's, and a row whose bed the bank has not got is stepped over rather than played silently; a sound object the world itself placed in that room wins over the table's bed, or the chatter plays twice. A planet's placed sound objects come out of its own `sounds.json` in the snapshot's frame, so the runtime mirrors X and takes the layout's centre off exactly as `LayoutStreamer` does and a pack whose centre moves needs no rerun; each is one looping voice for the life of the planet, and one the snapshot put inside a building keeps asking for its room on the grid's own pass, because a building streams out and back as a new object with a new number. A particle effect's emitters have named a sound since emitter version 5 and nothing played them: a standing effect now keeps a loop that goes with it when it sleeps and comes back with it, and a passing one plays what it names once where it plays. The weather's channels are placed with `sound: false` and played by the weather instead, at the channel's own share of the mix, since a channel's effect sits on the camera and cannot know what share of the sky it has.
- The mixer's nodes are made once and then only written to. One master and one gain per layer, made at start and never added to or removed; a voice's slot (its gain, its panner, the dry and muffled paths, the low-pass and the two echo sends) built the first time that slot is used and kept for the session, so a game that has played nothing holds no audio nodes; a slot's output rejoined to a layer only when the layer changes and only while it is silent. The only thing made per sound is the `AudioBufferSourceNode` Web Audio requires, which disconnects itself when it ends. A voice's parameters are written at most thirty times a second and only when they moved, through `setTargetAtTime`; the panner only pans (`rolloffFactor` 0), so the whole distance curve is one function in `distance.ts` that a node test sweeps; every looping sound, real or waiting, sits in a four-times-a-second grid and is distance-tested on a pass rather than on a frame, which means every rule about where a voice stands must answer the same on that pass as on a frame or the two paths drift apart; a voice that gives way is moved onto a cut node of its own and faded out there rather than cut dead on the gain its replacement is about to write. The samples go the same way: a WAV is decoded in a worker at the file's own rate and copied into its buffer in slices, nothing about sound is ever awaited on a visual path, and a one-shot whose buffer has not arrived within a tenth of a second is dropped rather than played late.
- A sound is placed against the ear's own room, not against its distance alone. The listener inside a building and the source outside it, or the other way round, moves the voice off its dry path onto a muffled one (a low-pass and a drop in level, both ours; whether the client muffled at all is not in the archives), and a voice standing in the ear's own room is sent to that room's echo -- one of two impulses of our own, the long one for the interior table's room type 7, which is six rows of the 265 (four capitol lobbies, one cantina and one station greenhouse), and the short one for the other 259 it names. It is one echo or the other, never both, and the send carries the voice's own layer gain, since the echoes are shared by every layer and return straight to the master. The returns stand open and each voice's send is what moves, so a voice that leaves a room rings out instead of being cut off at the doorway, and a slot handed to a new voice has its dry, muffled and send gains cancelled and written outright rather than ramped, or the new sound comes in wearing the last one's muffling. The sky's sprites hang at 3500 m and are depth-tested, so the occlusion counts depth as sky from 98% of that distance along each pixel's view axis, compared as `1 - depth` (exact near the far plane, unlike a linearised distance); fog does not dim the sprites, so it does not dim the flare. The occlusion is smoothed in a 2x1 target the element draw reads in its vertex shader, so nothing is read back. The composite never lifts a pixel past exposed luminance 0.9 (display 0.874, under the 0.888 where white begins) and adds nothing above it, which is why by day the flare is mostly a streak and ghosts; `__debug.flareProbe()` counts it, and `__debug.flare().sources[i].turn` is how to steer to a star when flying.

- A third of a building's point lights sit outside their own cell's box, many in the ceiling above it, and exit polygons stick out of their cell's box by up to half a metre (Mustafar's crashed ship's torn bridge opening stands 3.8 m off its own plane): anything that clips to a cell box or casts a sight ray to a lamp must pad the box with the doorway's own vertices or clamp the lamp inside first.

- Which weather level is active was the server's and is not in the archives: `weatherSchedule.ts` walks each planet's levels from the wall clock (an anchor drawn from the planet's climate every two hours, one-level Metropolis steps every five minutes between), so every player on the relay sees the same weather without a protocol change. The sky blends up to four environment rows (two levels, two areas while crossing a boundary; `SwgSky.setMix`), both gradients crossfade on the dome, and the clouds are a fixed pool of four sheets whose drift is integrated per image, never computed as time times speed, so a strengthening wind never makes them jump. A sheet samples its image at `xz / repeat + scroll`, so the picture moves against the scroll: the drift takes the wind's heading off the scroll (`driftScroll`) to move the clouds the way the rain leans and the dust blows.
- The time of day and the weather can be run off a clock a server hands out (`src/world/sharedClock.ts`), and neither may ever be made to jump. The clock is `off` with no server address (`Date.now()` exactly, so nothing in the game differs by a line), `shared` while a server is answering, and `adrift` once the socket goes, where the last offset is kept so the day carries on at its own rate rather than springing back to this machine's wall clock; the offset is the median of the last nine round trips (a round trip slower than `maxRttMs` tells us nothing but its own delay and is thrown away, as is an answer to a question nobody is waiting for, and a `pong` after the clock has been put down must not open sharing again — only a greeting may), and it is eased as a pure function of the wall clock, so nobody ticks it, nothing is allocated and a dropped connection needs no one to come and finish it. `DayCycle` takes the shared time **outright only where nothing was drawn**: a `dt` of zero behind the loading screen, or frames that have been away longer than `gapSeconds` beyond the step they reported — which is how a hidden tab is told from a slow frame, since the loop clamps `dt` to a twentieth of a second and a two-minute absence looks identical in `dt` alone. Everything else is walked, by the shorter way round, between a quarter and four times the day's own rate for a drift and thirty times for a correction, so the sun never crosses the sky in a frame and never stands still; a correction by the shorter way can wind backwards, which is deliberate (racing forward through a whole night would take four times as long) and is `catchUp` on the knob. Move the day by the error alone and never by the step plus the error: the error is measured before the day is advanced and already contains the step, so `step + err` settles exactly one frame ahead for ever. `Weather.clockSeconds` reads a second, *walked* copy of the same clock (`walkSeconds`), because the schedule has no easing of its own and a correction taken in one go turns the wind's heading, the rain's lean, the clouds' drift and the step of the schedule together in a single frame; the walk sheds at under real time so the weather's clock is never seen to run backwards, and a difference past `weatherEaseMaxMs` is still taken at once, because two players agreeing on the weather matters more than one player's smooth wind. Anything that writes `day.time` by hand (`__debug.time`, the room air's sun aiming) holds the day until `__sharedDay({ release: true })`, and the held note on the screen says so; a greeting that *opens* sharing and being told there is no server hand it back by themselves, a reconnect does not. Where a planet sits in the shared day is `phaseFor(azimuth, maxElevation)`, worked out from the planet's own sun so it is the same number in every browser with nothing on the wire — and a hash of two numbers spreads them no better than chance, so the salt is chosen by measuring the closest pair over the real planet list and the test re-measures it. A parameter property in a constructor stops node's type stripping dead, so any `src` file a node test reaches must write its fields out.

- The aimed depth of field keeps its focus on the GPU in a 1×1 float ping-pong: the median of five half-resolution depth taps at the crosshair, eased in dioptres. The sky and anything nearer than the shooter's plane (`cam.orbitDistance + 0.4`, 0.6 m in first person) do not count. There is no lens until a surface has been under the crosshair this aim, and the last surface is held after. The aperture widens as the square root of the focus only to 40 m, since an unstopped aperture blurred the whole foreground whenever the focus went far. The lens-grid texels carry the raw circle of confusion, which rises with depth, so the gather orders taps without a depth fetch. The grid strides to a quarter on buffers taller than 2000 px, so the radius never outruns the ±3 tile dilation. Glows that write no depth (gun and ship particles, bursts, blade cores) are drawn into a `dofGlow` R16F product (1/z, MAX-blended, particles masked where bright), so a bolt at the focus does not take the blur of the town behind it. The wardrobe doll takes its lens pass (one render into a 4-sample half-float target, then a premultiplied gather, tone curve and sRGB onto its see-through canvas) only once zoomed in enough for a pixel of blur, with hysteresis to 0.7 px. - A flip-book shader is a root `SWTS` form: `NAME` the base shader (sometimes an exporter path like `c:\a_exported\shader\x.sht`, which lives at `shader/x.sht`), a timing form and one `TEXT` per frame (slot tag, texture path) that replaces the base's main texture. The timing forms are the client's switcher classes (their RTTI names are in the executable): `DTST` DeltaTimeSwitcher (count, seconds per frame), `DRTS` DeltaRandomTimeSwitcher (count, min and max, drawn per frame), `DPPT` DeltaPingPongSwitcher (count, min and max; plays forward then back), `DFST`/`DRFS` frame switchers only on samples. `SWSH` is the same with whole shaders as frames; the Theed `SWSH` frames are not in the archives, and the falls the world places are the scrolling `a_splitalpha_scroll` shaders.
- Texture scrolling is `TSNS` (slot tag, then u1, v1, u2, v2 per second) and only matters when the effect's vertex program adds `textureScroll` (`a_scroll.vsh`, `a_scroll_rgb1_a2.vsh`, the water programs): the offset is `frac(rate x seconds)`. Only the scrolling, split-alpha, flip-book and unlit-alpha-screen shaders among the 2,113 that blend and test with z-write off are converted as translucent, in a new `translucent` field that leaves `alphaMode` alone because the sky's celestial sprites read it; the rest (foliage, hair, fences) stay cut-outs, because three sorts transparency per object and an instanced field would draw far over near. A shader can write its effect inline (`FORM EFCT` inside the shader, the whitewater and a few dozen holograms, particles and UI shaders); its pass is read like a file's.
- In the client a fully masked emissive texel is the texture colour exactly: the `a_emismap` family lerps the lit texture toward the unlit one, and the rest add the mask inside a light that `saturate` caps. three adds `emissiveMap` after lighting, so the converter splits such a texture in linear light into a base colour `rgb x (1 - m)` and an emissive `rgb x m` (image names carry the mask's source); laying `rgb x m` over the full texture made every lit sign twice as bright by day. The mask is read from the pixel program, and two shapes misled: `a_specmap_bump_emismap` declares a local `sample` in two blocks, the diffuse map (its alpha the gloss) and then the normal map, whose alpha is the glow, so a local is resolved from the read nearest before `emisMask`; and the envmask assembly programs `lrp` toward the environment cube (ENVM) by their shine mask with the same instruction the emismap ones use toward the texture, so only an `lrp` toward a sampler on MAIN is a glow. `a_emis_full` and its alpha variants are unlit (`KHR_materials_unlit`, `userData.unlit`); `emisadd` is unlit and additive, with alpha forced opaque only when the source factor is One. - Kessel's and Deep Space's hyperspace points, Deep Space's fields and its Star Destroyer are made up (`INVENTED_*` in `space.mjs`, `source: 'invented'` in the pack); Ord Mantell's one point is space_nova_orion's row, whose station, fields and sky are Ord Mantell's own. - A retail zone's planets are pictures hung on the sky at a fixed reach with no true distance, which is all any of the game's own zones ever needed. A body that stands somewhere (`place: 'world'` with a true `at` and `radius`) is placed every frame at its true direction from the camera, pulled in to no further than the sky's reach and scaled by the same ratio, so the angle it covers is exact at every distance and it grows with true parallax. Its depth cannot be a sphere cap built for one angle, so it is written by a flat quad hung near the camera whose fragment program traces the ray against the body and writes `gl_FragDepthEXT` at the true surface: the sphere it traces must be the DRAWN one, read off the picture's own matrix and never the quad's, because a true middle two hundred kilometres out, squared in the ray-sphere maths, is past what a float in a shader holds, and the depth found is multiplied back out. The deepest it may write is kept strictly inside the god rays' sky threshold, or a far planet reads as open sky. One program serves every such body in a zone (three keys a shader material's program on its source), built behind the loading screen, and the placement is a few vector operations into one kept record.
- A ship's hit test compares the velocity it commanded with what the step left, so at jump speed a slow frame's damping alone (5.4 m/s at 900 m/s over three steps) reads as a crash: a ghosted hull (`setGhost`) skips the test, and the jump commands its cruise through `Vehicle.jumpCruise`. Everything the jump holds (the hull, the tunnel and the camera's far plane, the crew hold, the effects) is released by `Hyperspace.abort`, which `travel`, the map's teleport, leaving for the select screen and death all call first; P, M (the map and its teleport) and N (noclip) are locked from the enter stage until control returns and E too, except in the transit for whoever is aboard the rooms (the lifts and the controls, never the door: `pressJumpE`), and I and B from the countdown on, since closing the ship edit page refits the hull in place. The jump's tunnel is one mesh for the session, in the scene hidden from the start so every loading screen compiles it, drawn at render order -0.5 (after every sky layer, which write no depth and some ignore it, before every ordinary opaque) and depth-writing, so the world behind it fails the depth test; fully closed, the camera's far plane comes in to its tip so the world is not drawn at all, and goes back (with `World.onCameraResized` for the cascades) the frame it opens. A walker who steps out of a door from the enter stage until control returns is boarded again at the entry (`keepCrew`), since the move would leave them behind.
- A run across a system at kilometres a second is held, not flown: Rapier caps a body's velocity at 400 m/s and the hull's own hit test reads that cut as a crash, so the run writes the pose itself through the hold API and ghosts the hull. The work is in what must not happen at that speed. The placed-object streamer is held where it is for the whole run (`World.streamHold`), and the hold must cover the NPC patrols as well, which stream themselves in: a sleeping group within a few kilometres wakes, spawns its hulls and compiles their programs on a live frame, and a few kilometres at that speed is a fraction of a second. Nothing new is drawn but the zone's own warp effect, already prepared at load, laid on again while the speed holds because a transient ends itself. The motion blur is handed the run's own step (`setReprojectionCarry`), or the reprojection of the scene depth pushes every pixel off the screen and the picture is a grey wash instead of a sense of speed. The others on the relay are told to hide the ship (`j`, as a jump does), since ten places a second a kilometre apart is a teleport on their side. The one moment a program can be built on a live frame is the stop, where the streamer is freed and `World.readyAround` waits at the stopping point with the ship already still, which is why `__debug.cruise` counts `programsWhileSettling` apart from `programsWhileFast`, and only the second must be 0.
- The loading screen in space waits for every tier in range, measured from the player's world position (aboard a hull `player.pos` is hull-local), and a jump waits `World.readyAround` inside its closed tunnel (at least `TUNNEL_TIMES.min`, 4 s), which also links every program still queued; a jump to another system then waits for the new zone's reflections (at most `ENVIRONMENT_WAIT`, 5 s) and compiles the whole scene once more (`World.settleCarried`), since there is no loading screen's settle to do it and a reflective material compiled before its cube landed would otherwise rebuild on the frame the tunnel opens; otherwise a 2 km landmark streams in and compiles after the screen lifts. Arriving from the galaxy map, `travel` streams from the zone's arrival (`arrivalAt`), where `arriveInSpace` puts the ship, not from the zone's origin.
- Objects wider than the streamer's 600 m collider cap in a space zone (the Star Destroyer) are kept in a set of their own: their collision is built with their tier, not by distance (the pack's radius counts from the model's origin, not its middle), in pieces of at most 4,000 triangles (`splitTrimesh` in `src/world/trimeshPieces.ts`) through `cleanTrimesh` and `TRIMESH_FLAGS`, about 3 ms a frame, and `settle`/`readyAround` wait for the pieces (in a hidden tab, where no frame runs `update`, they build them as they poll). Measured on a 120k-triangle sheet with the flags, 8 pieces took 76 ms in all (worst piece 17 ms) and 52 pieces 68 ms in all (worst piece 2.1 ms). Only in space (`LayoutStreamer`'s `hugeColliders`): a planet's snapshot gives thousands of ordinary objects a radius of 1024 m or more, which is not their size.
- A hull the world has disposed has no Rapier body: on a removed body `numColliders()` throws `unreachable`, and a throw inside `Hyperspace.update` (which `step` calls near its top) skips the rest of every frame after it. `Hyperspace.abort` releases a hull only while `alive` (still in `world.vehicles`), a crossing that comes back empty releases the old hull if it is still there, and `Vehicle.setGhost` checks `body.isValid()` first. A ghosted hull's colliders are the only ones in no collision group (`setGhost` is the only thing that empties a collider's groups): the bolts' world ray skips every collider in no group with a filter predicate (`Bolts.passable`), which covers a hull in a jump and one still being prepared before it joins `world.vehicles` alike, and every target choice (the NPC brains, the auto-pick, Tab) goes through `targetable` in `src/space/shipCombat.ts` (alive and not ghosted); any other ray cast without a group filter still hits one.
- The interface's colours are eighteen names declared once on `:root` in `src/style.css`, between the `palette` markers, and read from there by both sides: the panels' `var(--…)` uses and `src/core/palette.ts`, which hands the same strings to the overlay canvas and the same four layer colours to the hull flash, so a bar, a pip and the flash on the model cannot drift apart (`palette.test.ts` fails if the two tables disagree by a name or a value). The overlay (`src/ui/hudCanvas.ts`) is a plain 2D canvas, the first child of `#ui`, that touches no WebGL context and so compiles nothing; it draws no text ever (canvas text costs a shaping pass a call and gives up the browser's subpixel rendering), allocates nothing in a frame (colours are indices into a frozen table and alpha is `globalAlpha`, so no `rgba()` string is built; a polygon is read out of the caller's own array), strokes everything twice — once in `void`, two pixels wider, which is what makes a hairline read over a noon dune and over a starfield — and clears only the union of what it drew last frame, which a resize must clear rather than merely forget unless the backing store was reallocated. Every size is one number in `src/ui/hudMath.ts`, which is pure and node-tested, and `hud.css` states a handful of them again, which `hudMath.test.ts` checks against the table the way `palette.test.ts` checks the colours. Each piece of the display counts its own DOM writes and `__debug.hud()` sums them as `writes`, which should be 0 in a steady frame; a single shared counter was tried and taken out, because a window that only rolls when it is read reports whatever time has passed as one second. Every colour a panel wears is one of the same eighteen, either directly or as `color-mix(in srgb, var(--x) N%, transparent)` at exactly the alpha the literal had; `hudPage.test.ts` reads `src/style.css` as text and fails if a colour is ever typed into a panel by hand, and the three deliberate literals (the travel curtain, which must reach black because it replaces the world rather than being drawn over it, and the two lit wells behind an item's picture and the creator, which are a light rather than a surface) each carry a comment saying why.
- Everything the game says once goes to the message line (`src/ui/messages.ts`), never to the prompt: the prompt is rebuilt and rewritten every frame from outside every guard in `main.ts`, so anything written to it by an event lived about seven milliseconds and was never seen. Twenty-eight sites used to write it; the crash line, the relay's connection and every notice the ultra cruise sends were among them. The line holds what it is told for eight seconds in a fixed pool of eight elements, merges a repeat within two seconds into a count, and writes `textContent` only when it differs — so it never parses HTML, and a line moved there from the prompt must have its `<b>` tags taken off (`plain()` does it). The long prompt line is what is left and is now behind a setting; its cost was never its words but its conditions, which ask the world for the lift underfoot, the elevators near, the doorless building near and the nearest vehicle every frame.
- The overlay canvas is the first child of `#ui` so that every panel draws over it, and neither it nor anything the display builds on the page carries a `z-index`: two positioned boxes in one stacking context paint in tree order, so the page paints over the canvas. A shape meant to be seen *on* an element of the page must therefore be drawn by the page. A number slot’s cooldown is one custom property on the cell (`--cool`) and a conic gradient in `hud.css`, written only when it has moved by a step of `HUD_TUNE.cooldownSteps`; drawn on the overlay it sat under a cell whose own background is `--plate` at 0.7 and contributed about a fifth of a near-black, which is to say nothing. Drawing it on the page also takes away the `getBoundingClientRect` measuring, the resize listener and the whole question of what happens when the browser moves the row. A second a cooldown is running in writes about fifty times, which is meant to; a *steady* second is still 0.
- Anything on the screen that shows a key must be told when one is rebound, and must read the key of the thing it stands for rather than its own place in a row. The note is `onBindingsChanged`/`notifyBindingsChanged` (`src/ui/hudPage.ts`, re-exported by `src/ui/menu.ts` so the design’s import path works), fired wherever a binding is written — the Controls page’s `assign`, its reset button, and `__debug.bind`/`__debug.resetBindings` — never in a frame, with each listener in a `try` so a display that cannot redraw its caps does not take the menu down with it. An ability cell takes `slot<n>` from the slot the ability is in (`KitSlot.key`), because both classes drop an empty loadout entry: counting the cells instead put the wrong key on every cell after the first hole. Caps are spelled by `keyLabel` in `src/ui/hud.ts` (`Ctrl`, `Shift`, `LMB`, `↑`), never by the Controls page’s `keyName` (`Left Ctrl`), which is a keyboard diagram and does not fit a 22 px cap; the action bar imports the same one, so a key is spelled the same in both places two centimetres apart.
- Our own marks are one file, `src/ui/hud.svg`: a `<symbol>` per glyph on a 24×24 box, each carrying its own `fill`, `stroke`, `stroke-width` and joins, because `<use>` clones the symbol’s subtree and whatever the file’s root says is left behind. It is fetched once at boot through `new URL('./hud.svg', import.meta.url)` — which the builder rewrites and which a node test never reaches for — and put in a hidden `#hud-icons`; a sheet that does not arrive costs the marks and nothing else, every cell keeping its key, its cost and its border. Which mark an ability wears is keyed on its name with everything but the letters taken out (`hudIcons.ts`), with word tests under it and a last-resort mark under those, so an ability added later still shows something. Every glyph stays inside 3 to 21 of its own box: one that ran to the edge touched its neighbour at 28 px. The name and health over what the crosshair rests on (`src/ui/nameplate.ts`) needs both `hp` and `maxHp` on the living thing — a body that keeps only `hp` shows a name and, silently, no bar, which cannot be told from a full one.
- What the screen offers you to press is gathered a few times a second into one kept struct (`App.gatherPrompt` into `newPromptState`, at `HUD_WIRING.promptHz`), never per frame, and both the short action bar and the long prompt line read that struct. The words were never the cost: the *conditions* were, and the long line asked the world on every frame for the lift underfoot, the elevators near (twice on one line, once to test and once to read), the doorless building near, the nearest vehicle — through three separate walks for "in reach", "has a room" and "on its back" — and the ship the boots could reach. The gather asks in the long line's order, not the bar's, so the lift underfoot is asked for while a bridge's controls are held; the bar's rules read the same struct in their own order. The bar is emptied on the frame the game stops simulating rather than at the next gather, as the overlay is, and the long line is written only on a frame that simulates, since half its branches read the struct and half read the player and with a panel up it would otherwise disagree with itself; a jump's own line goes over it either way. The two words the struct has no room for (the lift's level count, the doorless building's name) are kept beside it, and are put back when the world is left, as the struct's own reset does not reach them.
- A panel whose own `canOpen()` asks `anyPanelOpen()` must never be added to `anyPanelOpen()`: it would then read "something else has taken the screen" about itself and shut a quarter of a second after every press of its own key. The group's panel frees the mouse without joining that list and stands down when the pointer lock goes back to the game (a `pointerlockchange` listener, with its slow step as a backstop), so a click on the world gives the view back instead of leaving the player with no cursor and no walk. Escape out of a typed line is the same thing from the other side: the browser takes the lock back on that very press, so the line asks for it again and holds the game's keys aside for a moment afterwards, or the one press that closed the line also opens the menu. A loop that carries a marker over a head is armed only while there is a marker to carry and disarms itself when there is not — a group in which nobody is far enough off runs no frames at all.
- Where a blow on the player came from reaches the game by two different paths, and both have to carry it. Everything that strikes calls `damage(amount, from, push, source)` on the target, and `PlayerTarget` hands that on to the callback the frame loop sets; but a creature that is aggressive and *unprovoked* does not call `damage` at all — `Creature.update` calls the `onAttack` it was handed, which is `World.hurtPlayer`, which calls `playerTarget.hurt` directly. Anything reading the direction must be fed from both, or the commonest bite on a planet arrives with no side to it. So `onAttack` carries `from` the whole way down (`Creature.update`, `CreatureManager.update`, `World.update`, `World.hurtPlayer`) and `PlayerTarget.damage` hands it to its callback. `App` keeps one wrapper round `world.playerTarget.damage` as a second source, installed in its constructor — the record is one object for the life of the session — held for the length of the call in a `try`/`finally` so a direction cannot be left standing to be worn by the next blow that has none, and read by the frame loop’s damage closure as `from ?? this.hurtSource`. Every one of the nine places in `main.ts` that hurt the player goes through `App.hurtFrom`, which raises the red flash and, with a direction and within `HUD_WIRING.hurtRange`, the arc on that side; the direction is measured from `player.worldPos`, not `player.pos`, because aboard a ship's rooms `pos` is the hull's frame.
- The relay grew into a small server in place, and every part of it had to be added without breaking a browser built before it. The server sends `hail` the instant a socket opens (the clock, how long a day is, a nonce, whether a join word is wanted, whether damage between players is on); an old browser has no case for it and drops it silently, and `welcome` stays exactly where it always was, sent once in answer to the first hello — a browser that ran `case 'welcome'` twice would re-fire `onJoin` for every peer and re-fetch a rig, a look and a `prepare` for each of them mid-play. A browser that hears no hail within a second knows it is talking to the relay that came before and turns everything new off. Adding fields to `welcome` is safe; sending it twice is not.
- A claim can fail in two quite different ways and they must not be answered alike. A proof that does not match and a wrong join word are the end of the line: that browser is not who it says it is, asking again cannot change that, and it is sent `denied` and closed. A character that belongs to another player is the end of that **character** only: the browser is sent `refused`, keeps its line and can offer a different one. A character id can genuinely collide, because the maker falls back to a time plus six random characters on a page with no `crypto.randomUUID`, and closing the line over it would lock that player out of the server for good, on every reconnect, with nothing telling them why.
- The server's news goes only to the world a player is standing on, but a peer is taken apart only when their line actually closes. `join` is the expensive word — `RemotePlayers.remove` then `add` → `dress`, a rig fetch, the wearables and `World.prepareActor`, which is a shader compile on a live frame — and `hello` is the cheap one, which the browser already handles correctly when it says another planet: keep the peer, stop drawing them. So the server keeps a set per connection of the peers that browser holds, sends `hello` for anyone it holds and `join` only for a first meeting, never sends `leave` merely because someone travelled, and sends `leave` on a closing line to everyone who holds that peer wherever they are now standing. What is saved is the stranger on another planet, who is never mentioned at all; a friend hopping to another planet and straight back costs nothing, which is what the first cut of the routing got wrong.
- The world the server keeps is `world.json` plus `world.log` (a line of JSON per change with a sequence number, appended and `fsync`ed as it happens; the snapshot is written to a temp file, flushed, renamed over the real one, and only then is the log emptied). Three Windows facts decide its shape: `ftruncateSync` on a handle opened for appending throws `EPERM`, so the log is emptied by closing the handle, writing the file empty and opening it again; a rename over a file another program holds open throws `EPERM`/`EBUSY`, so it is tried a few times and then left to the next ordinary write with the log keeping everything; and a failed rename must schedule nothing of its own, or the server writes and fsyncs the whole world about fifteen times a second for as long as somebody has the file open in an editor. Every table keyed by something a browser chose is `Object.create(null)`, and is rebuilt that way when a file is read back, so `__proto__` is a key and not a way into the language's own objects; the wire refuses `__proto__`, `constructor` and `prototype` outright as the near half of the same belt.
- A server started with a join word listens to nothing but a claim until the browser has said who it is (`relay.mjs`), so the hello cannot go first: with a word set the browser waits for the hail, claims, and then says hello, and with no word it says hello at once exactly as it always did. A browser told its character was opened somewhere else must clear `wanted` as well as closing the socket, or the reconnect takes the character back and the two browsers kick each other for ever. The player's key is never sent: what a server keeps is a second hash of it (`server/identity.mjs`), and what answers the server's challenge is an HMAC of the nonce under that.
- A group is held by the server, and a member of it is a **character, not a connection**: the key is `c:<character id>` once a browser has claimed one and `s:<connection>` otherwise, which is what lets a reload keep its place. A line closing holds that place for ninety seconds — the group is told the member stepped out, the roster reads them away, the place still counts against the eight so a reload cannot be locked out of its own group, and the leader changes hands only when the hold runs out, to whoever has been in the group longest. The one closing that must not look like stepping out is a takeover: the same character opened in a second browser closes the older line, so `Groups.absent` ignores a line that is no longer the one holding the member and `present` takes the older line out the moment the newer one claims, or the whole group is told somebody went away who is standing right there. Turning an invitation down takes back that one invitation and no other — only somebody actually going takes the ones they sent with them, and whoever sent one is told, rather than being left reading that it is still out while the person they asked has already been dropped.
- The group's words and its distances are the game's, read out of `datatables/player/radial_menu.iff`: an invitation reaches 90 m (`GROUP_INVITE`), a trade 8 m, a duel 128 m and a death blow 10 m, and 16384 m is that table's mark for no limit rather than a distance, so an invitation to somebody on another world is refused for being on another world and never for being 16,384 metres away. `GROUP_RANGES` in `server/groups.mjs` and `GROUP_RANGE` in `src/net/groups.ts` each hold the rows and neither is tunable. Everything beside them is ours and is one object apiece — how many fit in a group, how long an invitation stands, how many one browser may have out, how long a place is held, how often it may ask its group for anything, how many lines of chat a second — printed by the status page and moved for a run with `--set group.<name>=<number>`. A chat line is sent back to the speaker by the server rather than shown where it was typed, so everyone reads the same words in the same order and what is shown is what the server let through; a distance is measured in the relay, which is the only part that knows where two players are standing, and the state a browser sent from a world it has since left is thrown away rather than measured against.
- A label over another player's head hangs on where their figure is being **drawn** this frame (`RemotePlayers.peerAnchor`), never on where their last message put them: the figure glides toward that point over the tenth of a second between messages, and one riding in somebody else's hull is placed from the carrier's own pose, so a label hung on the message's place swims off the head and snaps back ten times a second. The roster's distances and the invitation's 90 m read the message's own place, where that lag does not matter.

On foot that is two bars with a grey ghost behind each that walks down after a blow so the size of it shows, a row of square cells each with its own mark, the key you have bound and what it costs, a cell for each hand with what is in it and the game's own name for it, and a crosshair that draws tighter and brighter while you aim and fills a ring round itself while a shot charges; over whatever the crosshair rests on, that thing's name and health, in place of the corner's old "nearby". Along the bottom, at most four things you can press where you stand, each with your own key on it, gathered eight times a second rather than asked of the world every frame; the long line of every key is still there behind a setting, and now starts off. A blow on you draws a wide arc on the side it came from, one of yours that tells ticks the crosshair and ticks it red with a ring on a kill and says what it hurt in words, and small numbers over heads are behind a setting that starts off, since the game said its results in words. At a ship's controls the reticle carries three arcs -- the speed up the left with a tick for the top speed with the wings open and another for the plain top, the guns up the right on their own refire clock with a notch where one is down, and the booster across the bottom, absent on a hull that has none -- the ship's own shields, armour, hull and one pip per fitted part stand under the middle where the body's health bar was (which stands down while they are up, since a body cannot be hurt at the controls), and a target is four corners closing onto the hull itself with its name, range, side and the three layers of the face turned toward you, or an arrow at the edge of the screen pointing the way to turn when it is behind you. Everything the game says once -- the damage from a crash, the relay connecting, a refused dock, every notice a cruise or a jump sends -- goes to a message line at the bottom left that holds it long enough to read and fades it away, repeats bumping a count rather than filling the screen; before this it went to the prompt line, which is rewritten every frame and swallowed all of it. The shapes are drawn on a plain 2D canvas over the picture that touches no WebGL context and so compiles nothing, and every switch and number the display has is an **Interface** page in the Escape menu beside Graphics and Sound -- the scale, the sharper canvas, what is shown while flying, the message line and how many lines it keeps, that long line, and four for a fight -- with a button that puts the lot back; `__debug.hud()` reports what the overlay costs and how many DOM writes a steady second took, which should be none. Every panel in the game now takes its colours from the same eighteen names.

Every creature, droid and NPC the game shipped (`mobiles`) can be stood from the spawner's NPC tab, searchable and grouped: creatures on their own models, people on parts bodies, and dressed NPCs in their own clothes and colours, armed off the rack, their lightsabers lighting what is around them. The planet's own wildlife comes from the catalogue when it has the species. They fight, flee and follow you through doors. Not done: dressed and parts bodies share nothing between entries (each look loads its own body textures; the design's optional part cache), and the fighters (`npcs.ts`) still think with their own temper, not the mobiles' brain (the design's stage 6 left them as they were).

NPC starships fly the garage's own hulls with their tier chassis's fits, in the game's formations (arrow, claw, wall): patrols keep to a space zone's stations, hyperspace points and arrival lane (woken within 3 km, put away past 6 km unless fighting, back 150 s after one is wiped out), and the NPC tab's starship groups stand one of a family at a tier, or a patrol of three, 700 m ahead. They dogfight by side (Imperial, Rebel, Black Sun, pirates: `factions.ts`), attack the player's ship on sight or leave it alone by side, turn on whoever hurt them (the player on foot too, with a quarter of the damage), taunt in the game's own lines, hold still while a panel is open, and fight through shields, armour, components and chassis with the game's own hit, target and explosion effects; the flight display colours the target's bracket by side and shows the flown ship's shields, armour, hull and a pip per part, and a part knocked down says so in words on the message line. Every stat, the tier pick, the pilots (a hand on the stick that caps and slows the turn by tier, and their aim) and the rosters are invented and kept in `shipStats.ts`, `loadout.ts`, `npcBrain.ts` and `roster.ts`. Not done: missiles, countermeasures and turrets (guns only), the hit effects' light and camera shake, the 105 tiered types with no garage hull, NPC ships across the relay (each player sees their own).

The relay is now a small server as well, and the two are one program: `npm run relay` still starts it, a browser built before it still plays against it unchanged, and a browser built for it that finds an older relay at the other end says so and turns everything new off. What it holds is **one clock** — the world's wall time and how long a day is, handed out in its first word and sharpened by a round trip every ten seconds, which the time of day and the weather schedule both read, so two people on one planet are no longer at noon and at dusk at once — and **who each player is**: a key the browser makes for itself with `crypto.getRandomValues` and never sends, a public name that is a hash of it, and the characters that player owns, all written to `server/data/world.json` with a log beside it so a machine that loses power loses nothing. The same character opened in a second browser goes to the newer one and the older stops asking for it back; a character played with no server and then brought to one is settled by a change counter, the higher winning, with the question put to the player on a true tie. News goes only to the world a player is standing on, and a peer is taken apart on the other side only when their line actually closes. A join word on the address (`--word=`) keeps a stranger who guesses the port out, and damage between players is a switch on the server (`--friendly-fire`) that starts off and that nothing reads yet. **With no server address set none of this runs at all and the game is exactly what it was**, which the day's own test pins to the last bit. Everything about it is invented except the day's 720 seconds, which is the game's: the protocol, how a player is named, the rates, the caps, the patiences and where each planet sits in the shared day. The server's own numbers are one `TUNING` object it prints back on `http://localhost:8787/` and moves for a run with `--set <name>=<number>`; the browser's are `__debug.session()` and `__debug.day()` (`__sharedDay()` is the same knob on the window). It holds **groups** as well: up to eight, asked in within the game's own 90 m, accepted or declined on a countdown, left, handed on, put out of and broken up, with the leader alone able to ask people in, remove them, hand the group on or offer it a trip. A member is keyed by their character rather than their line, so a reload keeps its place for a minute and a half and the group hears only that they stepped out and came back. The roster is its own light message that never reaches `RemotePlayers`, so a member on another planet costs this browser no rig, no clothes, no compile and no ship: it stands down the side of the screen, is marked on the planet's map and on the space map, and a member past forty metres gets a chevron with their name over their head. And there is a **chat line**: Enter opens it, plain words go to everyone on your world and `/g` to your group, every line comes back from the server so that everybody reads the same words in the same order, and what anybody says floats over their head for a few seconds and stands in the message line. A player standing in a hull somebody else flies now names that hull rather than sending a copy of it — the fix for two crew drawing two hulls on everybody else's screen — although nothing answers that question in play until another player's hull is a place you can stand in. And it carries **the fight**: every player on your world has a body where they stand and a box round the hull they ride, both sensors in a collision group of their own that collides with nothing, so a bolt, a blade and a sweep stop on them while the steps you take, a ship looking for somewhere to set down, the roof over the rain and the ground under a speeder all pass over them; a shot crosses as an explicit message and is flown again on every other browser as a picture that hurts nothing and is cut short where the one who fired says it landed; the shooter's screen decides the hit, the one who was hit is the only place health is ever taken off, their health comes back at five looks a second and only when it has moved (which is what fills the roster's bars), and the one who died announces it with whoever struck the last blow; a blade turning one of those bolts away is a word rather than a second bolt; a peer's lightsaber is drawn, lit in the colour they chose, heard, thrown, and lights what is round it; and damage between players is the server's `--friendly-fire` switch, off unless it is asked for, with the game's own duel and peace inside it. ## How to work with the owner

Give them exact commands to run and exactly what to look for, one list, every item independent of the others so they can do it all in one session. When something cannot be judged from here, ask for the one observation that separates the causes rather than guessing twice. Converter changes need a reconversion (`npm run swg -- ships @SWG assets-private --retail-only` for ships; the README's table for the rest); say so every time, and say when a change needs none.
