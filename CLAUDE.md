# swg3js: what this is and how we work on it

Read this first. It is the handoff from the sessions that built the game so far, written so a new session can carry on without the old chat.

## What we are building

A just-for-fun recreation of Star Wars Galaxies (the 2003 MMO) that runs in a browser: Three.js for rendering, Rapier for physics, Vite and TypeScript, no framework. The owner has a legal SWG install (the SWG Legends client, which contains the original SOE archives) and Jedi Academy; everything the game shows is converted from those installs on the owner's own machine into `assets-private/`, which is git-ignored. The game code is public; the assets never are.

The owner plays it on Windows, in Chrome, and tests by hand. They report what they see in words ("the cockpit is a metre too high"), paste console output, and run converter commands you give them. They cannot see your tool calls, so every reply has to stand on its own and say exactly what to run and what to look for.

## Hard rules

- Never commit, copy into the repo, or publish anything from `assets-private/`, any `.tre` archive, or anything derived from the game's files. Diagnostic output pasted into chat is fine; files are not.
- The converter must work with `--retail-only`, which mounts only the SOE-origin archives. Emulator and mod content stays out. See `docs/ASSETS.md`.
- Never put a model name or model identifier in a commit message, PR text, or code comment.
- Commit messages: a one-line summary in plain words (what changed for the player or the converter), then a short paragraph of why, no bullet lists, no file lists. Attribution trailers are whatever the current tool adds; do not invent them.
- Do not create pull requests unless asked.
- Development happens on `claude/gun-combat`. After every commit, push the branch and fast-forward `main`:
  `git push -u origin claude/gun-combat && git checkout main && git merge --ff-only claude/gun-combat && git push origin main && git checkout claude/gun-combat`
- Before pushing: `npx tsc --noEmit -p .` and `npx vite build` must be clean. `node --check` any converter module you touched. The converter tests are plain node scripts (`npm run test:converter`), not vitest suites.

## Setup on a new machine

Node 22.18 or newer, `npm install`. Copy `.env.example` to `.env` and fill in:

```
SWG=<folder holding the client's .tre archives>
JKA=<Jedi Academy's GameData folder>
```

The converter replaces `@SWG` and `@JKA` on its command line with those. Then follow "Converting your own SWG install" in `README.md` (the whole list, in order, every command with `--retail-only`), and `npm run dev`. `npm run swg -- status assets-private` says what is in place and prints the command for anything missing.

`.claude/launch.json` starts the Vite dev server for the Claude Code extension.

## How the pieces fit

- `tools/swg/cli.mjs` is the converter, one `case` per command; `tools/swg/README.md` documents every command. It reads the client's IFF-based formats (`iff.mjs`, `msh.mjs`, `appearance.mjs`, `pob.mjs`, `sht.mjs`, `dds.mjs`, `objtemplate.mjs`, `datatable.mjs`, `shipdata.mjs`), writes GLB (`glb.mjs`) plus a `manifest.json` per pack. Diagnostics that exist and are worth knowing: `list`, `dump --strings` (prints every readable string per chunk, the way to learn a file layout), `template` (an object template's parameter chain), `materials --ship=<id>` (every shader a hull uses with what the converter made of it, and its hardpoints), `shader`, `pob`.
- `src/main.ts` is the app: the game loop, input dispatch, mounting and boarding, the camera choice, the `__debug` object on `window` (every helper is documented in the README's Debugging section).
- `src/world/` streams the planet: terrain from the game's own terrain rules, placed objects, portal buildings with cells drawn through a stencil portal renderer (`portalRender.ts`), a compile queue that pre-compiles shaders so nothing stalls on first draw, cascaded shadow maps.
- `src/player/` is the character: a parts-based skinned rig, the Jedi Academy movement and saber port, the blaster carries, and the "aboard" mode (see ships).
- `src/vehicles/` is the garage (`garage.ts` reads the manifests and spawns), the vehicle physics (`vehicle.ts`), ship interiors (`interior.ts`), engine trails (`trail.ts`).
- `src/net/` and `server/relay.mjs`: a dependency-free WebSocket relay that passes player states around; other players are drawn as their own characters.

## Things that took a long time to learn (do not relearn them)

- GLTFLoader strips `:` from node names and keeps the original in `userData.name`. The converter names hardpoints `hp:<name>` and cells `cell:<index>:<name>`; read them through `hardpointName()` in `garage.ts` and `cellIndexOf()` in `interior.ts`, never by matching `o.name` for a colon.
- A ship's hardpoints live in its `.lod` appearance, not its mesh, and the appearance chain (`.apt`, `.lod`, `.cmp`) carries them through `resolveParts` onto the first part. A single-mesh ship must keep its chain when the chain has hardpoints.
- Rapier scene queries see nothing until the world has stepped once. A ray cast into a freshly built world misses everything.
- Rapier's character controller with "apply impulses to dynamic bodies" panics on a trimesh collider. The push is off (`Player.pushBodies`), and every trimesh goes through `cleanTrimesh()` with `TRIMESH_FLAGS`.
- Changing the number of lights in the scene recompiles every shader (a second each on the owner's machine). Lights are pooled and never added or removed at runtime: `effects.flash` is a pool of point lights that everything borrows, including a ship's room lights.
- Materials with `transparent` true and any opacity still cast full shadows; glass meshes get `castShadow = false`. The converter marks glass-named shaders with `userData.glass`; the game never blends them (the client did not either), it swaps in a clear copy of the material while someone is in the ship.
- The game's rooms in a portal building are often larger than the hull around them and are only meant to be seen through portals. The window openings are "invisible collidable" meshes: colliders only, never drawn, never casting.
- A cockpit frame (`cockpit/<ship>.iff`, FORM CPIT > 0000: FRAM the appearance, ZOOM the camera distances, FRST the first step out, 3OFF the chase offset, 1OFF the first-person offset) is authored in the ship's own space: hang it on the model at its origin and it lands in the canopy. Every frame carries one hardpoint, `camera`, pointing down the nose: that point plus 1OFF (X mirrored) is the first-person eye hovering and flying (`Vehicle.cockpitEye`). The game never drew a pilot. The body hangs under the eye by where the seated clip's first frame puts the eye joints and the pelvis (`rig.seatedPoints`; space_sitting: eyes 0.708 m over the pelvis and 0.109 ahead; skeletons without eye joints, the rodian, mon calamari and ithorian, use the head plus 0.07 up and 0.09 ahead), scaled by the figure's height. It is then moved up or down so the pelvis sits 0.10 m over the cushion that one downward ray through the frame's triangles finds at spawn (`seatDropBelow`, `bodyLift`), but in first person never more than 0.10 m up: the TIE frames' camera is 0.25 m lower than a seated pilot's eyes, and rising further puts the camera in the collar. The eyes are measured from the clip's first frame, never the live bones: the idle's fidget moves them 0.04 m.
- A hardpoint the gun patterns take is never a seat or an eye (`isSeatHardpoint`, `isEyeHardpoint` in `cockpitSeat.ts`): the gunboats' `pilotmuzzle1` is a gun. The ships without a frame are all room ships flown from their bridge, whose first-person eye is the pilot's own; seated in one (no pilot spot), the rider is not drawn. Only the ships pack's ships sit by the eye (`Vehicle.eyeSeat`); anything spawned "as a ship" keeps its own seat.
- Seated in a ship and zoomed all the way in, the view is locked to the hull hovering as in flight (`ThirdPersonCamera.cockpit`, then `chase`, both at `pos + q * eye`, so lift-off never moves it). Hovering, the mouse's sideways movement moves a heading target at most 0.6 rad ahead of the hull (`cockpitYawStep`), which also steers a bridge pilot hovering: aboard, the camera's yaw is in the hull's frame and must never be handed to `drive.heading`. Alt looks round from the eye itself (`update`'s `eyeAhead` 0), starting at the nose. A rider's spine takes no torso twist while mounted, and the on-foot twist is cleared on mount.
- Ship attachments are templates under `object/tangible/ship/attachment/`; the stock ones come from the per-hull `datatables/space/ship_chassis_<chassis>.iff` (each slot's stock component's look, `pickStock`, which on every retail hull is the column's most common `attachment:hardpoint` cell; a `modification_*` slot, whose one filled row is a reward look, has no stock part), never by name (the Jedi starfighter's parts are `jedifighter_*`, and a name search hung every X-wing gun twice). A client data file's version form also carries chunks beside its forms: HOBJ (appearance, hardpoint), IHOB (appearance, hardpoint, three floats that are non-zero only on turret barrels), CHL2 (an object template, then 17 floats, the first three its place in the parent) and CHLD (the same with an appearance): the Black Sun wing structures, the Hutt wings, turret bodies and barrels, radar dishes. A hardpoint a part's client data names is looked for on that part, then on what already hangs under it (a turret's barrels are on its body), then on the whole ship (an engine's ONOF names the hull's `engine_on1`). `yt1300_engine_none` is the empty engine slot's stand-in, the same mesh as the engine: written with `standInFor` and not hung while a component fills the slot. The ships command writes the tree (`tools/swg/shipparts.mjs`: `parent`, `hardpoint`, `place`, `turn`; `owner` on what a stock part's own client data produced; `chassis` on every ship, which is how status tells an old one; manifest `assembly: 2`); a def with no `parent` is hung by name anywhere on the ship, as before. `expandPart` (one part's own subtree, for a part swapped in) writes by name what the part does not carry itself (the Y-wing engine's "on" appearance on the hull's `engine1`, the V-wing engine's glow on the hull's `wing1`), so a part's `children` must be hung after the ship's other parts, over the whole ship, not under the part alone.
- A player hull's components are three tables: `datatables/space/ship_chassis.iff`, a row per chassis (`player_<ship>`) whose slot cells are comma lists of compatibility classes (an empty cell: no such slot); `ship_components.iff`, each component's templates, type and one class (seventeen names end in `.iff`); and `ship_chassis_<chassis>.iff`, a row per component that shows anything on that hull, each slot column's cell `attachment:hardpoint` pairs (an empty hardpoint is the hull's origin). The per-hull table is looser than the chassis both ways: a slot offers only what its classes accept, and a looks column the chassis row gives no class is a fixed part (the Star Destroyer's 92 turret bases); `buildSlots` in `shipfit.mjs` applies both. The chassis name is the template's file name without `shared_` (`chassisNameFor`: a decorated YT-1300 uses `player_yt1300`, the Corellian corvette `player_corvette`). The stock part is the modal look's best-ranked component (`pickStock`), and a `modification_*` slot has no stock part: it starts empty (`STOCK_LEFT_OUT`). The modal look over the components a slot accepts is the column's most common cell on every retail hull, so the stock parts hung and their order (the looks table's columns, `stockPairs`) did not change when the stock rule did.
- A component's name is `space/space_item:<name>_n` for most, the shared template's `objectName` for about two hundred more (the crafted ones are in `space_crafting_n`, and an unset string id must not stop the search up the template chain: `setStringId`), and nothing at all for about fifty (the collection rewards, the capital ships' turrets), which get one made from the key (`fallbackLabel`).
- The flight computers are `object/intangible/ship/shared_navicomputer_1..6.iff` ("v1 Flight Computer"); the astromechs are the pet templates in `datatables/space_command/programmable_droids.iff`, the crafted and plain ones sharing an appearance, drawn as the mobiles pack's `astromech_rN.glb` (R2-D2 has no model there and is left out). The eight hulls with `hp:astromech` take a droid there; `ship_droid_appearance_override.iff` (ship, ground appearance, space appearance) swaps in the N-1's head, which the ships command converts. Status asks for the ships again when the astromechs arrive after them.
- Ship paint is FORM CSHD: TXTR's TX1D operations pick a pattern's MAIN and HUEB textures together (`index_texture_1`), and TFAC's PAL operations set MAIN's and HUEB's colour factors from 64-colour palettes (`index_color_1`, `index_color_2`); all three are non-private, so one value per ship covers the hull, the wings, the carriers (the Black Sun wing structures, the Hutt wings) and the parts. The colours are passes two and three of the effect, so a first-pass check (`shaderNeedsBake`) misses them: the ships command bakes every pass at the shader's defaults (`paintedMain` in `cli.mjs`, through `surfaceTexture`'s `mainImage`, whose colour replaces the main's before the glow split, so the glow is split from the painted colour; its alpha, the gloss and a MAIN glow's mask, stays the chosen pattern's, since the bake's alpha is the first pass's and opaque: `withPatternAlpha`), and names the image `<pattern>#paint:<shader>`, since two paint shaders on one pattern differ by their colours. A hologram palette is not paint. A recipe's `glow` is written only when the converted material glows: seven emismap paint shaders have masks too faint to split, and a glow put on a material with no emissive map would need a new program.
- A WING form's DATA is the wing template, a float open angle in degrees, a float seconds to open, then the sound; then either PSOR (x, y, z and three angles in degrees) or HARD (a hardpoint of the part whose client data lists it). Either is where the wing object stands and its hinge: its mesh is modelled about that frame and turns about its own Z. The X-wing's PSOR is all zeros, which is why reading it as a hinge in the hull's frame looked right there and nowhere else; the ARC-170's and Jedi starfighter's PSOR places are exactly the hulls' wing1..4 hardpoints. An earlier try at placing wings failed only because it did not mirror X. The middle angle is never used and no wing uses two, so their order cannot matter; which axis each turns about is taken as yaw (Y), pitch, roll (Z): the V-wing is the only yaw, the B-wing the only roll (its body is a collar round the pod, which only a turn about Z keeps on it), each one constant in `shipAssembly.ts`. A wing's own client data can hold wings: the B-wing body's two foils hang on its `wing_l1`/`wing_r1` with HARD.
- Ship bolts come from `datatables/projectile/projectile.iff` (index to the bolt's `.prt`, its fire `.cef` and its hit `.cef` per surface; a `.cef` names a `.prt` and a `.snd`) and `datatables/space/ship_weapon_components.iff` (weapon name to projectile index, speed, range). Space bolts are 600 m/s, 512 m, drawn 19 m long ahead of the projectile point in local-space emitters, which `particles.ts` honours; passing effects are placed `transient`.
- A bolt is a thing in flight with a velocity: it carries the shooter's velocity (`inherit`) and its ray leads by its visual reach, so a fast ship's bolts never lag it and a long streak does not poke through what it hits.
- Every ship attachment hangs under the node it names (its parent's hardpoint, or its parent's origin at its place), a wing under a pivot turned about its own Z, so what rides a wing follows it with nothing copied: guns keep their muzzle node and are read at the shot (`Vehicle.muzzle`), glows are sprites under their hardpoints (made, with their trails, before the ship is prepared, so they are compiled with it) and trails follow the sprites. Each wing opens on its own clock (one shared counter opened four wings four times too fast). The hull colliders under a pivot are moved with it (`setTranslationWrtParent`, `setRotationWrtParent`) while it moves, and the mass sits on a piece that never moves. Hardpoints on parts never set the seat or the cockpit eye (a turret body's `turretcamera1` would). A ship is centred across on the meshes that do not ride a wing and along on the whole box (`frameExtents`): framed on its closed box, the B-wing turned about a point 7 m out along its flat wing, and centred along on its hull alone, the X-wing's turn point moved 0.77 m forward (its foils' engines reach behind the fuselage). A vehicle is prepared (`World.vehiclePrepare`: material schemes, textures, then a compile a drawable at a time) before `new Vehicle`; `World.breath` is the yield between steps (a MessageChannel when the tab is hidden), and a hidden tab compiles with `compile`, not `compileAsync`, whose link poll is a chained timer a hidden tab holds to one a minute. A travel during that wait is caught by the Terrain changing (`spawnVehicle`), and the vehicle is disposed rather than left in the next world.
- A ship converted with its fit (`fit` in its manifest entry, resolved against `components.json` by `shipFit.ts`; a pack without `components.json` is built as its stock tree) hangs its components from the fit, never from `attachments`: the garage's `assemble` drops every `kind: 'component'` def, every def with `owner` (what a stock component's own client data produced) and the stand-in of a slot the fit fills, and a def whose parent was dropped is hung by name after the fit's parts (`fitTree` in `shipMounts.ts`, tested on the X-wing's and the YT-1300's trees). The fit's parts go through `hangParts` (`shipMounts.ts`): by hardpoint name, the hull's own first, then anywhere on the ship, in repeated passes, never at the origin; each part's `children` whose chain ends at the part are hung on it with `hangAttachments`, and the ones with no `parent` (the Y-wing engine's "on" appearance on the hull's `engine1`) are pending parts marked `byName`, which `hangParts` hangs over the whole ship in a second round once every fitted part is on, never with `hangAttachments(part, …)`, which only looks on the part. `ShipBuild.fitParts` keeps each slot's top nodes (`''` for the ship's own by-name nodes), so a refit takes a slot down and re-hangs whatever rode it; `ShipBuild.standIns` keeps each empty-slot stand-in (the YT-1300's `yt1300_engine_none`), which every swap decides again (`settleStandIns`: down when a part of its slot hangs, up again when none does).
- Ship paint renders take 50 to 800 ms each, so they run in `paintWorker.ts` through the customizer's `renderOff` hook, never on the main thread. A ship wears the GLB's own materials until it is first given custom paint; then it gets its own copies (`ShipPaint`), prepared on stand-in meshes and compiled (the program is found, not built) before they go on, and a repaint swaps `map`, and on a glowing paint shader `emissiveMap` as well, between textures on the same channel (the glow is split from the painted colour in the worker, `glowSplit.ts`, byte for byte the converter's split, with the mask from the texture the pattern chose; a glow map is never added to a copy that has none). The copies leave the world's material sets through the paint's `forget` (`World.forgetMaterials`) when the ship goes or returns to stock. A render that lands after the paint changed course is dropped by a generation check made in the same step the texture would go on (`Customizer.accept`).
- A refit (`Garage.refit`, `World.refitVehicle`) stages the new parts, with spare glow sprites and trails for any engine spots the new look can bring (a part's, or the hull's thrusters when a slot is emptied) and any stand-in the slots may need, in a detached group, prepares them in their own materials (what a part wears whenever the paint is or goes back to stock: prepared only in the copies, a part would compile on a live frame when the paint went back), then lets the paint track them (which puts the ship's copies on while it is custom) and prepares again if that changed any material, and waits for their paint (`stageRefit`). One vehicle's refits run one after another (`inTurn` in `World.refitVehicle`), each staged from the fit the last one left, since two staged from the same fit leave the model and `v.fit` disagreeing. Then in one synchronous step (`refitSwap`) it moves every glow sprite to the vehicle's group, takes the old parts down and re-hangs what rode them, hangs the new ones, measures the guns and engine spots again with the wings closed (`collectMounts`, in the group's frame) and re-hangs the glows (`rebindGlows`: surplus sprites parked, hidden, under the group, their trails aged out; `v.engines` and `v.trails` rebuilt in place, so the heat shimmer follows). Colliders, bounds, seat and cockpit are not rebuilt. A fitted ship's gun fires its own slot's component (`gunWeapon`); a gun whose slot fires nothing is left out. Vehicles are prepared with `World.prepareVehicle`, not `prepareActor`, which would make glass, panes and cockpit frames cast shadows. `__debug.refit` and `__debug.paint` report `compiledOnSwap`, which must be 0.
- The ship edit page's preview (`shipPreview.ts`) has a WebGL context of its own, made the first time the page opens, stopped while it is shut, and made again on a fresh canvas after three ships (only a lost context frees the textures it uploaded; a texture's `dispose()` would free the world renderer's copy too, so it never disposes a geometry or a garage material). It compiles a drawable at a time with a breath between, visible drawables only, synchronously in a hidden tab, as `World.compileReady` does. Compiling a garage material the world set up for its cascades in a second context would take CSM's one shader record per material from the world's program (the cascades' uniforms would then move only in the preview's), so each compile is wrapped in `World.keepShadowRecords`. `__debug.refit` and `__debug.paint` count as `compiledOnSwap` only programs made for the ship's own materials, since a gun change also warms its new bolt's effects on the same frames.
- Wings open whenever a ship flies with room under them, and a chassis's `wing_open_speed_factor` (0.95 on the X-wing, advanced X-wing, B-wing and V-wing, 1 elsewhere) is taken as its top speed's share while they are open (with W up too: a cruise between the open top and the closed one eases down at the brake; only a boost's coast stays above it, as it always did); the client's own use of it is not in the archives, and the other reading (open only under that share of top speed) is `WING_RULE` in `wings.ts`, flipped live by `__debug.wings('threshold')`. In this game that reading would keep the wings shut in ordinary flight: holding W pins the cruise at top and it stays there. On a planet a wing that swings below the belly waits for that much air plus half a metre, with a metre's band (the B-wing's 15 m), and the ground easing and the slow-flight hold measure the wing as it hangs (`wingBelow`) while the crash stays on the belly.
- Normal maps are Direct3D's (green down); the converter writes them as they are and the game uses `normalScale (1, -1)`.
- An animation table's string selector (SSAT) keeps its value list in a chunk tagged `VAL ` (three letters and a space), not `VALS`: an i16 count, then each value's name and the i16 index of the branch it picks; several values share a branch. The converter names branches for their first value (`loop_riding:vehicle_speeder_bike`, `skill_action_5:dance_18`), the default branch plain, and writes every branch's values to the manifest as `variants`; `rig.variant(base, value)` resolves them in the game.
- A mobile's animations are shared: every appearance with the same skeletons and animation table plays one pack (`mobiles/anims/<pack>.glb`), so a clip is baked once for the hundreds of templates that use it, and the pack's JSON names the clip for each role rather than the game guessing by name. The tables nest their selectors (a mount's branch outside a mood's), and the shipped flattener loses the inner one, so `mobiles` has its own path-keeping flattener and picks the wild, calm, unridden branch: a bantha walks at 0.86 and runs at 3.47 m/s, not the ridden 6.93. Packs are compacted on the way out (no track for a joint that never leaves its bind pose, two keys for one that holds still), which is about half the bytes, and a one-frame pose is written twice a frame apart because three finishes a zero-length clip on its first update and poses a repeating one at NaN.
- How a rider sits comes from three mount tables (`datatables/mount/`): logical_saddle_name_map (a `.sat`, listed as its `_hue` variant, to a logical saddle), saddle_appearance_map (to the saddle's appearance), rider_pose_map (appearance and seat to the pose). The pose is the rider_pose selector's value; the hover chair is not in the tables, so unknown vehicles are tried as `vehicle_<id>`. A rideable vehicle's `pv_*.sat` is a placeholder whose body is the static appearance of the same name; the pose still keys on the `.sat`.
- A skinned mesh's hardpoints are `SKMG > <version form, 0004> > FORM HPTS > STAT` (and `DYN `, with a trailing space): an i16 count, then per hardpoint its name, its parent joint's name, a quaternion (w, x, y, z) and a position, in that joint's frame; every one in the retail archives parses to the byte this way. The `creatures` command writes them as `hp:<name>` nodes under their joints, mirrored exactly as the joints are (q to (w, x, -y, -z), x to -x). The mounts the game really let players ride (`datatables/mount/valid_scale_range.iff`) are exactly those whose mesh carries a `saddle` hardpoint; for the bantha, kaadu, bol and rancor only the `_hue` appearance the mount tables list carries it (the plain one has identical geometry and none), so it is read from there when both share a skeleton. The other creatures in the saddle map have no hardpoint and get a saddle on the back as measured posed.
- Every retail saddle (`appearance/mnt_saddle_*.apt`) has one hardpoint, `player`, at (0.0002, 0.164, -0.060), and the saddle poses' clip root (`loop_riding:saddle_*` and the plain `loop_riding`) is (0, 0.165, -0.057): the game stands the rider at the saddle's origin and the clip lifts the pelvis to `player`, as with the speeder bike. The seat hangs on the saddle's `player` node with `seatPelvis`, so the pelvis lands there whatever riding clip plays, and the seat is `add`ed (not `attach`ed) under the creature's `hp:saddle`, so the saddle and rider ride the joint in its own frame and the rest pose never matters (the bantha's saddle moves 1.5 m between its rest pose and its idle). Nothing in `Garage.finishSpawn` may be awaited after `new Vehicle`: the body is live, falling and unsprung until the world adds it, so the saddle model is loaded beside the creature's before it.
- A rideable vehicle's `pv_*.sat` is a placeholder only when its animation table is the shared `monstrosity.lat`; the walkers (AT-ST, AT-XT) and the basilisk carry their own table and mesh and walk with them. The game's own rider poses are what they are: the AT-ST seats its pilot as the hover chair does, the AT-XT as a pod racer.
- Three applies tone mapping only to the default framebuffer: with a render target bound the materials come out linear, so post-processing must end in an OutputPass, and toggling it recompiles every program (the tone mapping is in the program key). World warm-up binds `world.compileTarget()` (the effects' scene target) around every compile, so the programs built behind the loading screen are the ones drawn; switching Effects compiles the other variants in the background (`reconcileEffects`) and changes over when they are linked. Three's own output pass works its tone-mapping defines out on its first draw, so it is given one throw-away draw before the warm-up compiles it, or the program built there is one no frame ever uses. Every effect's settings, knobs, pass order, products and budgets live in `src/core/fxRegistry.ts`; `npm run test:fx` checks them.
- The game seats a rider at the vehicle's authored origin and the riding clip's root offset puts the pelvis in the seat: a speeder bike's `player` hardpoint is exactly its clip's root (0, 1.16, -0.04), so the rider must not be placed at the hardpoint as well. The garage recentres a model on its box, so the authored origin is `model.position` afterwards. A seat on a saddle's `player` point or on a creature's own `player` hardpoint names the pelvis instead and takes the clip's root off (`seatPelvis`); a pod racer's guessed cockpit (`podSeat`) names the pelvis and takes the root off itself; a ship's pilot is placed by the eye instead (`Vehicle.eyeSeat`, the cockpit-frame lesson), and a wild creature's bare back names neither; `__debug.seat(dx, dy, dz)` nudges a seat live and prints the pose's root.
- The scene draws into `postfx.sceneTarget`, which no effect writes into; the chain ping-pongs between two buffers with no depth. A pass may sample the scene's depth texture only while a target without that texture is bound: Chrome drops the draw otherwise (INVALID_OPERATION, and silently once its error cap is hit), which is why the god rays and the speed blur never drew before. Geometry products (heat, water mask, velocity) attach the same depth texture read-only, so they never sample it; a target sharing it must be the scene target's size, and is detached before being disposed on its own, since disposing a target disposes its depth texture. `__debug.fxCheck()` names a step that errors.
- A vehicle's hull colliders leave out the terrain group (`HULL_GROUPS`): the springs hold the vehicle off the ground from their rays, and hull-versus-heightfield contact made every slope snag and jolt.
- A flying hull is driven by setting its velocity every step, so a contact the solver resolves is overridden the next step and the hull wedges into whatever it hit: `flyShip` compares the velocity it commanded with what the step left (`commanded`), takes a big loss as a hit, and then leaves the body to the contacts for a few tenths of a second. - The motion blur merges two velocities per pixel. For everything still, the camera's reprojection of the scene depth, with a cut (25 to 60 m) pushed out past the far side of whatever the camera follows (`ctx.followFar`, from `App.followFar`), so the ship flown stays sharp at any size; last frame's view is taken with this frame's projection, so aiming's zoom is not motion. - The colour grade (`src/core/fx/gradeMath.ts`, pass `colorGrade`) runs in linear HDR just before the OutputPass. Every tint keeps the pixel's luminance, and its contrast turns about 0.18 divided by the exposure and leaves anything below a thirty-second of that and above thirty-two times it untouched, so it cannot crush shadows or clip highlights; a raise in saturation is scaled by how grey the pixel already is, so strong colours never clip. A planet's mood (gloom, heat, warmth) is hand-set in `GRADE_LOOKS`, not read from the sky: a planet's environment blocks differ region by region (one planet's keys run from dim to bright), so a mood read from whichever block is in use is an accident of block order. - Mustafar's lava is terrain water: a table is lava when its water type is 1, when water.json's entry says `kind: 'lava'`, or, with no entry, when its shader names lava (`isLavaWater`; all 102 of Mustafar's). - Water writes no depth, so its reflections come from a mask: every body's twin (the same shader compiled with `WATER_FX_MASK`, in `WaterBodies.maskScene`) is drawn into three targets sharing the scene depth: normal, view depth and coverage (the occlusion reads that alpha); the environment term the lit water leaves out, weighted by its blend and fog; the weight a traced colour gets. - The swelling sea is double-sided, transparent and writes no depth, so at low angles one pixel blends several layers of it (a crest's front, its back, the next crest). A mask that keeps one surface a pixel holds one layer's environment term and the picture darkens at the crests with the pass on; the mask's second and third targets are therefore blended exactly as the lit water is (`src + dst (1 - a)`), and the first writes alpha 1 so it is simply replaced (it keeps the last surface drawn, not always the nearest). The half-resolution depth samples half texel i at full texel 2i + 1 (its centre at 2i + 1.5), so everything upsampling from it places a half texel there.
- The heat haze is the client's 2d_heat_composite: sources draw into a half-resolution RGBA16F buffer as (r, noise × r, noise × r) with additive blending, so overlaps average; the composite moves the UV by (noise − 0.5) × r × 0.01 × strength only where the landing pixel is hot, and not onto or from anything nearer than the farthest depth in the pixel's bilinear footprint. Sources sit in `HeatSources` (lava from World, plumes from providers that push numbers and a phase they integrate themselves; one provider that throws loses only its own plumes) and draw on layer 30 in the heat product's own scene, depth-tested by texel against `linearDepthHalf`. `gather` runs only inside `PostFX.end`; console helpers read stats. The client's noise volume has mean 0.49 and spread 0.077; the runtime 32³ noise matches it.
- A particle effect placed with a `frame` (a hull's live matrixWorld) simulates in that frame and is carried into the world as its quads are built: anything held or played aboard is placed that way, and the planet's ground and the weather's kill are never applied to it. A held flame's heat is stamped each step and ignored when not held within 100 ms; `BountyHunterKit.coolDown()` (class switch, leaving a ship) drops the flame's heat and its held effect.
- The lens flare follows what the sky draws, not the light: a flare body is a `sun_*.sht` with a glow whose two sprites loaded (Yavin 4's sun slot is the gas giant and has none, Dathomir draws no sun, Mustafar's moon slot is a second sun and flares at night, in slot 1), and in space the brightest star sprite group, which is mostly nowhere near the zone's main light; each keeps a fixed slot, and `SwgSky.flareLights` reads the sprites' own position, opacity and `visible`. The sky's sprites hang at 3500 m and are depth-tested, so the occlusion counts depth as sky from 98% of that distance along each pixel's view axis, compared as `1 - depth` (exact near the far plane, unlike a linearised distance); fog does not dim the sprites, so it does not dim the flare. The occlusion is smoothed in a 2x1 target the element draw reads in its vertex shader, so nothing is read back. The composite never lifts a pixel past exposed luminance 0.9 (display 0.874, under the 0.888 where white begins) and adds nothing above it, which is why by day the flare is mostly a streak and ghosts; `__debug.flareProbe()` counts it, and `__debug.flare().sources[i].turn` is how to steer to a star when flying.
- Inside a building the world seen through its doorways is drawn after the rooms (the exits' stencil, a depth reset, the world pass), so anything additive drawn only with the rooms (`INTERIOR_LAYER`) is painted over wherever a doorway is behind it; outside, the world pass draws actors over the whole screen. The room motes (`RoomAir`) are on the actor layer, drawn in both passes and clipped by the stencil, and hidden on any frame the portal renderer draws from outside, since `cameraBuilding` can flip for a frame on the door line. The daylight beams are the doorways extruded along the sun, evaluated per pixel in the effects chain (`lightShafts`), where the scene depth stops them at whatever stands in them.
- A point sprite under about 3 px changes brightness up to eightfold as it crosses pixel boundaries (the Gaussian at 1.5 px; a hard disc twentyfold), which reads as twinkling: draw motes at 3.5 px or more with a Gaussian and no discard, and scale the colour by (true size / drawn size) squared.
- A third of a building's point lights sit outside their own cell's box, many in the ceiling above it, and exit polygons stick out of their cell's box by up to half a metre (Mustafar's crashed ship's torn bridge opening stands 3.8 m off its own plane): anything that clips to a cell box or casts a sight ray to a lamp must pad the box with the doorway's own vertices or clamp the lamp inside first.
- A light moved by setting its `position` keeps last frame's `matrixWorld` until the scene is drawn, and the effects' light records (`fillFxLights`) read the matrix: anything that reads the lights before the draw (the room's air does, because its motes are in the scene) sees last frame's places on the frame the room's lamps are handed out again, so `RoomAir` holds its lamps for that one frame and reads them all as new on the next.
- Which weather level is active was the server's and is not in the archives: `weatherSchedule.ts` walks each planet's levels from the wall clock (an anchor drawn from the planet's climate every two hours, one-level Metropolis steps every five minutes between), so every player on the relay sees the same weather without a protocol change. The sky blends up to four environment rows (two levels, two areas while crossing a boundary; `SwgSky.setMix`), both gradients crossfade on the dome, and the clouds are a fixed pool of four sheets whose drift is integrated per image, never computed as time times speed, so a strengthening wind never makes them jump. A sheet samples its image at `xz / repeat + scroll`, so the picture moves against the scroll: the drift takes the wind's heading off the scroll (`driftScroll`) to move the clouds the way the rain leans and the dust blows.
- Weather particles are in `weather.scene`, which has no lights and no fog. They are drawn once after the portal renderer (stencil 2 when the camera is inside, so only through exits) and compiled with `renderer.compile(weather.scene, camera, weather.scene)` at the end of `compileAllAsync`. Compiled against `world.scene`, the program key carries its lights and fog, and the first rain compiles during play. They die, and their fragments are discarded, below the top of their column: a grid of rays cast down around the camera (`RoofGrid`; rooms left out by collision group; lake surfaces included; no casts until physics has stepped since a reset, `Physics.steps`). The camera-following half runs after the camera and the physics step (`world.updateWeatherView`). Storm rows that turn shadows off fade `shadow.intensity` and skip the shadow pass (`portals.shadowsWanted`); clear rows always keep shadows. Never toggle `castShadow` or `shadowMap.enabled` for weather. The storms that blow sideways (dust, the snow storm) shoot along the effect's -X, so they are yawed by the wind's heading plus a quarter turn (`DUST_YAW_OFFSET`).
- The aimed depth of field keeps its focus on the GPU in a 1×1 float ping-pong: the median of five half-resolution depth taps at the crosshair, eased in dioptres. The sky and anything nearer than the shooter's plane (`cam.orbitDistance + 0.4`, 0.6 m in first person) do not count. There is no lens until a surface has been under the crosshair this aim, and the last surface is held after. The aperture widens as the square root of the focus only to 40 m, since an unstopped aperture blurred the whole foreground whenever the focus went far. The lens-grid texels carry the raw circle of confusion, which rises with depth, so the gather orders taps without a depth fetch. The grid strides to a quarter on buffers taller than 2000 px, so the radius never outruns the ±3 tile dilation. Glows that write no depth (gun and ship particles, bursts, blade cores) are drawn into a `dofGlow` R16F product (1/z, MAX-blended, particles masked where bright), so a bolt at the focus does not take the blur of the town behind it. The game clears the aim on any frame the player is not simulated (dead, a panel, the map), or the shoulder view and the lens hold on under the death card. The wardrobe doll takes its lens pass (one render into a 4-sample half-float target, then a premultiplied gather, tone curve and sRGB onto its see-through canvas) only once zoomed in enough for a pixel of blur, with hysteresis to 0.7 px. Both program variants are compiled when the panel opens.
- Wetness is shared uniforms (`WEATHER_UNIFORMS` in `wetness.ts`) read by the ground (its own `injectWetness(shader, 'ground')`, `userData.wetBuiltIn`), the water (rings in its slope) and every world material wrapped by `wetWrap` in `World.adoptMaterials`, right after `csm.setupMaterial` and in the same iteration, so the wrap is in the program key before anything compiles and rain only moves uniforms. The wrap is judged once per material by the first mesh the scan meets it on and is idempotent (a hook the cascades replaced is wrapped again around the new one). Never wet: skinned meshes, anything under a bone, under a skinned mesh or under a `userData.weatherDry` group (the player's figure and thrown sabers, another player's ship), and materials marked `interior`, `dry` (every ship's own materials, hull, wings, engines, guns and cockpit frame, marked by the garage when it loads the model and by the model's own kind, never the kind it is spawned as, since a shared material is judged once for every copy; the garage's per-model copies of a hull's room materials; ship interiors), `glass`, `water`, `wetBuiltIn`, `invisible` or `unlit`, or transparent. Shelter is the roof grid sampled with `texelFetch` beside a wall (out along its normal), not above it, so walls are wet down to the ground and a covered floor stays dry. `localStorage['swg.weather.wrap'] = '0'` turns the wrap off for a cost baseline.
- The dressed NPCs are mobiles, not fighters: a kinematic fighter walks through walls and knows no room, and a cantina NPC must follow the player out of the door and back in. A person is a "look" (`mobiles/look.ts`): a parts character (a species body, or the NPC's own `mobiles/models/<app>/parts.json`) built once per entry with `Character.load(..., { dir, skipRig: true })`, dressed with `wearItemFrom(<wardrobe folder>, item, part)`, coloured (the template's `custom` set as shared, which reaches each private copy; each piece's values as `<part>|<name>`), and cloned per spawn after `customizer.settled()`. No rig is fetched: the pack's clips bind to the clone by joint name.
- A ray for "the floor under a body" must pass only what stands still (`physics.topSurface` with a fixed-or-bodiless predicate): cast from inside a capsule, it finds that capsule and calls its middle the floor. A fighter rose a metre a frame that way.
- The planet's wildlife is stood in `World.warmUp`, before the pack's terrain arrives, on the stand-in heights; when the real ground comes in it can be metres above them. Mobiles are lifted back onto the terrain from the manager's 4 Hz pass (`Mobile.liftToGround`), and a frozen-tier body only sleeps when grounded: one put to sleep in mid-fall hung 200 m under the ground for good.
- A parts pack's `customize.json` (5 MB for a wardrobe) is fetched and parsed once per folder for the session (`loadCustomizeFile` in `customizer.ts`) and shared by every customizer: each dressed NPC's look builds its own customizer, and re-parsing it per look stalled the frame for every new entry. Nothing may write to a parsed recipe or palette; key per-character state by the recipe object instead.
- A mobiles model that fails with "no mesh survived" is one the game's own archives strip at every detail level (the gubbur): a rerun fails it again, so `status` lists it apart and does not count it as work (`permanentFailures` in `mobiles.mjs`), but only while the failure was recorded from the archives the catalogue was made from and for the unit signature it plans now. A skinned mesh's level list (`.lmg`) gives the finest level that has triangles, not merely the finest that exists (`lmglevel.mjs`, in `convertSat`, the wardrobe's worn meshes and the mobiles plan); on the retail archives that changes no pick (4,642 lists, and the only one whose finest level is empty is empty at every level).
- A particle can carry other effects (a `PATT` in its `PTCL`: path, a start-percent range, kill-with-particle, and spawn on creation, death, a percent of life or ground contact). `exportParticle` converts them through its `attach` callback (`convertParticle` recurses, with a `{ pending: true }` placeholder in its cache against cycles) and writes each one's `file` onto the attachment. The game places them as transient effects in the parent's frame, one level deeper (at most 12), follows the particle each frame and, with kill-with-particle, sets their `rateScale` to 0 when it dies; a stopped transient ends when its particles are gone. At most 256 live per `ParticleEffects` (Mustafar's lightning chain peaks between about 75 and 140); `ParticleEffects.status` counts what was skipped. A light dust storm, the forest's falling leaves and Mustafar's lightning draw nothing except what they carry. `status` asks for the sky again while a sky's effects carry one the pack has no file for.
- A flip-book shader is a root `SWTS` form: `NAME` the base shader (sometimes an exporter path like `c:\a_exported\shader\x.sht`, which lives at `shader/x.sht`), a timing form and one `TEXT` per frame (slot tag, texture path) that replaces the base's main texture. The timing forms are the client's switcher classes (their RTTI names are in the executable): `DTST` DeltaTimeSwitcher (count, seconds per frame), `DRTS` DeltaRandomTimeSwitcher (count, min and max, drawn per frame), `DPPT` DeltaPingPongSwitcher (count, min and max; plays forward then back), `DFST`/`DRFS` frame switchers only on samples. `SWSH` is the same with whole shaders as frames; the Theed `SWSH` frames are not in the archives, and the falls the world places are the scrolling `a_splitalpha_scroll` shaders.
- Texture scrolling is `TSNS` (slot tag, then u1, v1, u2, v2 per second) and only matters when the effect's vertex program adds `textureScroll` (`a_scroll.vsh`, `a_scroll_rgb1_a2.vsh`, the water programs): the offset is `frac(rate x seconds)`. Split alpha (`a_splitalpha.psh`) takes colour from set 0 and alpha from set 1 of the same texture; the converter writes an opaque colour image and an alpha-as-grey image (three's `alphaMap` reads green), each on its own glTF sampler so that GLTFLoader, which shares a `Texture` per image and sampler, gives every scrolling material its own offset.
- An effect pass's DATA has a heat byte after dither from version 10 on (and a pixel-shader byte first before version 5): reading blend and test at fixed offsets made every version-10 effect a cut-out. Only the scrolling, split-alpha, flip-book and unlit-alpha-screen shaders among the 2,113 that blend and test with z-write off are converted as translucent, in a new `translucent` field that leaves `alphaMode` alone because the sky's celestial sprites read it; the rest (foliage, hair, fences) stay cut-outs, because three sorts transparency per object and an instanced field would draw far over near. Translucent placed surfaces take `renderOrder` 3, or the terrain water, which follows the player and so always sorts nearer than an instanced mesh's centre, is blended over them. A shader can write its effect inline (`FORM EFCT` inside the shader, the whitewater and a few dozen holograms, particles and UI shaders); its pass is read like a file's.
- In the client a fully masked emissive texel is the texture colour exactly: the `a_emismap` family lerps the lit texture toward the unlit one, and the rest add the mask inside a light that `saturate` caps. three adds `emissiveMap` after lighting, so the converter splits such a texture in linear light into a base colour `rgb x (1 - m)` and an emissive `rgb x m` (image names carry the mask's source); laying `rgb x m` over the full texture made every lit sign twice as bright by day. The mask is read from the pixel program, and two shapes misled: `a_specmap_bump_emismap` declares a local `sample` in two blocks, the diffuse map (its alpha the gloss) and then the normal map, whose alpha is the glow, so a local is resolved from the read nearest before `emisMask`; and the envmask assembly programs `lrp` toward the environment cube (ENVM) by their shine mask with the same instruction the emismap ones use toward the texture, so only an `lrp` toward a sampler on MAIN is a glow. `a_emis_full` and its alpha variants are unlit (`KHR_materials_unlit`, `userData.unlit`); `emisadd` is unlit and additive, with alpha forced opaque only when the source factor is One. The game applies flags that are in a program's key (`alphaTest`, `alphaMap`, additive blending, `fog`) in the GLTF plugin's `afterRoot`, before anything compiles.
- Animated surfaces (`src/world/surfaces.ts`) swap `map`/`emissiveMap` between textures of one kind and move `texture.offset`, neither of which is in three's program key; every GLTFLoader that loads converted static models must be `surfaces.withPlugin(new GLTFLoader())`, and a material's link to its flip-book is the string `userData.swgTrack`, never a texture, because `material.clone()` copies `userData` through JSON. The plugin only registers; a material joins its track in `World.adoptMaterials`, when it is in the scene, and leaves on its `'dispose'`, because `AssetPack` swaps a cell's original material for a clone and never disposes the original. `World.unload` sweeps the records no material joined. The clock runs on `World.simTime`, so `__debug.advance` steps it.
- An item's name and description are string ids on its template (`objectName`, `detailedDescription`: a presence byte, the table, a presence byte, the key); take the first along the chain whose table and key are both set, since the base templates carry the table with an empty key. About one in ten points at `static_item_n`, a table the client never had: those fall back to the table with the item's id as key, then to words made from the id (`name: null`).
- What an item occupies is its template's `arrangementDescriptorFilename`: `FORM ARGD > FORM 0000 > ARG ` (three letters and a space), each `ARG ` one alternative of NUL-separated slots (`ring_either` is `[ring_l]` or `[ring_r]`); a shirt is chest1 and a jacket chest2, so they are worn together. The player's slots are `abstract/slot/descriptor/player.iff` (`SLTD > 0000 > DATA`). SWG's arrangements put every lightsaber and polearm in both hands.
- Who may wear what is `datatables/appearance/appearance_table.iff`: a row per `shared_<id>`, a column per species and gender (`Male Human` to `Female Sullustan`), each cell `:default`, `:block` (cannot wear), `:hide` (worn, takes its slots, not drawn) or that species' own appearance. The wardrobe converter takes its own folder's column (the men's bracelets, the Ithorian cuts) and writes the rest of the gender as `fit`; a cut the archives hold stripped (six Ithorian camouflage pieces) falls back to the template's appearance, or the item is lost; `fit.own` never names the folder's own species, which wears the entry's `sat`. The Ithorian folders hold the table's `:hide` items as entries with no meshes (`sat` null, `parts` empty): anything that dresses from a wardrobe must expect them.
- Item pictures are baked at conversion by a software rasterizer (`tools/swg/thumbnail.mjs`, X negated like the GLBs) and shown as `<img>`: a live 3D cell compiles a program per material on the main thread, which is the stall the whole game is built to avoid. The texture entries carry a reduced copy of their main image as a non-enumerable `thumb` only while `wantThumbs` is set (the weapons and wardrobe commands, unless `--no-icons`), taken before any glow is split off, so no run decodes a PNG it has just encoded and the snapshot, gallery and ships runs pay nothing.
- Three skips an object with `visible = false` before the shadow pass looks at it, so hiding something that way removes its shadow too. What first person hides of the player goes on `FX_LAYERS.shadowOnly` instead: the portal renderer's shadow camera enables every layer and its view passes only 0 or 1 plus 31, so the shadow maps draw it and no view does. Layers are not in a program's key; nothing compiles on the switch, because `World.passesOf` treats the layer as an actor's, or a warm-up made in first person (an Effects switch, an arrival) builds the head's world-pass programs only and zooming out indoors compiles on the frame. `markActor` leaves a shadow-only mesh as it is, so nothing that prepares or marks the player un-hides the head; both it and `passesOf` ask `isShadowOnly` in `fxRegistry.ts`, which the node test calls. A draw with `FX_ALL_LAYERS` (the debug mask) sees shadow-only meshes too.
- What is "on the head" (`headRule` in `src/player/headHide.ts`) is decided per worn item from the client's data, never from mesh names: hair and the `hair/`, `wearables/hat|helmet|goggles/` template folders go whole; an item whose triangles all lie in head zones (skull, face, sideburns, neck) goes whole; a garment (it hides a zone below the neck) only ever loses its head triangles; an item hiding only head zones goes whole; otherwise the skin decides. A triangle is on the head when any vertex is weighted at least half to `Head` or below. Zones alone fail (some helmets have none, the Kashyyykian chest plates hide `skull`, the Mon Calamari body hides `skull`) and the hooded robe's arrangement does not take the `hat` slot; the skin is what tells the hood from the robe. Skin alone fails too: the Mandalorian Imperial helmet is skinned to `spine3` and only its zones hide it.
- A partly hidden mesh has its index reordered once so its head triangles are last, and its `onBeforeRender` narrows the geometry's draw range for the eye's passes while `onAfterRender` puts `Infinity` back; the shadow pass calls `onBeforeShadow` and draws it all. The range lives on the geometry only for the length of one draw, because the wardrobe doll's clone shares the geometry (and `clone()` never copies the hooks). The per-triangle zones are reordered with the index, and `Character.cull` culls through `cullIndex` (headHide.ts), which keeps the order and counts the kept triangles ahead of the head, so the kept head triangles stay last and the eye's count stays right.
- `Object3D.copy` deep-copies `userData` through JSON: never put a typed array or per-triangle data on a mesh's `userData` (the doll clones the character every time the wardrobe changes); per-triangle data belongs on the geometry's `userData` or in the owner's own structures.
- SWG's arrangements put every lightsaber and polearm in both hands. This game keeps Jedi Academy's dual style for the off-hand classes (`OFF_HAND_CLASSES` in `src/core/inventory.ts`, the one list the rack, the player and `planHold` read); a gun or the double-bladed saber empties the left hand. `Character.wearItem` honours the appearance table's `hide` for everyone who dresses (an empty part: it takes its slots and draws nothing), `Equipment` refuses `block`; the species packs are dressed in `shirt_s03`, `pants_s01` and `shoes_s01`, which the table blocks or hides for Wookiees, so an item a species pack carries as a part is worn as that part and counts as wearable (`packPartOf`), or every Wookiee would own a shirt it cannot put back on.
- Anything put on or taken up in play goes: `Character.loadPiece` (hidden), `customizer.settled()` (a recipe can add a normal map, a new program), `World.prepareActor` a mesh at a time, then `Character.putOn` in one synchronous step that also takes off what it displaces. `prepareActor` calls `markActor`, so `putOn` (whose `applyOcclusion` ends in the first-person head layers) must come last. A weapon is prepared on every hold, not once per file: a program is compiled for the target and scene of that moment, and the Effects setting or a travel changes both. A peer's clothes and weapon go on the same way (`dressPrepared` in `look.ts`, `RemotePlayers.applyHeld`), and a peer's rig stays hidden until its look is on and compiled.
- The outfit, the items and the hands are written by `Equipment` on every change: before the backpack, clothes changed in the world were never saved, never reached other players, and the weapon in hand was forgotten at logout. `Equipment.reset()` empties the hands on the way to the select screen and into the creator (`useSpecies` keeps the rig when the species is the same, hands and all), and every queued operation is dropped if the character changed under it, or one character's weapon is saved into the next one's record. `restoreHeld` puts the saved hands back unlit (`Player.equip` lights a Jedi's blade) and does not switch the class; `setClass` writes the class to the record.

6. The engine client data (`clientdata/ship/component/eng_*.cdf`, `GLOW` forms) carries glow sizes per engine style; their float layout is not decoded, so glows are sized by hull height.
7. Mounts wear the game's saddle on the creature's saddle hardpoint where it has one (the 22 the game let players ride) and a guessed one on the posed back otherwise; the rider leans with the saddle as authored (the tauntaun's and cu pa's 5 degrees back, the lava flea's 16 at its idle), and a tilt damping in `syncMount` is the follow-up if the owner finds it harsh. God rays are a depth-based radial pass in `postfx.ts` (sky is depth past 2.5 km; the sun projected to the screen; off with bloom off); the effects still wanted are listed in the README's "Effects to do". Moving things blur by their root's motion only: limbs, a ragdoll's fall and a peer's roll do not blur on their own (a previous-bone texture per skeleton is the sketched fix).
8. The map window (M): a planet's map is the client's `texture/ui_map_<planet>.dds` over the terrain's width (`maps` command); the space map draws the streamer's placed objects and every ship. Not done: other ships needing a ping, the space map's stations named, remote players on either. The pod racers' game seats: for pod_racer_two, balta and Anakin's the authored origin plus the pose's root lands outside the pod's box, so the rider takes a cockpit guessed from the mesh (`podSeat`); which of the eight pods look right has not been seen from here (a hidden tab's screenshots would not frame them), so the owner's report per pod, with `__debug.seat` nudges, is what to bake into a per-pod seat table next.
9. The plain models' colour variants are whole GLBs beside the base (`mobiles/variants/`), and a combination whose palette none of the appearance's shaders bake comes out identical to the base and is not written: `shaderNeedsBake` looks at the first pass only, so a hue applied in a later pass never reaches the texture (the ships command bakes every pass of a ship's paint shaders; the mobiles' variants and the wardrobe still use the first-pass check). Every `--var=name=value` on the command line is lost the same way for `sat`, `parts`, `player` and `species`, because the option parser splits at every `=` (`cli.mjs`); the `mobiles` command passes its values as a Map and is not affected.
10. Weather: no weather sounds play (their names are in `sky.json`); the climate weights and Life Day's dates are invented; weather writes no depth, so ambient occlusion and depth of field treat rain as whatever is behind it; Mustafar's lightning (a chain of eleven carried effects) plays, but its look has not been seen yet; props inside buildings share materials with the same props outdoors, so seen through a door from beyond the roof grid (about 36 m) they can show a faint wet sheen.
11. The backpack: species cuts are recorded, not converted, for the shared human folders (a Rodian wears the human hat mesh; `fit.own` names its cut), and the species packs' own dress (shirt, trousers, shoes) overrides the appearance table for the species it blocks. NPC fighters still pick outfits by the give tab's regex groups and ignore `fit`, so a Wookiee fighter can wear a blocked shirt. Item modifiers (armour, damage variability) are not modelled; nothing limits how much is carried.

## How to work with the owner

Give them exact commands to run and exactly what to look for, one list, every item independent of the others so they can do it all in one session. When something cannot be judged from here, ask for the one observation that separates the causes rather than guessing twice. Converter changes need a reconversion (`npm run swg -- ships @SWG assets-private --retail-only` for ships; the README's table for the rest); say so every time, and say when a change needs none.
