# SWG3JS

Star Wars Galaxies, rebuilt for the browser with [Three.js](https://threejs.org/). A for-fun recreation of the SWG feel: big open planets, a free third-person camera, wildlife wandering the plains, and a galaxy map for hopping between worlds. Plus the things SWG never had: a jump button and Force powers.

## Play

```bash
npm install
npm run dev
```

Open the printed URL. The first screen is the **character select**: up to five characters kept in this browser as cards (name, species, class, the world it is on, when it was last played), a click on one enters the galaxy as it, the × on a card deletes it, and **Create new character** opens the **creator**: the appearance and wardrobe panels at full size over no world at all (nothing streams while you shape and dress, so nothing stutters), with the species and gender picker, the shape sliders, the colours, the hair and the clothes, and a bar below for the name, the class (Jedi or Bounty Hunter) and the world to start on. Entering shows a **loading screen**, the planet's picture grey and dim and coloured in from the left as the world arrives (the pack's stages, the ground chunks around the feet and the placed objects within working range, weighted by how long each takes, with a percentage and what is being waited for under the planet's name), until the ground under the feet, the chunks around them and the buildings within working range are in, and every shader in the scene has compiled behind it (the effects, the bolts and the kit's visuals put one of themselves in the scene first, so the first shot, hit or throw finds its shaders ready; a building that streams in later compiles in the background as it arrives, and a shader that still compiles on a live frame is reported in the console as `shaders: N compiled during play`); the character is held still meanwhile, so it never falls through ground that has not arrived (travelling by the map and the map's jumps wait the same way). Where a character stands is written into its record every few seconds and when the page closes, so it is back on the same spot next time; a new character starts at its world's spawn.

**Jedi**: `1` to `6` the Force powers in the slots (Jump, Speed, Push, Lightning to start; the Skills tab of the inventory picks others, and bare hands) · `L` lightsaber.
**Bounty Hunter**: `1` to `6` the gadgets in the slots (Thermal Detonator, Fragmentation Grenade, Trip Mine, Det Pack, Stim Pack and Bare Hands to start; the Skills tab picks others) · `RMB` aim · `K` pistol or rifle · `V` kneel and `Z` prone for steadier shots.
**Elevators**: `E` at an elevator terminal (up or down as it says), or standing in a lift shaft (a building's or a ship's): a menu of the levels the shaft reaches, by the rooms they open into; click one or press its number. `E` beside a building with no way in on foot (a dungeon whose door was a server object, a station whose doors are up in the air) puts you inside.
**Vehicles**: the mouse steers (the vehicle turns toward where you look; `A/D` steer too) · `Alt` hold to look around without steering · `W/S` throttle and brake · `Shift` boost · `Space` hop (bikes and mounts) · flyers climb and sink as you look up and down, or on `Space`/`X` · ships: `W` builds speed; in flight the mouse moves a cursor that stays where you leave it: inside the small circle in the middle it aims the guns (the circle and the lead reticle turn green on the lead), outside it the ship keeps turning toward it, harder the further out; `A/D` roll, `Space`/`X` pitch, `click` fires, `Tab` next target · `U` opens and closes the wings (a ship whose wings open) · `E` off.

URL options: `?planet=lok` spawns on a specific world, `?class=bounty_hunter` picks a class, `?lowfx=1` disables shadows and halves resolution for weak machines.

## Installation

1. **Node 22.18 or newer** (24 is fine) and a Chromium browser. Chrome on Windows is what the game is tested in.
2. Clone the repo and `npm install`.
3. Copy `.env.example` to `.env` (git-ignored) and fill in where your own installs are:
   ```
   SWG=C:/SWG                                                                # the folder holding the client's .tre archives
   JKA=C:/Program Files (x86)/Steam/steamapps/common/Jedi Academy/GameData  # Jedi Academy, for the saber and jump animations
   ```
   The converter replaces `@SWG` and `@JKA` on its command line with these, so paths with spaces need no quoting.
4. Convert the assets into `assets-private/` (git-ignored, never committed) with the command list under **Converting your own SWG install** below, every command with `--retail-only`. `npm run swg -- status assets-private` says what is in place and prints the command for anything missing.
5. `npm run dev` and open the printed URL.

For **Claude Code in VS Code**: `CLAUDE.md` at the repo root is the handoff, read automatically at the start of a session, with what the project is, the rules, the architecture, what took a long time to learn, where things stand and what comes next; `.claude/launch.json` starts the dev server from the extension. Ask it to read `CLAUDE.md` and `docs/ASSETS.md` before anything else.

## What exists today (v0.3)

- **Rigged character pipeline**: skinned GLTF characters with an animation state machine (idle, walk, run, airborne, seated), clip speed matched to movement, and world-space arm solving so aiming and saber swings override the clip pose. The Mixamo X Bot ships as a stand-in in `public/assets/characters/`; add `?rig=0` to use the primitive body.
- **SWG asset converter** in `tools/swg/`: reads TRE archives (including the `.toc`-indexed archives of the later client) from a locally owned install and writes textured static meshes as GLB, with retail-manifest verification. Verified on a real install. See `tools/swg/README.md` and `docs/ASSETS.md`.
- **Asset packs**: `npm run swg -- pack` builds `assets-private/<planet>/` from a spec; the game scatters the converted rocks, debris and flora across the terrain and places a hand-laid outpost of real buildings near spawn, with exact mesh collision. Without a pack the low-poly placeholders are used, so the public build stays asset-free. `npm run swg -- creatures` and `npm run swg -- player` convert the game's own creatures and a dressed player character (skin baked from the game's texture-renderer recipes) into `assets-private/creatures/` and `assets-private/player/`; the game swaps them in when the manifests exist.
- **Design doc** in `docs/DESIGN.md` with the settled decisions, pillars, combat model, skill system and phases.

- **Physics** via [Rapier](https://rapier.rs/) (Rust compiled to WebAssembly). Terrain chunks near the player get heightfield colliders, trees and rocks get cylinders, creatures are dynamic rigid bodies, and the player is a kinematic character controller with auto-step, slope limits and ground snapping. Force Push, detonators and deaths all move real bodies.
- **Speeder bike**: a dynamic body held up by four spring ray casts, with throttle, steering, lateral grip, boost, hops and engine drag. Mount it with `E`.
- **Hitbox combat**: the saber blade is swept as a capsule against creature colliders every frame of a swing, and the blaster fires bolts that fly at 58 m/s and hit the first thing in their path, so a moving target is missed. No hit-chance rolls anywhere.
- **Two classes**: Jedi (saber, Force Jump, Speed, Push, Lightning) and Bounty Hunter (blaster rifle, physics-simulated thermal detonators, stim pack). Switch with `C`. The placeholder jetpack is gone; the game's own jetpack will come back as something you equip.
- **Creatures fight back**: health, aggression on the dangerous worlds (rancors, kimogila, boar-wolves, mawgax), stuns, knockback, ragdoll-ish deaths and respawns.
- **Day and night**: a 12-minute day with a moving sun, sunset tint, moon, stars and moonlight. Hold `T` to fast-forward.
- **Player health** with regeneration, a defeat screen and respawn.

- **Twelve planets**: the ten launch-era worlds (Tatooine, Naboo, Corellia, Dantooine, Lok, Endor, Dathomir, Yavin IV, Talus, Rori) plus the expansions' Mustafar and Kashyyyk. Kashyyyk is several separate terrains in the game (Kachirho, the hunting grounds, the Dead Forest, the Rryatt Trail, the caverns, the Kkowir forest, the Avatar platform), so the galaxy map lists its zones and travel lands in whichever you pick. Each is a seed plus a set of terrain, palette, sky, fog, vegetation and wildlife parameters in `src/data/planets.ts`.
- **Streaming procedural terrain**: 64 m chunks generated from layered simplex noise around the player, with analytic normals (no seams), vertex-colored by height, slope and shoreline. Planets are effectively unbounded.
- **Real ground in private builds**: the terrain generator paints the game's shader families across the ground exactly where the original rules put them, and the ground material blends each family's texture (at its own world scale) across every triangle, so sand meets rock and grass the way it did in the game.
- **Particle effects in private builds**: the game's own emitter descriptions (campfires, smoke, sparks, steam, candle flames, waterfall mist, Mustafar's lava plumes) play where the world snapshot places them, batched per texture and asleep beyond their range.
- **The world's own sound in private builds**: every area plays the game's own day and night ambient beds, taken from the same environment rows the sky follows and blended at the same weights, so a storm's rain rises with its clouds and walking from the grassland into the swamp crossfades in sound as it does in sight. Each row's second sound is its bed of quiet one-shots — a bird, a distant call every fifteen to thirty seconds. Inside a building the interior table's row for that room takes over, and the game's placed sound objects (crowds, cantina bands, sparks, fires, the starport announcer) play where the snapshot puts them, with the waterfalls', steam vents' and fires' own particle sounds. The mixer's sliders are in the menu's Sound section; `__debug.ambience()` says what is playing and why.
- **Real creatures in private builds**: the converter turns the game's skeletal appearances (skinned meshes, skeletons, compressed keyframe animations) into skinned GLBs, and the planets' creatures walk, run, attack and fall with their own animations.
- **Real flora and water in private builds**: the planet's own trees, rocks and plants grow where the terrain rules and the engine's seeded random numbers put them (the same spots on every server), and water sits at the terrain's global table height with every lake and pool from the terrain layers. Each lake and sea is drawn with the look of the water shader its own terrain rules name: its colour and opacity come from that shader's main texture (Lok's sea is sulphur yellow, Dathomir's near black, the misty falls pools a clear teal), how rippled it is from its normal map, and how fast those ripples drift from its scroll rate. A pack converted before this falls back to the planet's own colour and says so in the console.
- **Real SWG terrain in private builds**: `src/swg/terrain/` is a port of the game's terrain generator (its seeded fractals, layer boundaries, filters and affectors, and the ground modifications buildings apply). When a converted pack carries the planet's `.trn`, chunks are generated from it in a Web Worker and the ground matches the original game to the centimetre, so snapshot buildings sit exactly on it.
- **Props**: instanced trees (six styles: pine, round, palm, dead, giant, swamp) and rocks scattered deterministically per chunk, with cylinder colliders.
- **Water**, per-planet gravity, a gradient sky shader with sun discs (Tatooine gets two), exponential fog, and shadow-casting sunlight.
- **Player**: SWG-style orbit camera, run/walk, jumping, air control, wading and swimming, a low-poly Jedi with a walk cycle and a toggleable lightsaber.
- **Force powers** with a regenerating pool: Force Jump, Force Speed, Force Push (sends creatures flying), Force Lightning (arcs to the nearest creature in front of you).
- **Wildlife**: per-planet creatures (banthas, kaadu, rancors, kimogila...) that wander, flee if skittish, get knocked around and stunned.
- **Galaxy map** overlay for instant travel.

Debug counters are exposed on `window.__stats` (frame, physics and render milliseconds, draw calls).

## Roadmap

Rough order, all up for discussion:

1. **Feel**: rigged GLTF characters and creatures with real animations (Mixamo for humanoids), saber stances and combos, blocking, dodge rolls, footsteps and ambient audio.
2. **Models**: replace primitives with proper assets. See "On assets" below.
3. **Places**: hand-placed cities and points of interest on top of the procedural base (Mos Eisley, Theed, Coronet), starports, buildings with interiors.
4. **Life**: NPCs with dialogue, quests, enemy humanoids that shoot back, loot.
5. **Systems**: skills and professions, inventory, crafting, harvesters, housing.
6. **Space**: ships, the JTL-style space layer, travel between planets by actually flying.
7. **Multiplayer**: authoritative server, chat, guilds. The code keeps world state in plain data with this in mind.

## Jedi Academy movement and saber combat (this branch)

The branch `claude/jka-combat` swaps the player's ground and air movement and the lightsaber combat for translations of Jedi Academy's (OpenJK, GPL-2.0; see `LICENSES/OpenJK-GPL-2.0.txt`). Swimming and noclip are untouched.

- **Movement**: Quake-style friction and acceleration, a little air control, and jumps that keep lifting while Space is held, up to the Force Jump level (level 3 by default, spending Force while it lifts). Landing from higher than your own jump's reach hurts. Ctrl crouches (half speed and a shorter capsule), tapping Ctrl while moving rolls that way, and landing with Ctrl held while moving rolls out of the landing for a third of the damage. `__debug.profile('swg')` in the console restores the original numbers.
- **Wall moves** (Force Jump level 2 and up, each a fresh press of Space): strafing and running beside a wall runs along it (press Space again to flip off, or run out of wall to stop); strafing into a wall flips off it; jumping at a wall just off the ground runs up it and flips back (level 3 runs higher); back and Space backflips; and at level 3, pressing at a wall in mid-air grabs it and springs off. A force jump that starts while pushing a direction becomes a flip that way.
- **Saber**: the first click draws the saber; the direction keys held with the click pick the swing (forward: overhead, sideways: horizontal cuts, diagonals: diagonal cuts); holding attack chains swings through Jedi Academy's arcs until the style's chain runs out and the saber returns to ready. **K** cycles the five styles: fast, medium, strong, the dual sabers (a second saber in the left hand) and the staff (a blade at each end); each has its own animations, speeds, chain lengths and damage, and the dual and staff styles chain without end. `__debug.saber()` reports the state.
- **Special moves**, as the game's rules pick them: pressing jump with attack held and forward pushed (medium flips over into a downward slash, strong leaps into the death-from-above, the dual sabers leap twice, the staff butterflies; the fast style has none, its special is the crouched lunge); jump with attack and a strafe (a cartwheel, the staff's sideways butterfly); the staff's back, jump and attack backflip attack. The press of jump starts the leap at once, cutting short any swing in progress, rather than waiting for the game's narrow window after the jump; crouched and forward (fast lunges, the dual sabers and the staff spin); back with an enemy behind (the back stab or back attack, low when crouched); attack out of a forward roll (the roll stab); the dual sabers hitting both sides at once with enemies on both; and the katas, both mouse buttons together while standing still (each style's own long special). **R** throws the saber, which flies where you look, returns when you let go (or at its reach, after six seconds, or off a wall) and cuts what it passes; with the staff, R kicks in the direction held (in the air too). The special moves cost Force.
- **Controls**: every action can be rebound from the console and the choice is kept in local storage: `__debug.bind('crouch', 'KeyV')` (KeyboardEvent code names, or `Mouse0`, `Mouse1`, `Mouse2`; several keys may be given; none restores the default), `__debug.bindings()` lists them, `__debug.resetBindings()` clears them. X crouches as well as Ctrl out of the box, because a Mac turns Ctrl-click into a right click.
- **Facing**: the body faces the camera while fighting, in the air, rolling and during the wall moves, so a flip or a wall run reads the way the move was made. On the ground SWG has no sideways or backwards clips (its run is `loop_standing:0:speed2` whichever way you go), so the game does what Jedi Academy does: the legs turn at most 45 degrees off the camera (sideways runs angle them, diagonals half as much), backing up plays Jedi Academy's back-pedal (`BOTH_RUNBACK1`, `BOTH_WALKBACK1`, imported by default) with the legs forward, and the torso twists back to face the camera. Without those clips the body turns the way it runs.
- **Blaster bolts** (after Jedi Academy's E-11, `src/combat/bolts.ts`): the bounty hunter's LMB fires a bolt every 0.35 s from the muzzle at whatever the crosshair is on. From the hip it scatters 1.6 degrees each way; with **RMB** held you aim, the shot flies true and the camera comes in over the shoulder with a narrower view.
- **Blaster carries** (`gunIdle`, `gunReady`, `gunAim`, `kneel` and the prone states in `src/player/rig.ts`), the game's own, as its animation table names them: the relaxed carries are `loop_pistol_standing:speedN` (a pistol at the side like a hilt) and `loop_rifle:speedN` (across the chest), idle, walk and run, with the body turning the way it runs. After a shot the combat carry comes up and stays five seconds past the last one: the table's one combat stance, `loop_combat_standing:speedN`, is the unarmed one (fists up), so with a blaster the combat carry keeps the gun's own carry and faces the camera, unless the table has the loops the game's state hierarchy names for it (`loop_pistol_combat_standing_aimed`, `loop_pistol_combat_kneeling_aimed`, the `pistol_combat_standing_fire_N` shots), which the game plays when it has them. `npm run swg -- ash @SWG object/creature/player/shared_human_male.iff --find=pistol` prints that hierarchy: every state with its idle loop, actions and links, and which of those names the table lacks. The converter ranks a speed selector's branches by the speed each animation carries, so `:speed0` is the still one everywhere (the files list them in their own order). There is no aimed loop: **RMB** holds the last frame of the transition into the aimed pose on the upper body over the carry's legs (`trn_pistol_combat_to_pistol_combat_aimed`, `trn_rifle_a_standing_ready_to_aimed`), and the inverse plays once when the aim ends. A shot standing or kneeling is one of the game's additive clips (`add_pistol_fire_N`, `add_rifle_fire_N`): a recoil on the arms added to whatever pose is up, which is why those clips stood as T-poses in the gallery when played alone; prone shots are the full `<kind>_combat_prone_fire_N`, and once the table's nested entries are read the hierarchy's own `pistol_combat_standing_fire_N` and `rifle_standing_aimed_fire_N` play instead. A whole-body shot takes the upper body while it plays and the state clip drives the legs alone meanwhile, since two clips on one bone would blend half and half; `__debug.upper('clip')` plays any clip that way. **V** kneels (`loop_pistol_kneeling`, `loop_rifle_kneeling`; `loop_kneeling` unarmed) and **Z** lies prone (`loop_<kind>_prone`, `loop_<kind>_combat_prone`, `loop_<kind>_combat_prone_aimed`, still and crawling); the game's transitions play between standing, crouched, kneeling and prone (`trn_standing_to_kneeling`, `trn_prone_to_standing` and kin, the blaster's own `trn_<kind>_combat_<from>_to_<kind>_combat_<to>` set while the combat carry is up, their `_aimed` forms while aiming). The game's poses point the arm off to the left of the body, so the torso turns 30 degrees to the right, the legs still facing the camera: in the hip-fire carry with either blaster in every posture but prone, aiming with the rifle everywhere but prone, and aiming with the pistol only kneeling or crouched, since its two-handed standing aim points straight (`__debug.gun('rifle', { ready: 30, aim: 30, aimKneel: 30 })` tunes each). The hip-fire carry after a shot is the pistol's one-handed riding carry (`loop_pistol_riding`) and the rifle's "ready" pose, which the table has only as the end of its transitions (`trn_rifle_a_standing_hold_to_ready`, or `aimed_to_ready` when the aim has just ended), held there; aiming holds the transition into the aimed pose. All of these ride the upper body over the relaxed idle, walk, run or kneel, and over walking or running legs only, the torso is held steady (the lowest spine bone is turned back by the pelvis's rock; `__debug.steady(false)` shows the difference). The combat stances and hip shots the state hierarchy names (`loop_pistol_combat_standing_aimed`, `pistol_combat_standing_fire_N` and the rifle's) are in the Legends animation table but not the retail one (908 logical names against 870), so with `--retail-only` the carries fall back to the relaxed ones and the additive shots; the `player` command says so when it happens. A kneel steadies the hip shot to half its scatter, prone to a third, a crouch to three quarters. **K** switches between the pistol's and the rifle's carries as it cycles the saber styles (`__debug.gun('pistol')` or `('rifle')` does the same; there is one placeholder gun model until the weapons are converted); without the converted clips the arms are aimed by hand as before. The reloads are converted but not played yet. Bolts fly straight at 2300 units a second (58 m/s) with no drop, hurt the first thing they run into (20 damage), and can be sidestepped: whoever shoots aims where you are, not where you will be. **Blaster turrets** (`src/combat/turrets.ts`) are stood 20 m ahead of you from the spawner's NPC tab (B), which also stands the planet's creature ahead and removes either kind; none appear on their own. A turret turns to face you within 45 m, fires every 0.8 s with a degree of scatter, has 120 health, and stands again 25 s after it is destroyed. `__debug.turret(20)` stands one ahead of you, `__debug.turrets()` and `__debug.bolts()` report them, and `__debug.shootPlayer()` fires one bolt at you.
- **Blocking**: **RMB** held with the saber lit is the block: the style's stance comes up, and a bolt that reaches you from ahead is turned back into the air (`src/combat/deflect.ts`, after `WP_SaberCanBlock` and `G_ReflectMissile`). It then belongs to you and hurts what it hits. At saber defence rank 3 (the default) it flies where you look, and you can block in the middle of a swing; at rank 2 it is turned back the way it came with some scatter; at rank 1 it scatters widely, and swings leave you open. `__debug.saberDefense(n)` sets the rank. Nothing is blocked while the button is up. The parry played comes from where the bolt struck (`BOTH_P1_S1_T_`, `_TR`, `_TL`, `_BR`, `_BL`; the dual sabers' `P6_S6` and the staff's `P7_S7` sets), imported by default. Bolts from behind, while the saber flies, mid-flip or mid-roll are not blocked. Only a lightsaber blocks; other melee weapons, when they come, will not.
- **Jumps**: every jump is Jedi Academy's, since SWG's own jump clip is not usable: the jump, the pose in the air and the landing come in the direction pushed (forward, back, left, right, as `PM_JumpForDir` picks them) and in their force jump versions when the jump is a Force one (`PM_ForceJumpAnimForJumpAnim`), all imported by default. Only the Jedi has a Force jump level; the bounty hunter's jump is the plain one, with no wall moves, flips or backflips. Standing still and holding attack chains swings round the quadrants the way `PM_AttackMoveForQuad` does, each starting where the last ended.
- **Pace**: the ground speed follows the clip that plays for it, so the feet stay planted: walking is as fast as the walk clip travels (SWG's own, or Jedi Academy's saber walk with the block held), crouch-walking with the walk key as its clip, and backing up with the block held a touch slower than the run, as its back-pedal is; a plain crouch moves at Jedi Academy's crouched walking speed, a little quicker than the clip, with the clip scaled up to it, and running keeps Jedi Academy's speed with the run clip scaled to it, except with the block held, where the run drops to the saber run's own pace within 65 to 80 percent of the full run and the back-pedal to its own within 50 to 80 percent. Jedi Academy's clips were made for less than its speeds (the game lets the feet slide), so the paces taken from them are held within those bands, and its walks go no slower than 1.2 m/s. The importer measures each Jedi Academy locomotion clip's speed from its feet (the planted foot slides back under the body at the travel speed) and stores it beside the clip; SWG's clips carry their own. Looping clips (idles, walks, runs, stances) now close properly: the converter adds the key that takes the last frame back to the first over one frame interval, which is what the loop was missing when it hitched.
- **Postures**: Ctrl or X held crouches (`trn_standing_to_crouched` and back play when standing still); without the block held it is SWG's own crouch (`loop_crouched:speed0` still, `loop_crouched:speed1` moving, at the clip's pace, and the same clip slowed with the walk key as the movement is), with the block held Jedi Academy's. **V** kneels (`loop_kneeling`; moving, the crouch key, a jump or a swing gets up, Z goes down to prone) and **Z** lies prone and gets up again (`loop_prone:speed0` still, `loop_prone:speed1` crawling, at the crawl's own pace, with the walk key too); the capsule shrinks to the crouch height for both. A saber swing, the block, swimming or the jump key stand you up (the jump key only stands you up; it jumps on the next press). SWG's female walk is its own clip (`loop_skill:speed0`), to be picked up when the other species and genders are converted.
- **Weapons in hand**: the saber and the rifle sit on the skeleton's own weapon hold points (`hold_r`, `hold_l`, the bones the game hangs weapons from, in the palm) when the skeleton has them, and on the wrist bones otherwise. Where the blade points in the hand is solved by the importer from Jedi Academy's own swings: each medium and strong swing starts and ends in a named quadrant (the overhead starts pointing up, a side cut starts pointing that way), which pins the blade's axis in the wrist frame by least squares over fourteen swings; the left hand's axis is the right's mirrored through the dual stance. When the Jedi Academy archives hold a player model and the default hilt (`models/players/kyle/model.glm`, `models/weapons2/saber_1/saber_w.glm`), the axis comes from the game's own geometry instead: a hilt bolts to the player's `*r_hand` tag triangle and its blade runs along the `*blade1` tag of the hilt, both at the skeleton's base pose, so the blade's direction in the hand bone can be read off; the importer prints both axes and how each fits the swings, keeps the swing solve as the default (the swings were made to look like it) and carries the tag axis beside it as an alternative (`jkaGrip.tags`). The axis is written beside the clips (`jkaGrip` in the manifest and in `parts.json`, carried by the clip bundle), and the game aligns the hilt to it, so wrist twists in the katas turn into the saber spins they are; without it the game guesses from the bind pose. The solved axis is used through Jedi Academy's one-off clips (its swings, katas and throws) and the bind-pose guess for everything held, its stances, runs and walks as much as the game's own clips, blended over a few frames when the source changes: the stances read right with the guess and the swings with the solve. In the console, `__debug.grip({ source: 'tags' })` swaps the tag axis in and `{ source: 'solved' }` the swing solve; `__debug.grip({ tilt: 20, turn: -10 })` turns the axis by degrees about two axes at right angles to it, for every clip alike, since one axis serves the stances and the swings both (the retargeted hand keeps a constant offset from the game's hand); the result's `effective` field is the axis to bake into the manifest once it looks right. `stanceRoll` and `jkaRoll` still roll the hilt about the forearm.
- **Animations**: SWG's own idle, walk, run and swimming are what you see by default, saber lit or not, with the saber hanging at your side and the body turning the way it runs. Jedi Academy takes over while the block is held, and through any swing, throw, flip or roll: the style's stance when standing, Jedi Academy's saber run and walk (`BOTH_RUN2`, `BOTH_WALK2`; the staff's and the dual sabers' own `BOTH_RUN_STAFF`, `BOTH_RUN_DUAL` and walks, since the game gives the three single-saber styles one set) and back-pedals, the crouch and its back-pedal, when moving with the legs angled to the camera, its jump and landing in the air, and its crouch. Swimming with the block held layers the stance on the torso and arms over the swimming legs. A swing started on the move plays on the upper body alone over Jedi Academy's run (or strafe, or back-pedal) on the legs, the two played apart the way that game plays its torso and legs; standing still, the swing has the whole body, and the ordinary SWG run comes back once the saber is down. The clips come in when the player is converted with `--jka=<path to Jedi Academy's GameData or base folder>` (see the converter README); the importer retargets them onto the SWG skeleton, and the parts rig receives them through `clips-save` and `clips-apply`. Without them, everything is SWG's and swings fall back to the stand-in arm swing. `__debug.player().rig` names the clip playing.

## Species and the character creator (a start)

`npm run swg -- species @SWG assets-private --retail-only` converts every playable species and gender the archives hold (`object/creature/player/shared_<species>_<gender>.iff`: human, Twi'lek, Zabrak, Wookiee, Rodian, Trandoshan, Mon Calamari, Bothan, Ithorian, Sullustan, each male and female) into a parts pack under `assets-private/characters/<species>_<gender>/`, applies the player's Jedi Academy clip bundle (`player/jka.clips`, from `clips-save`) to each rig, and writes `characters/index.json`: for each character its shape sliders (the meshes' blend targets) and its customization variables, structured: every palette variable with its colours in order (skin, hair, eyes, lips as the species has them) and every index variable with its number of choices, and which shaders and texture renderers read each. `--only=twilek,human_female` converts a few; `--var=index_color_skin=12,index_color_hair=3` bakes them with those values.

In the game, the creator (and the inventory's tab of the same name, I) has an **Appearance** tab of its own, wider than the others, with a species and gender picker in its header that swaps the rig live (the choice is remembered; `__debug.species()` lists them and `__debug.species('rodian_male')` switches), the doll beside it (drag turns it, the right button pans it, the wheel zooms in on the face, a double-click frames it again), and **Shape**: a slider per blend target, two-ended pairs (`blend_jaw_0` and `_1`) as one slider from -1 to 1, moved live on the body and everything worn over it. **Skin, hair and eyes** are live: every palette is a row of swatches with a slider under it to scrub through, every index variable (a texture choice) a slider, and moving one renders the skin, hair or eye texture again in the browser. A worn piece's own colours (the game's private variables, a shirt's colour 1 and 2) sit in a section of their own per piece, only while it is worn, and reach only that piece: the body's colour 1 is not the shirt's; a private copy of a shared variable (the head's own skin colour) follows the shared one. The wardrobe's items carry recipes too (`wardrobe` writes `customize.json` beside the catalogue), so clothes put on from the wardrobe recolour live as well, and hairstyles sit in the Appearance tab (a species' styles, either gender's, and their colour) rather than the clothing slots. Height is a slider of its own, a scale over the model within the species' creation range. Age is a choice among the head's wrinkle maps, the game's compressed normal maps (x in the alpha, y in the green) unpacked and lit as normal maps (`__debug.normals(1, 1)` flips them the other way up, `__debug.normals(2, -2)` doubles them, `(0, 0)` turns them off; the same call reaches every normal map in the world); a mesh whose recipe carries one (the head, the body) is lit with it once any of its colours has rendered. The images are decoded by the game's own PNG reader rather than a canvas, since a canvas premultiplies the alpha and blacked out the colour under the masks' transparent texels. A blend variable the skin's blueprint reads (the fat and muscle levels pick among skin textures) is driven by the matching shape slider, and a height variable scales the whole character. The game's texture renderer, which the converter runs at conversion time to bake those textures from the game's blueprints (`.trt`), shaders, effects, textures and palettes, is ported to the browser (`src/player/texrender.ts`, the same fixed-function pixel pipeline), and the `species` and `parts` commands write its inputs into the pack as recipes: `characters/<id>/customize.json` names, for each material the converter baked, the blueprint that renders it and the shader baked over it, with every texture (and every texture a choice can pick) as a PNG under `customize/` and every palette's colours; `src/player/customizer.ts` renders the recipes that read a changed variable, one per idle turn, and puts the result on the material. A pack converted before this carries no recipes: its swatches show the `species --var=...` command instead until it is converted again. The look (sliders and colours) and the outfit are kept in the character's record in the browser and restored when it is played again. A humanoid species without a wardrobe of its own borrows the human one of its gender, since they share the skeleton. Still to come: the wardrobe's own items rendered live (a hairstyle's colour), hair styles as a slot the species allows, the species' own height and build ranges, and a saved character shared between browsers.

Zoomed into first person the head, hair and anything worn on the head are drawn into the shadows only, so the body stays in view and the shadow keeps its head.

Characters own their items. The backpack (I) shows them with the game's own names, descriptions and a picture each; a double-click puts a piece on or a weapon in hand, and the game's body slots decide what comes off (a shirt and a jacket are worn together, the Padawan robe takes off the jacket, trousers and shoes). A new character starts with a kit (a shirt, work pants, shoes and a belt, and the class's weapon in hand); a character from before gets the same kit and keeps what it wears. What is worn and held is saved, and other players see the clothes and the weapon. The Clothes (give) and Weapons (give) tabs are developer tools: whatever they put on is given too.

## The weapons rack

`npm run swg -- weapons @SWG assets-private --retail-only` converts every weapon the game can hold into `assets-private/weapons/`, sorted by class from its template path: pistols, carbines, rifles, heavy weapons, one-hand swords (the batons and clubs with them), knives, two-hand swords (the axes with them), polearms and lances, fist weapons (knucklers, the punch dagger, the razor, the fan), lightsabers; a weapon whose appearance is a blade file is a lightsaber whatever folder it sits in (the named sabers under the sword and polearm folders). **I** opens the inventory; its Weapons tab is the rack: a row per weapon with a button per hand it can go in, and the kinds the game does not play yet (grenades and thrown weapons, turrets, mines and traps, the unarmed "weapon") listed at the bottom with why. A weapon goes on the hand's hold point exactly as the game hangs it there, and its class decides everything else: a blaster switches to the bounty hunter's kit with the pistol's or the rifle's carries (carbines and heavy weapons use the rifle's) and its own torso turns (`__debug.gun('carbine', { ready, aim, aimKneel })`, one set per kind); a sword or knife switches to the jedi's kit and fights with the fast, medium and strong styles (K cycles those alone), a blade in each hand (swords of either grip, knives, polearms, lightsabers; only the double-bladed staff stays in the right hand) fights as the dual style and nothing else, a polearm or lance fights as the staff, and a lightsaber from the rack hangs its own hilt where the placeholder's was with the blade out of it. A held blade sweeps its own length for hits. `__debug.equip('dl44')`, `__debug.equip('knife_survival', 'left')` and `__debug.equip(null, 'left')` do the same from the console, `__debug.weapons('sword')` lists matches.

The rack, the garage and the NPC tab share one layout: a folding group per class or kind with its count in the heading (closed until opened, except the group holding what is in a hand, and every group a search finds something in), a grid of short names inside, read out of the ids (`sword_lightsaber_one_handed_gen4_must` shows as "Gen 4" tagged "must", `carbine_dc15` as "DC15"; the full id and the reach are in the tooltip), and **R** and **L** buttons for the hands. What is in each hand is written at the top.

With a blaster up, the barrel is measured against the crosshair every frame and the torso turned the rest of the way (a spine twist first, then the whole body's facing once the spine has turned 35 degrees), so the gun lines up in every carry: hip fire or aimed, standing, crouched or kneeling; lying down the game's prone poses are left as they are. The game's poses turn out to be nearly right on their own once the barrel is read along the model's true long axis (the manifests' bounds came with their corners swapped, which had put the "far end" of every weapon on the wrong axis). `__debug.gun()` reports the correction in degrees; `__debug.gun(undefined, { fix: false })` turns it off to see the poses bare, with the tuned turns (`gun('carbine', { aim: 30 })`) as they were. Prone, every shot plays the aimed prone shot clips, since the unaimed ones throw the off hand about. The camera's centre follows the posture: the standing eye height, lower crouched or kneeling, near the ground prone.

A lit lightsaber burns what it touches, as Jedi Academy's did: each blade is cast along its length against the world's fixed surfaces every frame, and where it meets one the stroke goes on from where that blade last touched, a red-hot line cooling to a dark char that fades over a dozen seconds; a blade dragged along a wall or swung through the floor draws one continuous stroke (`src/combat/saberMarks.ts`, one mesh of nine hundred pieces, the oldest overwritten; `__debug.marks()` counts them). Every mesh takes a burn but flesh: walls, floors, props, hulls and vehicles; creatures and fighters do not. A mark is laid in the world, so one left on a vehicle stays where the vehicle was. Swords and polearms burn nothing and throw no light: only a lightsaber (the placeholder's or a hilt from the rack) glows, and its light is the blade's own colour. Aboard a moving ship the blade's smear is kept in the hull's frame, so the ship's own motion draws none.

### Guns, after Jedi Academy's and the game's own

Every gun on the rack is one of seventeen kinds (`src/combat/guns.ts`), each with two triggers: the left mouse, and the middle mouse or Q for the other. The kind comes first from the client's own weapon effect: a gun's template names a family and an index into `datatables/weapon/weapon.iff`, whose row names the shot's particle effect, the muzzle flash and the hit effects, so the flame throwers (a fireball), the lightning rifles (a lightning beam), the slugthrowers (a tracer), the sonic and scatter guns, the bowcasters, the disruptors, the crossbows and the acid and rocket weapons declare themselves; a name settles what the table leaves plain (ion, carbonite, repeater, concussion, launcher), and the class settles the rest (pistols, carbines, rifles, heavy weapons). The converter carries the family and index in the manifest as `fx` with the effects converted into the pack's `particles/`, and the game draws the client's own bolt, flash and hit for every gun that flies a bolt, plus the flame, lightning, acid and ice beams for the held triggers.

The Jedi Academy kinds keep both of its triggers (`bg_weapons.c`, `g_weapon.c`): the pistol fires a bolt and charges on the other trigger to five times the damage; the rifle fires true and the other trigger is the rapid scatter, the carbine the other way round; the disruptor hits the instant it fires along a beam, and charges on the other trigger to four times the damage; the bowcaster charges into a fan of up to five bolts, or fires one that bounces off walls; the repeater streams, or lobs a slow concussive ball with a blast; the ion (DEMP2) bolt stuns and throws vehicles, or charges an ion blast; the flechette spreads five shards, or throws two bouncing mines that go off on a fuse or when something walks up; the rocket blasts where it lands, or follows what was under the crosshair; the concussion rifle's heavy bolt has a small blast, its other trigger an instant beam that throws whatever it hits. The game's own kinds are built the same way: the flame thrower is a cone of flame while the trigger is held, burning on for seconds after (the other trigger a fireball with an arc); the lightning rifle a bolt held on what is ahead that jumps to what stands near it (a ball of lightning on the other); the slugthrower a fast slug that drops over distance; the sonic guns a slow wide wave that staggers, with a pulse around you on the other trigger; acid eats at what it hits for seconds, or sprays; the crossbow's bolt falls as it flies; carbonite freezes what it hits to a crawl. Spread is less aimed and less in a steadier posture, a charge shows as a bar under the crosshair, and a plain bolt is a bright core with a glow tapering to the tail. `__debug.gunType()` says what the gun in hand is and what each trigger does.

### Fighters

The spawner's NPC tab (B) has **Fighter**: a humanoid of a random species from the character packs, with a random look (its height and every colour and choice the pack lets vary) and a weapon off the rack, a lightsaber half the time, else a sword or polearm or a gun. It fights whoever is nearest, you or another fighter: it runs to its weapon's reach, swings on a timer (its blade drawn like yours, in a colour of its own) or fires bolts at your middle with a little scatter, and it can be cut, shot, burned, stunned, frozen or gripped like anything else. Dead, it plays its incapacitation and lies there for a while. It dresses off its species' wardrobe: something on the chest, the legs and the feet, a hat, gloves or a back piece now and then, the pieces made for Wookiees (the Kashyyykian sets and the `wke` pieces) on Wookiees only and on every Wookiee; the Ithorians, whose skeleton is their own, dress from their own wardrobe. A piece made for the human skeleton put on another species' rig has its joints re-pointed by name (a Rodian has no lip or lid joints; those ride the root). The first fighter of a species parses that species' rig, two hundred megabytes of clips, which takes a few seconds; the clips are then shared, and each fighter's clothes are compiled a mesh at a time in the background before it shows, so later spawns cost a few short frames rather than one long one. `__debug.fighter(3)` stands three ahead, `__debug.fighter(1, 'wookiee')` one of a species, `__debug.fighter(0)` lists them with what they wear. A first pass: no cover or dodging. The Force powers reach a fighter the same way they reach a creature: it can be gripped, lifted off the ground, choked and thrown, and it falls where it lands rather than sliding along the ground. A fighter spawned inside a building stands on its floor, and its room is followed through the doors as the player's is.

### Creatures, droids and NPCs (the catalogue)

The `mobiles` conversion holds every creature, droid and person the game shipped: 5,067 entries over 532 models and 150 animation packs. The game fetches the catalogue once at boot, behind the select screen. From the console, `await __debug.mobile('rancor', 14)` stands any entry that is on its own model, whether creature, droid, special or humanoid NPC (about 1,100 of them). The body is shaped from the template's collision values and the model's bind-pose box: an upright capsule, or a capsule plus hull balls along a long body, so a krayt dragon blocks along its whole length and a bolt in its tail hurts. It walks and runs at speeds held near its own clips' speeds, so its feet do not slide, and plays its pack's clips by role.

Each one has a brain on the world's simulated clock. It wanders near home, and an aggressive one hunts whatever it is hostile to (the player, fighters, the other side). A defensive one fights back when hurt, a skittish one runs, a passive one (a hologram, a vendor) never fights. It turns on whoever hurt it, its neighbours of the same group turn with it, and it goes home past a leash. Ranged ones spit (creatures) or fire a blaster bolt (droids and people). Allies do not hurt each other. A spawned one plays its incapacitation, falls to the physics a couple a frame, and is taken away ten seconds later. People are stood the same way, in their own clothes: a person on a parts model of their own, and a dressed NPC (a player species wearing the outfit its template names, from the species wardrobes and the wearables only NPCs wear, each piece in its own colours). Armed people hold a weapon off the rack: troopers a rifle, officers and the underworld a pistol, Wookiees a bowcaster and Trandoshans their hunting rifle whatever their job, the combat droids (IG-88, 4-LOM) a gun, and anyone else what their clips hold; a protocol or a surgical droid holds nothing. They fire that gun's bolt. The Jedi, Sith and Inquisitors carry a lightsaber, swing Jedi Academy's swings, and their blades light what is around them as the fighters' do. The planet's own wildlife is the catalogue's too, when it has the species.

The NPC tab (B, then NPCs) lists the whole catalogue: creatures by family, droids, people on their own models, dressed NPCs by species and temper, the specials, and the holograms, pets, vendors and tutorial folk. It has a find box, category chips and a "ready only" switch. Each row has spawn and clear; each group has "one of each" (the first eight that can be stood, stopping at the first refusal and saying it) and clear. The counts refresh in place. Things stand a few metres ahead, on the floor when you are inside a building. The one model the game's own archives lack (the gubbur) is shown greyed as unavailable, and spawning it says why. Two settings in Graphics, Distance and detail: "Spawned creatures and NPCs" (how many may be out, 40) and "Creature animation range" (past it they hold their pose, 160 m).

### Death and ragdolls

Nothing fades when you die: the body falls where it stood and the camera stays on it, with a card offering **Respawn**. The body is a ragdoll (`src/combat/ragdoll.ts`) built from the skeleton itself: every bone long enough gets a capsule from itself to its children, hinged to its nearest ancestor's by a ball joint, and each frame the bones are posed from the bodies so the skin follows; it starts from the pose the last animation frame left, so a creature plays its incapacitation and then falls on from that pose, and a fighter its death clip. A dead creature's or fighter's body lies ten seconds and is gone. Ragdolls touch only what stands still (the ground, buildings, a ship's rooms when aboard) and never the living, vehicles or one another: a physics hook drops those contacts, and the character controller walks through them. `__debug.kill()`, `kill('creatures')` and `kill('fighters')` are the quick way to see them fall. Every joint is sprung towards the pose it died in (a torque applied each frame, stiffening past a limit; the engine's own joint motors and limits fought one another and never settled), so a body sags and folds under its weight rather than into a heap, and once the whole body has been near still for a second its pieces are stopped and put to sleep, so it lies as it fell. The springs fade out over the first seconds, so they shape the fall and then let the body lie loose. The numbers are at the top of `src/combat/ragdoll.ts` and live in the console: `__debug.ragdoll({ stiffness: 80, limit: 1 })` changes them for the next body to fall (the sleep numbers at once), and `__debug.ragdoll()` reads them with every fallen body's speed and whether it sleeps. A creature stood by hand from the NPC tab lies where it fell and is then taken away; the planet's own wildlife comes back somewhere else instead. A creature or NPC stood from the catalogue lies where it fell and is then taken away; the ragdolls of many deaths at once start a couple a frame, nearest first, the rest holding their death pose meanwhile.

### Aboard a ship

Fighting inside a ship's rooms happens in the hull's frame: a bolt fired aboard flies against the room's own walls and is drawn where the hull carries it, a thrown saber flies and comes back in the same frame, the blade's smear stays with the room, and nothing done inside cuts the hull down (the blades, bolts, blasts and Force pushes all leave the ship you are in alone). A hull blown up or removed with people still in its rooms puts them out into the world where it was, with its motion: adrift in space, falling on a planet. `__debug.wreck()` blows up the vehicle you are on or in.

### Skills: Force powers, gadgets, bare hands

The number keys 1 to 6 use whatever is in their slots, and the inventory's **Skills** tab (I) picks it for the class in play: a row per skill with the slot buttons, the choice kept with the character (a Jedi's powers and a Bounty Hunter's gadgets separately). A tap skill fires on the key, a hold skill lasts while it is down, a toggle until the key again.

The Jedi's are the Force powers (`src/combat/forcePowers.ts`): the four the game started with (Jump, Speed, Push, Lightning) and, after Jedi Academy, The Force Unleashed and Jedi: Survivor, Pull (everything ahead dragged to your feet), Grip (hold: the creature under the crosshair lifted and held in the air, choking; let go to throw it), Drain (hold: life drawn out of what is ahead into you), Repulse (a blast in every direction), Slow (the creature under the crosshair at a crawl for five seconds), Heal, Protect (toggle: what hurts you counts for a third) and Rage (ten seconds faster and half again as hard with the blade, paid in health, then a rest). `__debug.powers(['grip', 'pull', null, 'repulse'])` sets the slots from the console, `__debug.creature(8)` stands a creature ahead to try them on.

The Bounty Hunter's are the gadgets (`src/combat/gadgets.ts`): the game's grenades, each after its own flavour text and played the way Jedi Academy plays a thrown charge (an arc from the hand with a little lift, bouncing where it lands, off on its fuse, a blast that hurts and throws everything within its reach, you too when close). The thermal detonator is the strongest, the fragmentation grenade quicker and lighter, the proton grenade made for machines (vehicles and turrets take it three times over), the Imperial detonator the biggest and it stuns what it leaves standing, cryoban freezes everything in it to a crawl for six seconds, glop sticks what it splashes for two seconds and slows it after, the poison grenade and the Kashyyyk bug bomb leave a cloud that hangs for seconds and keeps hurting whoever stands in it. Each flies as the rack's model for it (the weapons pack converts the grenade templates now; before a reconversion, a plain ball). From Jedi Academy come the trip mine (set on the wall or floor under the crosshair within four metres, a red laser out from it; whatever crosses the beam sets it off, you included) and the det pack (stuck where the crosshair is, or thrown when nothing is near; the key again sets every one off; a blast near a mine or a pack sets it off too), and the stim pack mends forty-five health. `__debug.gadgets(['cryoban', 'trip_mine', 'det_pack'])` sets the slots from the console.

Bare Hands is a toggle both classes can carry: the weapon is put away and hidden, the left mouse punches and the right kicks, the game's own brawling clips (`unarmed_standing_ready_jab`, `_lead_uppercut`, `_rear_roundhouse_kic` and kin; the player pack converts them now, so reconvert with `player`) or, without them, Jedi Academy's two punches and its kicks. A punch does a little and shoves a little, a kick more of both, each landing part way into its clip on whatever is within reach ahead of the chest.

### Lightsabers

The game's crafted sabers live under the melee templates (`object/weapon/melee/{sword,2h_sword,polearm}/crafted_saber/`), and the converter sorts them into three classes of their own: lightsabers (one hand: the fast, medium and strong styles), two-hand lightsabers (medium and strong) and double-bladed lightsabers (the staff style, a blade out of each end). Each one's appearance is a blade file (`.lsb`) that names the hilt's model and the blade the client drew from it: its length and width in metres, and the seconds it took to ignite and retract; the converter keeps those in the manifest as `blade`, so a hilt's blade is as long as the game made it, and the tips the hits are swept to move with it.

The blade itself is not the game's sprite: it is drawn as the films have it, a white core inside a coloured glow (two camera-facing ribbons, so it reads the same from every side, additive and never writing depth, so crossing blades add up), and behind it a smear, the surface the blade swept over the last fraction of a second, fading with age, so a blade in motion looks drawn out along its path. A swing sweeps far and the smear is long; walking with the blade out sweeps little, so it shimmers; a still blade has none. `src/combat/saberBlade.ts` has the numbers (the smear's life at rest and in a swing, the core's share of the width, the brightness the bloom catches). The pooled light the blade throws takes its colour, softened toward white.

The rack's Weapons tab starts with **Blade colour**: the game's own 48 (from `palette/wp_lightsaber.pal`, written to the manifest as `saberColors`) as swatches, and a colour picker for any colour at all. The choice goes on every blade at once (the staff's second, the dual style's left, the thrown and orbiting ones) and into the character's record, so it comes back when the character is played again. Other players' blades are not drawn in their colour yet, and hilt styling beyond the game's own hilts is still to come.

## When something fails to draw

A mesh that throws inside the renderer (a broken attribute, a missing uniform) used to abort the whole frame from that pass on, so the water and the doorways flickered whenever it came into view, and since the frame ended before the mouse movement was spent, the view slid on with a momentum of its own. Now the camera spends the movement as it reads it, a frame that throws is caught and logged, and the portal renderer finds the object that fails by drawing the candidates one at a time, hides it, and prints its name, geometry attributes and material (`render: hid an object that fails to draw`); `__debug.passLog()` and the renderer's `broken` list say what was hidden. Paste that line to have the converter fixed for it.

A terminal screen or sign whose flip-book names frames the archives lack draws its first frame, still (the converter logs `flip-book <shader>: base <base>, N of M frames missing`); when the first frame is missing too it draws untextured, as it always did. `npm run swg -- shader @SWG <shader> --retail-only` prints what a shader's forms and its effect say (flip-book timing and frames, the pass's blend and test at its version's offsets, scroll rates, split alpha, how it glows) and what the converter made of it; `materials` prints the same decision per shader as a `surface:` line.

## Vehicles and the garage

Every vehicle is one physics body held up by springs at the corners of its footprint (or by its feet), driven by a spec that says how it handles (`src/vehicles/vehicle.ts`). There are four kinds, and the kind is read from the vehicle's name (`vehicleKindOf`); when a name says nothing the garage guesses and marks it:

- **Podracer** (`podracer`): the fastest thing there is (85 m/s, 125 boosting), a wide drifting turn that redirects its speed rather than scrubbing it, banking into corners, and a **heat** boost after Star Wars: Racer: holding Shift builds heat for about four seconds; at the top the engine burns out and the pod limps at a third of its power for three seconds, and the heat has to fall before it boosts again. The mouse steers it like everything else; **A** and **D** are its air brakes, as in Racer: the nose yaws round hard, the pod banks further and slides wide while they are held. The pods whose animation tables carry them (Gasgano's, Mawhonic's, the light-bending one) spin their engines with their own clips at speed. The prompt shows the heat bar and the speed.
- **Speeder bike** (`speederbike`: swoops, STAPs, BARCs, flash speeders): quick and tight (42 m/s, 60 boosting), bites into turns, banks, a **burst** boost that runs down and recharges, and a hop on Space.
- **Ground** (`ground`: walkers, wheel bikes, tanks, and every animal mount): slow, turns in place, never slides. An animal from the creatures pack walks and runs with its own clips at its own pace under a saddle on its back, and can hop; the creatures pack holds every mount the game sold (the 52 creatures its saddle map lists: banthas, dewbacks, kaadu, cu pa, varactyls, tauntauns, rontos, blurrgs and the rest, `creatures --no-mounts` leaves them out) beside the planets' own creatures, the garage marking which is a mount and which a wild thing. A walker (the AT-ST, the AT-XT, the basilisk, the wheel bike) has an animation table of its own and walks and runs with its clips too; the gallery's `vehicles` conversion keeps them, and the game plays them by speed as it does an animal's. A vehicle's hull collides with everything but the ground: the springs hold it off the terrain from their own rays, and a hull that also met the heightfield dug its underside or its feet into every slope, snagging and jolting there.
- **Flyer** (`flyer`: landspeeders and skiffs as flying cars, gunships and airspeeders as aircraft): looking up climbs and looking down sinks (Space and X do too); the vehicle holds its height over the ground meanwhile and settles back down when nobody drives it. A flying car climbs slowly to 60 m, an aircraft fast to 260 m.
- **Ship** (`ship`: the player ships from the `ships` pack): a first flight model. W builds speed and S bleeds it (no key holds the speed); past a few metres a second the ship lifts off and is flown by hand, free of gravity and of any levelling: the mouse moves a cursor that stays where it is left, and outside the small aim circle in the middle the ship's stick points at it (harder the further out, for as long as it is held there), asking for turning rates about the ship's own axes, and the ship's inertia lets those rates build up and die away over a moment (half a second for a fighter, longer for a freighter: `__debug.vehicleTune({ inertia: 1 })` changes it), so a turn carries on a little after the cursor comes back into the circle; A and D roll it, Space and X pitch it, a flight display shows the aim circle where the ship's nose points, a faint ring for the cursor's reach and the cursor (a pip inside the circle, an arrow from its rim outside it), and it can fly on its back and loop, the camera following it in its own frame so the world turns over with it, a quarter of a second behind so a turn shows the ship swinging and banking against the view; the wheel sets how far back it sits, scaled to the ship, and all the way in is the cockpit view, on the model's cockpit hardpoint when it has one (the hull is hidden meanwhile; Alt looks around from the orbit instead). Near the ground or the ceiling a light hand eases the nose toward the horizon, only while the stick is slack, so a pilot who keeps pushing flies into the ground: the ship stops dead, drops onto its gear, and the rider takes damage by the speed. Below a few metres a second it settles, levels and lands on its gear as a flyer. Fighters are quick, freighters ponderous. The engine glow sits on the hull's engine hardpoints when the model has them (the engines themselves are parts a player fits in the game, so the hulls carry only the sockets), else at the rear. Interiors are converted but not entered yet.

The mouse steers every kind: the vehicle turns toward where the camera looks (A/D steer directly while held), and holding **Alt** frees the camera to look around. Vehicles lean into their turns. A speeder bike rides half a metre off the ground, a flying car the same. Machines float on water at their ride height and mounts swim chest-deep; a vehicle's wake is wider, stronger and less even than a swimmer's, with spray past a brisk pace. Every machine trails dust in the colour of the ground it runs over (the terrain texture's mean colour on a real planet), more the faster it goes, and none over water or in the air, and carries engine glows at its rear that brighten with the throttle and the boost (orange on a podracer, blue on a repulsor drive; dimmer and flickering while burnt out). The rider sits the way the game seats a rider on that vehicle: the riding loop has a branch per rider pose (`loop_riding:vehicle_speeder_bike`, `vehicle_landspeeder`, `vehicle_hover_chair`, the saddle poses of the mounts, `space_sitting` for a pilot's chair), and the converter reads the game's mount tables (`datatables/mount/`: a skeletal appearance to its logical saddle, the saddle to its appearance, the appearance and seat to the pose) into each vehicle's and creature's manifest entry, so a speeder bike's rider crouches over the bars, a landspeeder's sits, a bantha's rides the wide saddle, a ship's pilot sits in the chair; a vehicle the tables lack is tried by its name (`vehicle_<id>`), and the plain `loop_riding` is the game's default saddle. The game's own vehicles seat the rider at the vehicle's origin and the riding clip's root offset puts the pelvis in the seat (a speeder bike's rider hardpoint is exactly its clip's root); a mount wears the saddle the mount tables name, hung on the saddle hardpoint its own mesh carries under one of its joints (the 22 mounts the game let players ride; for the bantha, kaadu, bol and rancor the hardpoint is read from the tables' own `_hue` appearance), and the rider's pelvis sits on the saddle's own `player` point, which is exactly where the game's saddle poses put it, so the saddle and the rider ride the joint together at a walk and a run; a creature the tables list that the game never saddled wears its saddle on the top of its back as its idle stands it (the back, never a neck held up over it), the basilisk seats its rider on its own `player` point, a wild creature's bare back takes the seat, and `__debug.seat()` says which (`seatFrom`) and whether a saddle is worn; a ship's pilot is placed by the cockpit's own camera point: the eyes go there (the B-wing's view takes half of its cockpit file's first-person offset) and the body hangs under them as the chair pose's first frame has it, so in first and third person alike the pilot's head is where the view is. `__debug.seat(right, up, forward)` nudges the ridden vehicle's seat live and reports the pose and its root, for finding a seat by eye; in a ship it moves the body under the eye while the view stays put, and prints a `paste` line for the per-frame table (`COCKPIT_BODY_NUDGE` in `src/vehicles/cockpitSeat.ts`). A fast vehicle can outrun the physics ground being streamed in, so the terrain's own height is a floor under every vehicle. Every vehicle's turning is asked for as an acceleration and scaled by its own inertia (a box of its measured size, never smaller than a bike), so a barge and a swoop right themselves alike, and the springs' ground rays start inside the body so a corner pushed into a slope is lifted out rather than left to tumble. A machine's box is measured from its model when it is spawned, since the pack's bounds can be another mesh's. Both blaster fire and Force Push still shove them.

**B** opens the spawner; its Garage tab lists every vehicle the gallery pack holds (`gallery --only=vehicles`) and every creature in the creatures pack, listed by kind, with a button that stands one in front of you on clear ground (ahead by its own half length and a gap, and further on while an exhibit, a house or another vehicle is in the way, since a box spawned inside something is thrown out of it), a "try it as" choice to drive any model with another kind's handling, and Remove all. Walk up to any side of it and press **E** to ride (within 3.6 m of its edge, so a barge is mounted from its side), **E** again to get off. In the console, `__debug.vehicles('speeder')` lists what can be spawned and what stands on the world, `__debug.spawn('speeder_ab1')` or `__debug.spawn('bantha', 'ground')` stands one ahead of you, `__debug.spawnBox(2, 1.5, 5, 'podracer')` a plain box of that size as any kind, `__debug.mount()` rides the nearest, `__debug.vehicleState()` reports where each stands, how level it is (pitch and roll), its spin and speed and how many corners find the ground, `__debug.vehicleTune({ bank: 0, turnRate: 1.2 })` changes the ridden one's handling live, and `__debug.unspawn()` clears them. A vehicle's rider pose shows in the spawn message; `__debug.player()` names the clip the rig plays.

A ship the `ships` pack gave a fit has an **edit** button beside **spawn**. It opens the ship's page, styled like the Appearance tab: the ship turning on the left on its own renderer (drag turns it, right-drag pans, the wheel zooms, a double-click resets, "wings open" opens them at their own pace), and on the right its paint (the pattern and the two colours from the game's own palettes, where the hull's shaders take them; the TIEs and a few others say their paint is fixed), every slot of its chassis with the components the game allowed in it, grouped by the look each shows on this hull ("Look 2 (115)", "No model on this hull"), the droid (an astromech in the socket on the eight hulls that have one, the N-1 wearing its own droid head; a flight computer elsewhere, which shows nothing), and the systems that change nothing to look at. A pick shows on the preview within a second (new parts are compiled a piece at a time and painted before they are swapped in; paint renders off the main thread) and is kept with the character; **Spawn** on the page stands the ship as edited, as does the garage's spawn button afterwards; closing the page refits the ships of that kind already spawned, in place, and, when it is the ship you fly or last flew or stood out, tells the other players once. **Stock** goes back to the game's stock parts, no droid and the shaders' own colours.

## The gallery (a development world)

`npm run swg -- gallery @SWG assets-private --retail-only --jka=@JKA` builds `assets-private/gallery/`: a flat world under Tatooine's sky with every player house (interiors and all, walk in through the doors), every vehicle and every weapon in rows, each with its name over it, and every animation from both games on a grid of player models six feet apart, sorted by category (SWG's locomotion, pistol, rifle, one-hand and two-hand melee, polearm, unarmed, emotes, reactions and so on; Jedi Academy's stances, each saber style's swings, the specials and katas, parries, jumps and rolls, Force powers, deaths) with the clip's name over each. A clip that moves part of the skeleton only is layered over the idle on its joints, and the game's additive clips (`add_pistol_fire_N` and kin, deltas that would stand as T-poses on their own) are added to the idle the way the game adds them to whatever plays. Play it with `?planet=gallery` or from the galaxy map. Only the mannequins within 12 m of you animate (the rest of the grid is labels), so the grid can hold thousands of clips; `__debug.gallery(30)` widens that to 30 m. `--only=houses,vehicles,weapons,anims,interiors` rebuilds part of it and keeps the rest from the last build, `--limit=N` a sample.

The last section, **Interiors**, is every structure with rooms once each: the converter follows every building and ship template to its portal layout and shows one exhibit per layout (the same cantina stands on three planets, a station in every zone), so the world's buildings, the space stations and the ships with interiors (the yacht, the corvette, the gunboats, the Star Destroyer, the Y-8) stand in wide rows with their names over them, walk-in interiors and all. A layout whose rooms include a lift shaft (a cell named `elevator1`, `reactorlift`, `empelevator`) is labelled **(lift)**, which is how the buildings with elevators are found on the ground. The game's lifts were objects the server spawned in those shafts, and the shafts have no floor at their upper levels, so the shaft's doorways are its stops: stand in it and `E` opens the lift menu, the levels the shaft reaches by the rooms they open into (`src/world/lifts.ts`), and a pick steps you out through that level's doorway. A shaft that opens into another shaft, or one split in two by name (`elevator_e3_up` and `elevator_e3_down`, the Star Destroyer's), shares its stops with it. The same works aboard a ship's rooms. Twenty-odd layouts have shafts: the hospitals (three levels), the civilian association halls, the Emperor's retreat, the Lucky Despot, the Warren, the merc bunker (two shafts, three levels), the corvette and Star Destroyer dungeons, the spires and the yacht among them. The dungeons whose way in was a server object (the Old Republic facility, the tombs and caves, the corvette and Star Destroyer dungeons, the chapter 8 station) stand as hidden rooms with nothing to see outside: within their footprint `E` offers to put you inside, in the room their door would have opened into. In the console, `__debug.gallery()` names the animation slot nearest you and `__debug.anim('name')` plays any clip the player's rig has on the player, so a saber style can be assembled by naming its clips.

## Ship interiors (a start: the physics)

A multi-crew ship's interior is a still room of its own. Its meshes hang inside the hull in the world, so it moves, banks and rolls with the ship, but its physics lives in a Rapier world of its own in the hull's frame, never rotated, with gravity straight down (`src/vehicles/interior.ts`). Whoever is aboard has their body in that world and walks, jumps and stands in the still room; each frame the figure is drawn where the hull's transform puts it. The hull can be thrown about and nobody inside feels it, which is how Garry's Mod's Gravity Hull Designator did it. The rooms come one of two ways: a separate interior model the ship's template names (the YT-1300s, when the archives hold it), or the hull model itself when it is a portal building (the Sorosuub yacht), its rooms converted as cells beside the shell; the game finds either without a new conversion, measures the vehicle's collider from the shell alone (the game's rooms are often larger than the hull around them), and shows a hull's own rooms only to whoever is aboard until the windows are portals (while someone is aboard the hull's glass turns clear so those outside see in; otherwise it is the game's own solid pane), a vehicle's collision is its model's own triangles (a portal building's shell alone, cleaned of degenerate triangles) rather than a box, and the figure no longer pushes the vehicles it walks into (the engine's push against a hull's triangles crashed it; `__debug.pushBodies(true)` turns it back on to check), and the glass casts no shadow, so the sun (and the moon, at night) falls into the rooms through the windows. Aboard, the camera's frame is the hull's: the orbit, its up and the mouse's yaw all follow the room, so the view stays upright however the hull banks. Windows are drawn as the game draws them: a hull's window shader is opaque and reflective (its texture's alpha is the reflection mask, not transparency), a room's window opening is an invisible collidable surface, drawn as nothing and kept for the colliders, and from inside the hull's single-sided window is seen from behind, so the outside shows through; the converter only marks glass-named shaders (by the shader's or its texture's name: glass, window, windshield, canopy, viewport, pane) so the sun comes through them and they clear while someone is aboard, a glassy name covering more than a third of a shell is taken for its skin and kept solid, and `ships --glass=<regex>` marks more shaders for a ship whose windows are named otherwise (`materials --ship=<id>` shows the names); `npm run swg -- materials @SWG appearance/sorosuub_space_yacht.pob` lists every shader a hull uses with what the converter made of it, and `ships --glass=<regex>` names more of them as glass, `--match=yacht` redoing that ship alone. Near a ship with an interior, **E** steps in at the room's entry (a hardpoint naming the way in when the rooms carry one, else a clear spot on the floor of its entry room, or its first room, found under a grid of points with a ceiling above and head and elbow room; the console lists every room's hardpoints on spawning). Aboard, the rooms' own lights from the portal file, the nearest three, shine through the effects' light pool (no new lights, so nothing recompiles), and the shell casts no shadow while someone is aboard, since the rooms lie where its shadow would fall and would never see the sun rather than taking the pilot's seat, and E again steps out beside the hull; falling out of the room (through a door while it moves) drops you into the world with the hull's motion. `__debug.shipDrift(2, 0.4)` sets the hull adrift at 2 m/s spinning 0.4 rad/s with no gravity or righting, to try the room while it moves; `__debug.shipDrift(0)` brings it to rest. A ship with a bridge among its rooms is flown from it: at the front of the bridge **E** takes the controls (the figure stands there, still in the room's own physics, while W/S and the mouse fly the ship as from a seat; the view is from the bridge in first person), and **E** again lets go, in flight too (the ship carries on as it was; there is no landing place in space). Still to come: the room's windows as exits in the portal renderer so the world shows through them; the relay carrying who is aboard what; the lifts and terminals the server spawns into the rooms.

## Ship attachments and cockpits

A ship's client data (`clientdata/ship/client_shared_<ship>.cdf`, named by its template) says what hangs on the hull beyond its own mesh, and the `ships` command reads it: the wings (objects of their own, each standing at its own place in its parent's frame and turning about its own Z; a wing's own client data can hold more wings, as the B-wing body holds its two foils); the carriers the client keeps beside its forms (turret bodies and barrels, radar dishes, the Black Sun wing structures, the Hutt wing pieces); "engine on" appearances shown while the drive runs, or while boosting for a booster's; the hardpoints its thruster effects sit at, which place the engine glows, else any hardpoint named for an exhaust; and the effect and smoke of each damage band, kept in the manifest for later. The engines, guns and boosters are attachments of their own (`object/tangible/ship/attachment/engine/shared_xwing_engine_pos_s01.iff` and the like), and which ones a ship carries as sold comes from its chassis tables (`datatables/space/ship_chassis_<chassis>.iff`, each slot's looks as `attachment:hardpoint` lists): each slot's most common look, leaving out the `modification_*` slots (one reward look each, the X-wing's side strakes among them), so the X-wing has one gun per hardpoint and the Jedi starfighter its own engines and guns. Every part's own client data is read in turn, and a hardpoint it names is looked for on that part, then on what already hangs under it (a turret's barrels are on its body), then on the whole ship; the manifest writes the lot as a tree, 596 parts over the 63 ships (`yt1300_engine_none`, the empty engine slot's stand-in, is written but not shown while the slot is filled). Each part is turned the way its hardpoint faces, and its own glow hardpoints place the engine glows (the client data's thruster points, then any exhaust, then any numbered engine hardpoint, when there are none), sized by the hull's height. A ship's hardpoints live in its `.lod` appearance, which the converter now reads through (`materials --ship=<id>` lists them). The cockpit file the template names (`cockpit/<ship>.iff`) gives the frame drawn around the pilot, converted as `<ship>_cockpit.glb`; it is authored in the ship's own space, so it hangs on the model at its origin and lands in the canopy by itself, and its one hardpoint, `camera`, is the game's own first-person eye: that point with the file's first-person offset is where first person looks from, hovering and flying alike, so the view never moves at lift-off. The game never drew a pilot in a fighter, so the body hangs under that eye as the chair pose has it and sits on the cushion one downward ray finds in the frame's triangles when the ship spawns (the console's `garage: <ship> cockpit:` line gives the eye, the seat and how far the body was moved); in first person it rises no more than 0.10 m, which keeps the view clear of the collar. It shows while someone is at the controls, seen from outside through the canopy, which clears like a hull's windows, and in first person the view sits inside it and the hull stays in the picture (`__debug.cockpitFrame(right, up, forward)` nudges the frame and its eye live, for checking). A gun's hardpoint is never taken for a seat or an eye (the gunboats' `pilotmuzzle1` is a gun), and a ship without a frame, which is always one with rooms, is flown from its bridge; seated in one, the rider is not drawn. A ship with rooms has a bridge instead of a frame. Zoomed all the way in, the view is locked to the hull hovering as in flight; **Alt** looks round from the same eye in the ship's frame, starting at the nose (a bridge pilot looks from their own eyes), and the wheel zooms out from there in steps sized to the ship; each engine leaves a ribbon of exhaust behind it, longer the faster it goes.

What a hull can be fitted with comes from the game's own tables, not from names: each slot of its chassis (reactor, engine, shields, armour, capacitor, booster, droid interface, cargo, modifications, guns, launchers, countermeasures) takes the components whose class the chassis names, and the hull's looks table says which model each shows there, so an engine or a gun has up to seven looks on the X-wing. The ship as sold carries each slot's stock component, from the look the most of its components show: the X-wing has its Incom Advanced Blasters, one per hardpoint, and no side strakes, which were a reward. It fires that gun's own bolt. The fighters with an astromech socket (the X-wings, the Y-wings, the Jedi starfighter, the N-1, the ARC-170 and the V-wing) take R2 to R5, the N-1 as its own droid head; the rest take a flight computer. 41 hulls have paint the game let players change, a pattern and two colours from the game's palettes. The models wear each shader's default pattern and colours, every pass baked, as the client drew a ship nobody painted.

A ship converted with its fit is built from the fit its character keeps (the stock one until it is edited): the manifest's tree without its stock components, then the fitted components' own parts, hung by hardpoint name over the whole ship in as many passes as they need (the Hutt heavy's booster hangs on its engine part; a part nothing carries waits and is named in the console, never put at the origin), each with the parts its own client data hangs on it (the ones it does not carry itself hung by name after every fitted part is on), and the droid in the astromech socket as its own model at rest, sunk so only its dome and the top of its body show (the N-1 wears the game's droid head); an empty slot's stand-in (the YT-1300's engine cover) shows while the slot is empty and comes off when it is filled, on a spawned ship too. A ship already spawned changes in place when its fit changes, one change at a time: the new parts are loaded, compiled in their own materials and then in the ship's paint, and painted, in a group of their own first, then swapped in one step, and the guns, the engine glows, their trails and the heat shimmer follow the new parts; the colliders stay as spawned. Paint is the game's own: until a ship is first given custom paint it wears its model's materials (the stock bake); then it gets copies of its paint materials, compiled before they go on, and each paint shader's texture is rendered from the game's recipe in a worker, off the main thread (a big freighter's takes most of a second), and swapped onto the copies when it lands; a glowing shader's glow is split from the painted colour as the converter splits it. Going back to stock puts the model's materials back. `src/vehicles/shipFit.ts` resolves a saved fit against the hull (anything the pack no longer has, or a slot does not take, falls back to stock with a note), `shipMounts.ts` hangs and swaps the parts, `shipPaint.ts` and `paintWorker.ts` paint.

## The map (M)

**M** opens the map window, with the galaxy (every world, and the places on each to jump to) as its second tab. Its first tab is where you are. On a planet it is the client's own map of it (`npm run swg -- maps @SWG assets-private --retail-only` writes `texture/ui_map_<planet>.dds` into every converted planet pack as `map.png`, with `map.json` giving the width of ground it covers, from the pack's terrain; without it the ground's extent is a grid; the same command also writes `galaxy.json` beside the packs, every planet's ground width and the game's own thirty shuttle routes with the price of each, which the galaxy tab draws as the lines between the systems), with the cities as rings the size of their reach, the starports and shuttleports, and every other place once the map is close enough to read them, and you as an arrow the way you face, with your height under it when flying. Drag pans, the wheel zooms about the cursor, a double click centres on you, and a click on a place jumps to it. In space the tab is the zone in three axes: a grid at the zone's plane, every rock as a dot, and from the zone's own pack its stations by the game's own names, its hyperspace points, its launch point, its asteroid fields and its nebulae as faint shells in their own colours, each kind a layer with a box to switch it off and the client's own zone map icon beside it; the ships are cones the way they point, yours in orange with a dashed line down to the plane. Left-drag turns, right- or middle-drag slides, the wheel zooms toward the cursor and a double click centres on a mark. The view follows your ship until you slide it, and **F** or the Follow button brings it back. Resting the cursor on anything names it, and a click picks it: the panel beside the picture gives the game's own description, how far off it is, how big it is, how many docking lanes its model has, a Centre button and, at a ship's controls, **Hyperspace…**, which opens the System Map on this system. Other ships will need a ping to show later; for now every ship in the zone is on it.

The window's other tab is the **galaxy**: a disc of stars with every system we have standing at its canon grid square, turned, slid and zoomed with the mouse exactly as the space map is, with **Reset view** to frame it again. Where the systems hang is ours and not the game's — the archives hold a picture of the galaxy but nothing that places a world on it, and only the shuttle fares say which worlds are joined — so a system placed by us carries a star beside its name and says so when it is picked; the lines between them are the game's own shuttle routes, read out of `galaxy.json`. Each system wears the picture of its world that its own orbit's pack carries, or a tinted globe where the archives have none. A ring marks the system you are in. Click one and the panel beside the map gives each of its worlds: what it is, its own ground map with its cities and ports dotted on it, its cities, ports and landmarks to jump straight to (a dot jumps as its chip does), **Travel** to go there, and, at a ship's controls in space, **Hyperspace to orbit**, which starts the same jump the System Map does (Talus and Rori arrive at their own stations in their neighbour's system; Mustafar has no orbit and says so). **List** puts the old card list back for reading and for the keyboard.

## Adrift: on foot in space

Out of a ship in space (E beside it, carrying its motion) there is no down. The mouse turns the body itself, yawing and pitching it in its own frame through any angle, **Z** and **V** roll it, and the view rides behind however it is turned (Alt looks round without turning it). The keys are thrusters: **W** and **S** ahead and back, **A** and **D** sideways, **Space** and **Ctrl** up and down, each adding to a momentum that is kept until **Q** brakes it off, capped at 60 m/s; a hull or a rock met on the way stops the drift into it. E beside a ship boards it. For now anyone can do this; it will want a jetpack to move and a helmet to live.

## Speeders on the ground

A speeder's springs are stiff and well damped and the ground under it is a hard floor: a corner that has got under the ground is lifted out at once, and the speed it went in at is a hit, so a hull cannot sink into a slope the way it used to. A speeder bike or a landspeeder does 65 km/h flat out and 75 on the boost (a pod racer keeps its 300). Off the ground, past its cushion, the repulsor still carries half the machine's weight and holds the fall to a walking pace within a few dozen metres of the ground, so a ramp gives a glide; it never carries more than the weight, so nothing flies. A machine on its back for more than a moment throws its rider (a little hurt), and **E** beside a machine on its back turns it upright rather than climbing on. The pod racers' seats: the game seats a rider at a pod's authored origin with the riding pose's own offset, and for the pods left unfinished that origin is nowhere near the cockpit, so when the pelvis would land outside the pod's own box the rider sits in the cockpit guessed from the mesh instead (the pod's far end from its origin, half a metre under the mesh's top there); the console says which it did for each pod and where, and `__debug.seat(dx, dy, dz)` nudges a seat live to find a better place by eye.

## Hovering, and the way into space

A ship not yet in flight hovers as a VTOL: it holds still until the throttle opens, the view's tilt does not lift it, **Space** and **Ctrl** (or **X**) raise and lower it, and **A** and **D** slide it sideways; the mouse still turns it, and zoomed into the cockpit the view turns with the hull (up and down do nothing there; **Alt** looks round). At a bridge's controls, hovering, the mouse's sideways movement turns the hull. **W** builds speed and past a few metres a second it is in flight, where the mouse's cursor flies it (above) and A and D roll. Flown into something solid (a building, an asteroid, a station) the hull bounces off with most of its speed gone and is hurt by what it lost, and for a moment the contacts, not the throttle, have it, so it comes clear rather than being driven deeper in; the ground ahead on the course counts as ground coming up, so the nose eases over a slope, and a hull that ends up inside the ground (flown sideways into a hillside) is a crash, lifted back onto the surface. The way into space and back is the ship menu, **P**, for whoever is in a ship (at its controls, riding a fighter, or aboard as a passenger), since E aboard a multi-crew ship takes and leaves the controls and steps out. Near the top of a planet's sky (above 1100 m over the ground) the prompt says the ship is at altitude, and the menu's **Go to space** takes it into the planet's space zone in flight; in space the pilot's **Land on …** brings it back 700 m over the planet's spawn, flying, and anyone's **Eject to …** goes down on foot, the ship left behind. A ship with rooms crosses with its crew: whoever is aboard stands in the new hull where they stood in the old, at the controls if they were there (the relay does not carry this yet, so other players make their own crossing). **Dock** is in the menu for later: two ships alongside in space and a way across. The galaxy map lists each orbit too, arrived at in the ship last flown (else an X-wing). Every panel (the menus, the map, the inventory and spawner) drags by its header and stays where it is put, and the screen round it is clear, so a graphics setting is seen as it moves.

**Hyperspace.** In space the ship menu's **Hyperspace…** row (the pilot's) opens the **System Map**, a page of the ship menu closed by the same key: every space system down the left (the nine orbits, Kessel, Ord Mantell and Deep Space; the one flown in marked, and one not yet converted for hyperspace greyed with the command that converts it), the picked system's hyperspace points by the game's own names, its stations and, for a planet's orbit, its launch point (where a ship climbing out of the planet's sky comes out) in the middle with how far each is from the ship, and on the right the one picked, with the game's description, how far it is and **Hyperspace**. The arrows pick (up and down the points, left and right the systems) and Enter jumps. A jump counts down from five while the ship flies on (the menu's row reads **Cancel the jump** meanwhile, the Escape menu holds the count, and the inventory and spawner keys wait until the jump is over); then the ship vanishes for everyone else, the view goes behind the ship, P, M and N do nothing and the prompt says "jumping" while the game's own streaks play and a tunnel of streaking light closes round the ship; E works only inside the tunnel, aboard a ship with rooms (see below). Inside it the ship is carried there, within the system or to another one, whose world loads behind the tunnel while it runs (at least four seconds); aboard a ship with rooms you can let go of the controls with E and walk about meanwhile, ride its lifts and take the controls again, but not step out (whoever walks out of the door is put back at the entry). When the far side is ready the tunnel opens ahead, the others see the ship arrive, it brakes onto the arrival facing the nearest station or landmark, and control comes back. A place in the same system whose arrival is less than a kilometre off is refused with the game's own "You are already at that point." Points marked "made up" are ours (Kessel's and Deep Space's, whose places the game kept on its servers). In Kessel, Ord Mantell and Deep Space the menu says "In Kessel System" and so on, and Land and Eject are greyed: there is no planet below. Arriving in a space zone from the galaxy map comes out at its arrival point facing its landmark (a system with no pack yet says so on its card, with the command), and a character saved in space comes back where it was.

`npm run swg -- space @SWG all assets-private --retail-only` converts the space zones (`space_tatooine`, `space_naboo`, `space_corellia`, `space_dantooine`, `space_lok`, `space_endor`, `space_dathomir`, `space_yavin4`, `space_kashyyyk`, and three systems that are no planet's orbit: `space_light1` Kessel, `space_heavy1` Deep Space and `space_ord_mantell` Ord Mantell; one at a time by name), each into `assets-private/<zone>/`: the station its station table places (drawn as the faction station the client has for that system), every asteroid of its asteroid fields (each field scattered from its own seed through its style table, along a spline where the table gives one, capped at 400 a field), the planets and moons its terrain file hangs in the sky (`space.json`, with each one's surface texture; the game draws them as lit spheres far out, following the camera), and its sky from the same terrain file: the six-sided nebula skybox it names, its two parallel lights and ambient (the main light's direction is fixed; there is no day in space), its clear colour, its star field (tens of thousands, all around), its star sprites (the suns and their glows, hung where the file turns them) and its dust (motes fixed in space within a few dozen metres of the camera, so speed shows against nothing). In the zone there is no ground at all, no gravity and no fog; placed objects load out to three times the setting's reach; ships fly at twice their planetary speeds with no ceiling and never land. `__debug.sky()` lists the sky's parts and lighting, and `__debug.sky('skybox')` (or `'dome'`, `'stars'`, `'dust'`, `'sprites'`) toggles one to see what it contributes. The zone's stars hang fixed in its sky (they are quads turned once towards the camera, not screen-upright sprites, so a roll no longer rolls their glows), and the ground sky its environment file carries — a sun, two moons and two planet pictures, the same 348-byte file copied into all 23 of them, and none at all for the orbit added last — is never built: `__debug.sky()` counts it as `envBodiesLeftOut`. Which star is the zone's sun is ours to choose, not the game's, since the file's own light points as much as 119 degrees away from any star: the brightest by the lens flare's ranking, with a star within six degrees of it folded in as a companion that flares beside it and takes no light of its own. The main light, the shadows, the lit side of every planet, the flare and the god rays (new in space, and stopped by planets and by stations kilometres off) all come from that one star. `__debug.suns()` shows the choice and `__debug.suns({ rule: 'disc' })` compares it with the largest disc. Each zone's `space.json` also carries its hyperspace points, its stations' names, its arrival and the jump scene, which the Hyperspace paragraph above flies. Made up here, because the game kept them on its servers: Kessel's and Deep Space's hyperspace points, Deep Space's asteroids and wreckage, and a Star Destroyer hanging broadside a couple of kilometres from Deep Space's first point (the exterior only: scenery with collision, never boarded); Ord Mantell's one point is the Nova Orion point the game gave the same sector. NPC starships patrol near the stations, the hyperspace points and the arrival lane and fight by side (Imperial, Rebel, Black Sun, pirates), and the NPC tab (B) stands them by hand; every number of their fight is invented, kept in `src/space/shipStats.ts`, `loadout.ts`, `npcBrain.ts` and `roster.ts`. The pack also carries the zone's nebulae with their colours and their lightning, its asteroid fields' shapes, its stations' docking lanes, drydocks and hangar mouths, and the sound a dock plays, which the space map draws. The nebulae are drawn as well: each row becomes a cloud of glowing or misty sheets in its own colours, the far ones pulled in toward the camera so they show past the far plane and fade before it, half of them turning to face you and the rest fixed in the sky. Fly into one and a haze comes up around you, the lens flare and the god rays dim with how deep in you are, and in the rough ones the view shakes by the row's own jitter. Lightning strikes on each nebula's own clock, read off the wall clock so everyone on the relay sees the same strikes at the same moments, drawn with the game's own lightning appearance and its two end effects; a strike that ends on your ship takes shields and armour off it at a quarter of the tables' numbers, which the Space section of the settings turns off. How many sheets there are, how big they are, the pull-in, the haze and when lightning strikes are ours, not the game's, and `__debug.nebulae()` moves every one of those numbers live. Not done: the stations' interiors, landing at a station.

## Ship guns, targets and wings

A ship with weapon hardpoints has guns: **click** fires them in turn (a gun part's own muzzle hardpoint when it names one, else the mount it hangs on). The bolts are the game's own. The `ships` command reads the projectile table (`datatables/projectile/projectile.iff`: each projectile's particle effect, the effect played when it fires and the ones played where it strikes, per surface, through client effect files) and the weapon table (`datatables/space/ship_weapon_components.iff`: each gun's projectile, speed and range), converts every bolt effect and hit effect into the pack's `particles/`, writes the tables as `ships/projectiles.json`, and names in each ship's manifest entry the gun it fires (the blaster named for its family, `wpn_awing_blaster`, `wpn_tiefighter_basic`, `wpn_z95_blaster`; else the light blaster, green for the Empire's ships). Nearly every blaster fires at 600 m/s to 512 m. A bolt carries the ship's own velocity on top of its muzzle speed, so it never lags the ship that fired it, and lives its range over its speed. Its look is the projectile's effect (a streak 19 m long in red, green or blue), a particle effect carried along with the bolt: the particle player now honours the client's local-space emitters (particles that live in the emitter's frame and are put into the world only when drawn) and can place passing effects (a bolt, a hit) that play from their start when placed, are never put to sleep for distance, and are dropped once they have played out; where the bolt strikes, the table's hit effect (armour panels and sparks on metal) is stood on the surface. A pack converted before this has no `projectiles.json`, and the bolts are drawn as a blaster's. A ship converted with its fit fires from each gun what that gun's chassis slot holds (the component's own row of the weapon table: its bolt, speed and range), so a gun fitted with a green-bolt blaster fires green bolts beside red ones; a gun on the hull itself fires the first weapon slot that fires bolts, and a missile launcher or countermeasures slot fires no bolt. The lead is worked out with the speed of the gun that fires next.

Bolts hurt ships: a vehicle's colliders are known to the bolts, a hit takes from its hull (the prompt shows the hull once it is dented, and a pilot whose ship is hit feels a jolt), and a ship with no hull left blows up as a vehicle does. In flight the guns lead a target. **Tab** cycles the ships ahead (within 70° of the nose and 2.5 km) by how far off the nose they sit, and with none chosen the nearest to the nose is taken; the HUD boxes the target (kept at the screen's edge when it is off it) with its name, range and hull under it, and draws the lead reticle where the guns must point for a bolt fired now to meet it, joined to the box by a dashed line: the meeting is worked out in the ship's own frame (the target's place and velocity relative to the ship, the bolt's speed over the ship's), the earliest time a bolt can be where the target will be. In flight the guns swing toward the cursor inside the aim circle, every gun's bolt crossing under it at the target's range, and take the lead exactly when the cursor sits on the reticle (the circle and the reticle turn green), never more than 12° off the nose; hovering, or with Alt held, they fire at the lead while it sits within 12° of the nose, else along it.

The game's fighters carry wings that open in flight. Each wing stands where its client data places it (the PSOR place, mirrored as the model is, or a hardpoint of the part that lists it: the B-wing's foils hang on its body) and turns about its own Z by its angle over its own time, so the X-wing's foils take three seconds, not a quarter of that. Everything hung on a wing hangs under it: the engines, boosters and guns ride the foils, the glows and exhaust ribbons leave from the engines wherever they stand, and the bolts leave from the muzzles as they stand at the shot; the hull's colliders under a wing move with it. Wings open whenever a ship flies with room under them (on a planet a wing that swings below the belly waits for that much air and half a metre, with a metre's band: the B-wing's 15 m) and close on landing, and a chassis's `wing_open_speed_factor` (0.95 on the X-wing, advanced X-wing, B-wing and V-wing) is taken as the top speed's share while they are open; `__debug.wings('threshold')` shows the other reading (open only under that share of top speed). The pilot opens and closes them with **U** at any speed; the choice holds until **U** again or leaving the seat, and a wing that swings below the belly still folds on landing. A ship is centred side to side on the meshes that do not ride a wing, so it turns about its hull: the B-wing about its cockpit pod, not a point out along its flat wing. A large ship takes a few seconds to appear, since everything it draws is compiled before it is shown (the console says how long when it is over a second). Other players' ships open and close their wings as their pilots' do. `npm run swg -- dump @SWG clientdata/ship/client_shared_xwing.cdf --hex` shows the layout.

On a planet a ship can be set down. Stopped with its engines running it holds the height it is at, and **Ctrl** and **Space** fly it down and up from there a metre and a half a second; hold **Ctrl** once it is at the bottom of its hover band, or press **J** to cut the engines, and it comes down, tilts to the ground under it and rests on the point the game marks beneath half the hulls (never more than 0.3 m off the ground, and on its underside for the hulls that carry no such point), held still with its springs off and its wings folded. A slope steeper than 20 degrees is refused, with the reason in the prompt; arriving faster than 8 m/s is a crash, which hurts the hull and the pilot as flying into the ground does, and a ship whose engines are out is measured by its whole speed, so cutting them in a fast cruise is a crash rather than a landing. **W** or **Space** lifts it off again. Standing inside a hangar room (the Theed and Massassi hangars, the Imperial outposts' bays), a ship flown from a cockpit is stood on that room's floor rather than on the ground under the building, turned along the room, and while it is in a room it takes the floor and the collision the room's own bodies take, so it can hover about inside without snagging on the shell. Ships with rooms of their own still spawn outside. How high a ship rests, the slope it will take, how long it settles and what counts as a hard landing are ours, and `__debug.landing` tunes all of them live; `__debug.landing({ rule: 'springs' })` puts the older hover-only ride back. Other players see a landed ship standing still.

## Playing together (a start)

`npm run relay` starts a relay (`server/relay.mjs`, port 8787, no dependencies: a WebSocket server on Node's own http module) that passes every player's place and pose to every other. In the game, the Escape menu's **Multiplayer** page takes the relay's address (`ws://host:8787`, or `?server=ws://host:8787` in the page's address) and connects; each other player is shown as their own character, of their species, standing where they stand and playing what their rig plays (walking, running, crouching, seated on a vehicle, an emote or a dance), with their name over their head, gliding between the relay's ten updates a second, and only while on the same world. The vehicle or ship a player is on goes with them: the others draw it (the model, with no physics) where it is and how it is turned, with the player seated on it in the pose it seats them, flying it from its rooms, or aboard as a passenger, and a figure aboard a banked hull or adrift in space is turned as it is there. A winged ship's wings open and close for the others as its pilot's do (a relay started before this drops that, and the wings then follow the ship's speed). A ship in a hyperspace jump is hidden from the others from the jump's start until its tunnel opens, and then shown where it comes out without gliding across (a relay started before this drops that, and the others then see the ship vanish only when it changes zone). A ship's components, droid and paint go with its pilot's hello when the Edit page closes or they change ship (one hello, never while a colour is being dragged), and the others hang the same parts and paint it the same, in place, without rebuilding it; a relay started before this drops the fit, and the others then see the stock ship. A player's look goes with their hello (the shape sliders, height, colours and outfit), so the others draw them as they are. Nothing is kept on the relay and nothing is checked: no combat between players, no bolts or damage across it, no chat yet. Behind a reverse proxy with TLS the address is `wss://`.

To play across a home network from the machine with the assets: run the relay (`npm run relay`, port 8787) and the dev server listening on the network (`npx vite --host`) on that machine, find its address (`ipconfig` on Windows, the IPv4 of the wireless or ethernet adapter, say `192.168.1.20`), let Node through the firewall when Windows asks (both ports), and on the other machine open `http://192.168.1.20:5173/?server=ws://192.168.1.20:8787` in Chrome. That machine downloads the converted assets from the first as it plays (a few hundred megabytes the first time; the browser caches them), and the two see each other once both are on the same world. The first machine's own game connects from the Escape menu's Multiplayer page with `ws://localhost:8787`.

## Vehicle damage

A vehicle's hull takes damage from a hard hit (the velocity lost in one step beyond what braking or a slope can take off) and from bolts, a blaster's or a ship's: sparks and a jolt to the rider on the hit, smoke below two thirds of the hull, heavy smoke, sparks and a limp (about half the power) below a third, and at nothing it blows up and throws the rider off. The prompt shows the hull once it is dented. Hover kinds pitch and roll to the ground a length ahead and behind, so a rise ahead lifts the nose before the hull meets it, and speeder bikes ride a little higher than they did.

## The picture's effects

The Graphics menu's **Effects** page is one master switch (on by default) with a switch, and where it means anything a strength, for each effect under it. With it on, the frame is drawn into a target of the game's own — half floats, so light brighter than white survives, a stencil for the portal renderer and a depth buffer the effects can read — and reaches the screen through a chain of passes in a fixed order: the picture is **cleaned** (a pixel that is not a number becomes black before any blur can spread it), the sun's **god rays** are scattered into it, the camera's movement **smears** it, the bright parts **spill over** (the engine glows, the bolts, the suns), the **output** pass applies the exposure, the tone curve and the colour space exactly once, and the **edges are smoothed** at the end. With it off the frame is drawn straight to the screen as before, multisampled, and none of the passes run.

Nothing in the chain ever writes back into the scene's own target, and that is the whole point of it: a pass may read the frame's depth only while it is drawing somewhere else, and before this the god rays and the speed blur each sampled the depth of the very buffer they were writing into, so the browser threw the draw away and said nothing — the rays never appeared at all, and the blur and the bloom went missing whenever the sun was off the screen. `__debug.fxCheck()` draws one frame asking the driver for an error after every step and names the step at fault; it should answer `{ clean: true }` both with the sun on screen and with it behind you.

The blur is the camera's: each pixel's point is found in the world from the frame's depth, projected with the last frame's camera to see where it was on the screen, and the colour averaged along that movement, so the ground rushing under a ship at speed and a wall sweeping past in a turn smear in proportion, the far sky hardly at all, and nothing within a few dozen metres of the camera (the hull flown, a cockpit) at all. Its strength is a slider (0.35 by default, a film's shutter at 60 frames a second; the smear is scaled so a slow frame is not a longer one), and it is capped at a few percent of the screen. Things that move on their own smear too: the game lists them each frame (the player and what they ride, vehicles, creatures, fighters, mobiles, other players) and a velocity picture of their moving parts is merged with the camera's reprojection of everything else; what the camera follows stays sharp at any size.

**God rays** come from the same depth: the sun's place on the screen is found by projecting its direction, and each pixel marches towards it summing the open sky along the way (depth past two and a half kilometres counts as sky) with a decay, so light streams past a tree, a wall or a hull that stands against the sun and nothing is drawn twice. They come before the blur and the bloom, so the light smears and spills as the sun's does, take the day's sun colour, fade towards the horizon and as the sun leaves the screen, and are off at night and in space. Their toggle and strength (0.6 by default) are on the Effects page.

The edges are smoothed by FXAA rather than by multisampling: the renderer resolves a multisampled target at the end of every render call, and the portal renderer makes a dozen of those a frame, which took the frame rate from 144 to 11. A pixel that is not a number (a material that divided by zero somewhere) is black on the screen, and the bloom's blur used to spread one into a black box the size of its coarsest level whenever the object was in view; the first pass of the chain makes such pixels black before anything else sees them, and `__debug.blackBox()` names the object under one so the material can be fixed.

Turning Effects on or off no longer costs a pause. Tone mapping is applied by a different program depending on whether the frame is drawn to the screen or to a target, so every material has a variant for each, and moving the switch compiles the other set in the background while the frames keep drawing the old way — a notice over the picture counts the objects — and the picture changes over only once the programs are linked. Settings kept from before the switch existed are carried over: a speed blur left off stays a motion blur left off, at the strength it had.

From the console, `__debug.postfx()` lists every pass with its setting, whether it drew last frame and why not, what it cost and which pass drew to the canvas; `__debug.postfx({ godRays: false })` forces one on or off (`null` hands it back to the settings); `__debug.fxTiming(true)` and then `__debug.fxTiming()` times every step on the GPU against its budget; `__debug.fxView('linearDepthHalf')` shows one of the pictures the effects work from — the distance to each pixel, the direction each surface faces, the mask of the player — instead of the picture, and `__debug.fxView()` puts it back; `__debug.fxWarm()` compiles every pass's shaders again, and a second call should say none were needed.

**Wet ground.** Wetness rises while it rains and falls slowly in sunshine and wind, and every world material, the ground and the lakes read it: surfaces darken by how porous they look, turn glossy and reflect the sky at a low angle, flat ground near you gathers puddles that the rain rings, lakes ring too, and snow settles on what faces up. The rays that keep the rain off covered ground also tell the shading what is sheltered, so a floor under a roof stays dry and a wall is judged by the open air beside it. Rooms, ships, people and what they hold are never weathered. It is all compiled in once and moved by uniforms, so the weather never recompiles a shader; "Wet ground" in the weather settings turns it off.

**Effects to do**, roughly in the order they would pay off:

1. Shoreline foam from the water mask; a lit blade's glow on the ground is the `bladeGlow` pass now, and the bolts' light still comes from the pooled lights.
2. Limbs that blur on their own: moving things smear by their root's motion only, so a swinging arm, a ragdoll's fall and a peer's roll do not (a previous-bone texture per skeleton is the sketched fix).
3. The sunlit patch where a doorway's beam lands: the light shafts already work it out, and its gain waits at 0 until it has been judged by eye.

## Normal maps

Every converted model carries its normal map: the converter reads the shader's `CNRM`, `NRML` or `DOT3` slot, unpacks the game's compressed layout (x in the alpha, y in the green, z rebuilt; an ordinary RGB map is left as it is) and writes it into the GLB as the material's normal texture; the game's maps are Direct3D's, green down, and the glTF loader's own flip of a map without tangents turns them the renderer's way up (`__debug.normals(1, -1)` is that; `(1, 1)` flips every normal map in the world and on the character the other way, to check by eye on a wall's edges), and the Graphics menu has a strength slider for them (1 as the game has them). Packs converted before this carry none: run the conversion commands again (the planets' packs, `species`, `wardrobe`, `weapons`, `ships`, `creatures`, `gallery`) to get them. A character's head and body take theirs from the live recipes as well, since the age slider picks among them.

**Common problems.**

- *Something is missing or old after pulling*: run `npm run swg -- status assets-private`; converter changes need the pack reconverted, and the table under **Converting your own SWG install** says which command. Ships: `npm run swg -- ships @SWG assets-private --retail-only` (`--match=yacht` redoes one ship and keeps the rest).
- *A hitch the first time something appears*: a shader compiled on a live frame; the console says `shaders: N compiled during play`. Whatever appeared should be warmed up behind the loading screen or given to the compile queue (see `compileObjects` in `src/world/world.ts`). Adding or removing a light recompiles everything: lights are pooled (`effects.flash`) and never added at runtime.
- *`RuntimeError: unreachable` then `recursive use of an object` on every frame*: the physics engine panicked and its world is poisoned until reload. The known cause was the character controller pushing a dynamic body with a trimesh collider (now off); a new one means a bad trimesh or an unsupported shape pair.
- *A model's hardpoints, cells or names do not match*: GLTFLoader strips `:` from node names and keeps the original in `userData.name`; read names through `hardpointName()` and `cellIndexOf()`.
- *A ray or query finds nothing right after building a physics world*: the world must step once first.
- *Nothing is heard at all*: `__debug.audio().state` tells the causes apart. `suspended` means the browser has not let the context run yet, which one click on the world fixes. `running` with voices listed and `master` above 0 is a routing or volume problem. `bank.available` false means the sound pack is not converted: run `npm run swg -- sounds @SWG assets-private --retail-only`. `recent` says why each of the last dozen sounds did not play.
- *The world is silent but the interface clicks*: `__debug.ambience()`. An empty `beds` list with rows in `sky().mix` means the planet's sky pack was converted before the environment tables' ambient sounds were read (`npm run swg -- sky @SWG assets-private --retail-only`). `sources.placed` 0 with `pack` `none` means the planet's places have not been converted (`npm run swg -- sounds @SWG assets-private all --retail-only`), which leaves the area's beds playing and the town's own crowds and cantina bands silent. A bed with a weight and nothing playing is either a full pool (`audio().waitingLoops` counts the voices waiting, which are the non-positional slots in `VOICE_TUNE.flat`) or a sound the bank has no entry for, which `ambience().bedsMissingFromBank` names. `sources.missingSounds` says the same for the town's own emitters.
- *Which shader is a window, and what did the converter make of it*: `npm run swg -- materials @SWG --ship=<id>`; `dump @SWG <file> --strings` shows a file's readable strings when its layout is unknown, and `--hex` every chunk's bytes with the floats they would be, for decoding the numbers between the strings; `template @SWG object/…/shared_x.iff` shows an object's parameters through its base chain.

## On assets

The original SWG client assets (the `.tre` archives) are copyrighted by Sony Online Entertainment / Lucasfilm and cannot be redistributed, so they will never be committed to this repo. A private build could load them from a local install via a converter, but a public site cannot ship them. The plan instead:

- **CC0 low-poly packs** that already match the flat-shaded style: Kenney, Quaternius, Poly Pizza. Good for props, buildings and vehicles.
- **Mixamo** for a rigged humanoid and a large animation library (free with an Adobe account, licensed for use in games). The X Bot stand-in in this repo comes from the three.js examples.
- **Sketchfab** fan-made Star Wars models under CC-BY where the licence allows it, credited in a `CREDITS.md`.

GLTF is the loading format for all of it.

## Converting your own SWG install

Everything the game shows from the original client (planets, buildings, ground textures, creatures, the player character) is converted from a locally owned install into `assets-private/`, which is git-ignored and never committed. The converter is `tools/swg/cli.mjs`; `docs/ASSETS.md` explains what may be converted and why, and `tools/swg/README.md` documents every command.

**Setup, once per machine.** Node 22.18 or newer (24 is fine), then `npm install`. Copy `.env.example` to `.env` (git-ignored) and put the folder holding the `.tre` archives in it, and Jedi Academy's `GameData` folder if you have the game:

```
SWG=C:/SWG
JKA=C:/Program Files (x86)/Steam/steamapps/common/Jedi Academy/GameData
```

The converter replaces `@SWG`, `@JKA` and `@CORE3` on its command line with those values, so the commands below work the same in cmd, PowerShell, Git Bash and a Unix shell, and paths with spaces need no quoting. A shell variable works too (`export SWG=...`, then `@SWG` as the argument), and the environment wins over `.env`.

**The whole conversion, in order.** Every command takes `--retail-only`, which mounts only the SOE-origin archives and leaves an emulator project's own content out.

```bash
npm run swg -- verify @SWG --retail-only                                        # 1. which archives are retail (sanity check)
npm run swg -- planets @SWG --retail-only                                       # 2. which planets the archives hold
npm run swg -- snapshot @SWG all assets-private --radius=all --retail-only       # 3. every planet: objects, terrain, ground textures, sky, flora, places (long: minutes per planet)
npm run swg -- creatures @SWG assets-private --retail-only                      # 4. the creatures the planets spawn
npm run swg -- player @SWG assets-private --retail-only --jka=@JKA             # 5. the player character, dressed, with its animations and Jedi Academy's saber, jump and parry clips (@JKA: its GameData or base folder); always with --jka once you have it, a run without it drops them
npm run swg -- parts @SWG assets-private --retail-only                           # 6. the same character as parts (body, head, clothes on one skeleton), which the game prefers
npm run swg -- clips-save assets-private/player/human_male.glb assets-private/player/jka.clips --only=BOTH_
npm run swg -- clips-apply assets-private/characters/human_male/rig.glb assets-private/player/jka.clips   #    carry the Jedi Academy clips onto the parts rig
npm run swg -- species @SWG assets-private --retail-only                         # 6b. every playable species and gender as parts, with the character creator's index
npm run swg -- loading @SWG assets-private --retail-only                         #    the game's own loading-screen pictures, one per planet (without them a planet is drawn from its sky colours); --list shows what the archives hold
npm run swg -- wardrobe @SWG assets-private --retail-only                        # 7. every wearable and hairstyle, with the game's names, body slots, species rules and a picture each, for the wardrobe on I (optional, long)
npm run swg -- wardrobe @SWG assets-private --retail-only --gender=female        #    ... and the women's (wardrobe/human_female); every humanoid species of a gender shares it
npm run swg -- wardrobe @SWG assets-private --retail-only --template=object/creature/player/shared_ithorian_male.iff                    #    the Ithorians have a skeleton of their own: their wardrobes (about 520 pieces each, their own cuts included, 172 of them worn unseen)
npm run swg -- wardrobe @SWG assets-private --retail-only --template=object/creature/player/shared_ithorian_female.iff --gender=female  #    (run `species` again after, so the index names them)
npm run swg -- mobiles @SWG assets-private --retail-only                         # 7b. every creature, droid and NPC for the spawner (B, the NPCs tab): models, shared animation packs, names, stats and the NPCs' outfits; after wardrobe and species (about 5 minutes and 1 GB; add --skip-existing to resume a run that stopped)
npm run swg -- weapons @SWG assets-private --retail-only                         #    every weapon, with its name, hands and picture, for the backpack and the rack on I
npm run swg -- ships @SWG assets-private --retail-only                           #    every player ship, with its interior, the components its slots take, its droid and its paint, for the garage on G; and the NPC ships (combat.json)
npm run swg -- space @SWG all assets-private --retail-only                        #    every space zone: stations, asteroid fields, planets, sky and hyperspace points; Kessel, Ord Mantell and Deep Space
npm run swg -- water @SWG all assets-private --retail-only                        #    each planet's own water: the colour, opacity, ripples and drift of every lake and sea, and each lava shader's look
npm run swg -- sounds @SWG assets-private --retail-only                           #    every sound the game can play, the samples they name and where each one is used (about 856 MB)
npm run swg -- status assets-private                                              # 8. what is in place, and the command for anything missing
npm run dev                                                                       # 9. play
```

Step 3 also accepts one planet at a time (`snapshot @SWG tatooine assets-private/tatooine --center=auto --radius=all --retail-only`), and `--radius=500` for a quick look at just the starport area. Step 5 dresses the character in a shirt, trousers and shoes; `--wear=object/tangible/wearables/...,...` picks other clothes (`list @SWG wearables/` shows what exists), `--var=name=value` sets skin and hair colours (the command prints every variable), `--template=object/creature/player/shared_twilek_female.iff` picks another species.

**After pulling new code.** Run `npm run swg -- status assets-private` first: it reports each pack and prints the exact command for whatever is missing. In general:

| What changed | Command to rerun |
| --- | --- |
| Ground textures, terrain rules, building layers, the sky | `terrain @SWG all assets-private --retail-only` (refreshes every existing pack in seconds) |
| Just the sky: sun, moons, stars, colour ramps, skybox, reflection maps, the weather effects and sounds | `sky @SWG all assets-private --retail-only` (run it again after pulling the converter that converts the effects particles carry: the light dust storms, falling leaves and Mustafar's lightning; `status` asks for it until it has run) |
| Just the water: each lake's and sea's colour, opacity, ripple, drift and reflection map, and each lava flow's look (a pack converted before the lava look draws a stand-in, and both the console and `status` ask for this command) | `water @SWG all assets-private --retail-only` (seconds; `terrain` does it too) |
| Reflective metal and glass on buildings and props | `snapshot @SWG <planet> assets-private/<planet> --center=auto --radius=all --retail-only` (the shine is baked into each model's textures) |
| Buildings, objects, flora, a new planet | `snapshot @SWG <planet> assets-private/<planet> --center=auto --radius=all --retail-only` |
| Animated screens, waterfalls, glowing surfaces | `snapshot @SWG all assets-private --radius=all --retail-only`, then `gallery @SWG assets-private --retail-only` (the ships pack follows with its next `ships` run; `status` asks for all three until they are done) |
| Named places on the galaxy map | `pois @SWG all assets-private --retail-only` |
| Skin, clothes, eyes, animations (walking, swimming, crouching, prone, the blaster carries, the emotes, the dances and their flourishes, the riding poses) | `player @SWG assets-private --retail-only --jka=@JKA`, then `parts @SWG assets-private --retail-only` and the `clips-save` and `clips-apply` pair (steps 5 and 6), then `species` for the other characters: the game plays the parts rig, so new SWG clips reach it only through `parts` and `species`, and the Jedi Academy clips through the bundle |
| Creature models or clips, or how a rider sits on a mount | `creatures @SWG assets-private --retail-only` |
| The spawner's creatures, droids and NPCs: models, animations, names, stats, outfits | `mobiles @SWG assets-private --retail-only --skip-existing` (redoes only what changed; `--match=rancor` redoes some and keeps the rest) |
| How a rider sits on a vehicle | `gallery @SWG assets-private --retail-only --only=vehicles` |
| The NPC ships: their types, tier fits, formations, taunts and hit, target and explosion effects (`combat.json`; without it the NPC tab offers no starships) | `ships @SWG assets-private --retail-only` |
| Sound: every sound template, the samples they name, and the client data and tables that say where each one is used (without the bank the game is silent and `__debug.audio().bank.available` is false) | `sounds @SWG assets-private --retail-only` (about 856 MB; a second run copies nothing) |
| Where a planet's sounds are: the sound objects its snapshot places (crowds, cantina bands, fires, the starport announcer), each placed model's surface, and its buildings' rows of the interior table. Without them a planet still plays its area beds and its rooms' beds, and `__debug.ambience().sources.placed` is 0 | `sounds @SWG assets-private all --retail-only` (the bank again, then every planet's places; one planet by name instead of `all`) |

Two optional sources add what the client files alone do not place. `--events` on `snapshot` includes buildout areas the game only shows during an event (`planets` lists which planets have any, with the event each needs). `--core3=<path to Core3/MMOCoreORB/bin/scripts>` reads the SWGEmu server scripts: the static objects its screenplays place go into the pack, and every creature and NPC spawn point is written to the pack's `spawns.json` for later use. `--core3` on `mobiles` also reads each mobile's level, health, damage and aggression from its scripts and puts them in the spawner catalogue in place of the estimates made from size and name. A later `mobiles` run without it keeps those stats; `--core3=none` drops them.

Commands that write a single planet's pack take the planet's folder (`assets-private/tatooine`); commands that take `all` take the parent (`assets-private`). Reconverting is always safe: each command overwrites only its own files.
