# SWG asset converter

Converts data from a locally owned Star Wars Galaxies client install into GLTF for private builds. Nothing it produces may be committed; `assets-private/` and `*.tre` are git-ignored for this reason. See `docs/ASSETS.md` for what you may convert and why.

```bash
npm run swg -- verify "C:/SWG"                                   # which archives are retail, which are a project's own
npm run swg -- list "C:/SWG" appearance/mesh/thm_tato            # list files, search priority applied
npm run swg -- dump "C:/SWG" appearance/mesh/thm_tato_moisture_vap_s01_l0.msh
npm run swg -- shader "C:/SWG" shader/thm_tato_moisture_vap.sht
npm run swg -- materials "C:/SWG" object/static/naboo/shared_waterfall_200m.iff --retail-only   # every shader a model uses and what the converter makes of each
npm run swg -- texture "C:/SWG" texture/thm_tato_moisture_vap.dds assets-private/vap.png
npm run swg -- msh "C:/SWG" appearance/thm_tato_moisture_vap_s01.apt assets-private/vaporator.glb
npm run swg -- batch "C:/SWG" assets-private/meshes appearance/mesh/ --retail-only
npm run swg -- pack "C:/SWG" tools/swg/packs/tatooine.json assets-private/tatooine --retail-only   # scatter props and outpost models
npm run swg -- snapshot "C:/SWG" tatooine assets-private/tatooine --center=3528,-4804 --radius=500 --retail-only   # the real Mos Eisley, with terrain
npm run swg -- snapshot "C:/SWG" tatooine assets-private/tatooine --center=3528,-4804 --radius=all --retail-only   # the whole planet (streams in-game)
npm run swg -- planets "C:/SWG" --retail-only                                                                       # which planets the archives hold, and where each would centre
npm run swg -- snapshot "C:/SWG" all assets-private --radius=all --retail-only                                      # every planet the game knows, one pack each
# The expansions' planets convert the same way: mustafar, and Kashyyyk's zones kashyyyk_main, kashyyyk_hunting, kashyyyk_dead_forest,
# kashyyyk_rryatt_trail, kashyyyk_north_dungeons, kashyyyk_south_dungeons, kashyyyk_pob_dungeons (one pack per zone; `all` includes them).
npm run swg -- terrain "C:/SWG" tatooine assets-private/tatooine                                                  # just the terrain template and ground textures
npm run swg -- terrain "C:/SWG" all assets-private                                                                # the same into every planet pack already there
npm run swg -- sky "C:/SWG" all assets-private                                                                    # just the sky of every pack (snapshot and terrain do it too)
npm run swg -- water "C:/SWG" all assets-private                                                                  # just each planet's water look (snapshot and terrain do it too)
npm run swg -- sounds "C:/SWG" assets-private --retail-only                                                       # every sound the game can play, and where each one is used
npm run swg -- status assets-private                                                                              # what each pack holds, and the command for what is missing
npm run swg -- terrain-check assets-private/tatooine                                                              # generated heights vs. snapshot heights
```

`snapshot` reads the planet's world snapshot (`snapshot/<planet>.ws`) and its buildout areas (`datatables/buildout/areas_<planet>.iff` and `datatables/buildout/<planet>/<area>.iff`, the tables that place later-added structures such as the Theed palace; template names come from `misc/object_template_crc_string_table.iff`, event-only areas are skipped), keeps every top-level object within the radius of the centre (`--radius=all` for the whole planet; the game streams objects in 256 m regions by size, so a full planet costs disk and conversion time, not frame rate), resolves each object template through its base-template chain to an appearance (portal buildings use their exterior cell), converts each unique mesh, and writes `layout.json` plus a `layout` category in the manifest. It also copies the planet's terrain template (`terrain/<planet>.trn`) to `terrain.trn`, decodes the terrain bitmaps its layers reference into `terrain/<name>.hmap`, and copies every building's terrain-modification layer (`terrainModificationFileName`, a `.lay` file) into `terrain/`, recording which object uses which. The game centres the world on that point, mirrors X to match the converted meshes, instances every object with its exact rotation, and gives the larger ones near spawn exact collision. Without `--center` (or with `--center=auto`) the centre is the planet's starport, failing that its shuttleport, failing that the middle of the 256 m square holding the most objects; `planets` lists every snapshot in the archives with the centre it would pick, and `snapshot <dir> all <out-dir>` converts each planet the game knows (`src/data/planets.ts`) into `<out-dir>/<planet>`, which is where the game looks for a planet's pack.

`snapshot` also converts the planet's flora: the terrain template's flora group names, per family, the appearances the game plants (trees, rocks, plants, with weights and scale ranges); each is converted into `flora/` and listed in the manifest's `flora` category keyed by appearance file. In game the terrain's flora affectors and the baked collidable flora map decide where each family grows, and the same seeded random numbers as the engine decide the exact spot, heading and scale of every plant, which is why flora was identical on every server. Terrain water comes from the template as well: the global water table height, and every lake and pool boundary (rivers still to do).

`flora <dir> <planet>|all <out-dir>` reconverts just the flora for packs converted already.

Shaders that move or glow are converted with what makes them move or glow (`tools/swg/surface.mjs`). A flip-book (root `SWTS`: a base shader, a timing form and one texture per frame; or `SWSH`, whole shaders as frames) keeps its first frame as the main texture and writes every frame into the model with its timing (`DTST` seconds per frame, `DRTS` a random range drawn per frame, `DPPT` forward then back); a frame missing from the archives drops the animation. A shader whose effect's vertex program adds `textureScroll` gets its `TSNS` rates (texture lengths per second); split alpha (`a_splitalpha`, colour and alpha scrolled apart from one texture) is written as an opaque colour image and an alpha image, each on its own glTF sampler. The effect's first pass is read at its version's offsets (from version 10 a heat byte follows dither, and before 5 a pixel-shader byte leads), and inline effects are read as well. A surface that blends, alpha-tests and writes no depth is drawn translucent only when it scrolls, splits, flips or is an unlit alpha screen; the rest keep their cut-out. Unlit effects (`*emis_full*`) are written with `KHR_materials_unlit`, additive ones (destination One under the add operation) unlit and additive, and a texture that glows through a mask (the emismap families: MAIN, EMIS, NRML or SPEC, read from the pixel program; an envmask program's lerp toward the environment map is shine, not glow) is split in linear light into a lit base colour and a glow image that add up to it, so a sign is never brighter than its texture by day. What the game needs to animate a material is in its `extras.swg`. Each pack's manifest records `materialFormat`, and `status` asks for `snapshot`, `gallery` or `ships` when a pack is older; the snapshot prints `surfaces: N flip-books, N scrolling, N unlit, N additive, N glowing (X MB of glow images)` per planet.

Named places come from `regions/regions.json`, a table of every planet's cities, landmarks and named areas with SWG coordinates, generated by `regions/build.mjs` from the SWGEmu (Core3) planet region scripts; display names resolve through the client's own `string/en/<planet>_region_names.stf` at conversion time. Regenerate it with `node tools/swg/regions/build.mjs <core3>/MMOCoreORB/bin/scripts/managers/planet` if you want a newer version.

`snapshot` also writes `pois.json`: the planet's named regions from the client's `datatables/clientregion/<planet>.iff` (cities and landmarks, with their display names from `string/en/*.stf`) and every starport and shuttleport in the snapshot, named after the region it stands in. The galaxy map lists them under each planet and teleports you there. `pois <dir> <planet>|all <out-dir>` rewrites just that file for packs converted already (the centre comes from the pack's `layout.json`).

`sat <dir> <appearance/x.sat | object/mobile/shared_x.iff> <out.glb> [--anim=all|idle,walk,run]` converts a skeletal appearance: the skeleton (`.skt`) becomes a glTF skin, each mesh generator (`.mgn`, or the finest level of a `.lmg` that has triangles: a level the archives hold stripped is passed over, and when every level is stripped the finest is taken and reported as before) a skinned mesh with up to four joint weights per vertex, and the logical animation table's entries (`.lat`, pointing at `.ans` keyframe files) become baked animations named by their logical names. Meshes that name a texture renderer (`.trt`: the game's recipe for baking skin, hair and eye textures from base textures, overlays and palette colours) get that texture rendered in software with the default customization values; `--var=name=value,...` sets other values (the command prints every variable it found, with its palette or range), and the same values choose the default texture and palette colour of customizable shaders. `--wear=object/tangible/wearables/shirt/shared_shirt_s01.iff,...` dresses the character: each wearable's meshes (they share the body's skeleton) are composed with the body the way the game does it, outer occlusion layers hiding the skin triangles under them, so clothes do not poke through. `list <dir> wearables/` shows what the archives hold. In game, `__debug.show('creatures/bantha.glb', 'walk')` in the console shows a converted model next to the player with a clip playing, for checking a conversion before it is wired in.

`trt <dir> <appearance/x.trt> <out.png> [--var=name=value,...]` bakes one texture renderer blueprint on its own, listing its shaders, effects, textures and variables, for checking a skin before converting the character.

`player <dir> <out-dir> [--template=object/creature/player/shared_human_male.iff] [--wear=...|none] [--var=...]` converts the player's character (any player species template) with skin baked, clothing composed (a plain shirt, trousers and shoes unless `--wear` lists other wearables, or `none`) and the clips the game drives (idle, walk, run, jump, sit, a light attack, a hit, incapacitation; by exact logical name, so pass `--anim=` with names from `sat --anim=list` if a table names them differently) into `<out-dir>/player/<id>.glb` and `player/manifest.json`; the game replaces its placeholder rig with the manifest's first entry when the file exists, finding the hand, spine and arm bones by name pattern and reading each clip's natural speed from the manifest. In the browser console `__debug.show('player/human_male.glb', 'walk')` previews it, and the result lists its bones and clips.

`--jka=<dir>` on `player` adds Jedi Academy's animations from a locally owned install (`<dir>` is its `GameData` or `GameData/base` folder; the humanoid skeleton `models/players/_humanoid/_humanoid.gla` and `animation.cfg` are read straight out of the `assets*.pk3` archives, later ones overriding earlier ones). The GLA's compressed bones are decoded as the renderer does (a 14-byte quaternion and translation per bone per frame through a 3-byte index table), `animation.cfg` gives each clip's frame range, loop and rate, and each clip is retargeted onto the SWG skeleton: a table pairs the JKA bones (pelvis, lumbar and thoracic spine, neck, head, clavicles, humerus, radius, hand, femur, tibia, talus) with SWG joints by name pattern, the rest is a relaxed standing frame (BOTH_STAND1) rather than the file's base pose, each limb pair carries the rotation turning the SWG rest direction onto the JKA one (SWG's bind pose is an A pose, the standing frame has the arms down), and every frame the JKA bone's change from its rest is applied in world space on top of that (the spine takes the change as it is, keeping its posture); the hips also take the JKA pelvis' rise and drop, in metres, at a scale measured from the leg lengths. The humanoid file's model space runs x across the body, -y forward and z up, which the importer maps to the converter's x left, y up, z forward. The command prints which bones matched, the rest-direction differences, and which clips `animation.cfg` lacked. By default it imports the five styles' (fast, medium, strong, dual, staff) attacks, wind-ups, returns, arcs and bounces, the stances, the special moves (katas, leaps, cartwheels, butterflies, spins, the staff's kicks, the throw), jumps, landings, flips, rolls, the wall moves and the parries that block blaster bolts, about 460 clips; `--jka-anims=BOTH_A1_T__B_,...` picks others. The clips keep their Jedi Academy names (`BOTH_...`) in the GLB and are listed in the manifest entry's `jkaClips` with loop and rate. Jedi Academy's assets never leave the install: only the retargeted clips go into the private pack. `jka-clips <player.glb> <jka-dir>` re-imports the clips into an already converted player (the SWG archives are not needed; the previous file is kept as `.bak`), and `jka-extract <jka-dir> <out-dir>` copies the humanoid skeleton and `animation.cfg` out of the archives as loose files, which both commands accept in place of a Jedi Academy folder.

`terrain <dir> <planet>|all <out-dir>` copies just the terrain template, its bitmaps and its ground textures into an existing pack (`all`: into every planet pack under `<out-dir>`), which is the quick way to add ground textures to packs converted before they existed.

`sky <dir> <planet>|all <out-dir>` writes the planet's sky into the pack (`snapshot` and `terrain` do it as well): `sky.json` and PNGs under `sky/`. The client environment file `terrain/environment/<planet>.iff` (FORM `ENVM`) names the sun and moon shaders with their sizes and glows, supplemental suns and moons with yaw and pitch offsets, extra celestial bodies, the star count and colour ramp, a time lock, and a skybox (a cube map, or six `texture/<mask>_<side>.dds` faces). The environment table `datatables/environment/<planet>.iff` has a row per environment family and weather index: the gradient sky texture (columns are the time of day, rows the horizon up to the zenith), two cloud layers with their shader, size and speed, the colour ramp image, shadow and fog settings, and the day and night reflection cube maps. The colour ramp is a 256 by 8 (or 10) 32-bit image indexed by the time of day, one row each for the ambient, main, specular, fill and bounce lights, the clear colour, the fog and the shadow, with light scales, the sun and moon alpha and the star alpha in the alpha channels; it goes into `sky.json` as base64. Cube maps are written with their faces swapped and mirrored for the mirrored X axis, so the game loads them as ordinary cube textures. In game the sky replaces the procedural dome, its ramps drive the sun, fill and ambient lights and the fog, the sun and moon ride the client's fixed 67.5 degree light path, and reflective surfaces get the block's cube map (or the sky itself, filtered every few seconds). Mesh textures whose effect keeps a specular or reflection mask in the alpha channel (effects with an `ENVM` or `SPEC` stage, or named for specular, gloss, metal, glass or chrome) get a glTF metallic-roughness image from that mask, so those surfaces reflect the environment. Each row also names a particle effect to play around the camera and the ambient sounds and music cues for that area and weather; the command keeps them with the block (`cameraEffect` with the effect's kind and how hard it falls, and `sounds`) and converts the effect into `particles/`, along with the rain, dust and snow effects listed in `FORCE_EFFECTS` so any planet can be given any weather. The top-level `weather` says how many weather levels the table has and where those forceable effects were written. Nothing plays the sounds yet; their names are kept for an audio system. Particle effects are cached per output pack, so a run over several planets writes every planet's own files. Effects a particle carries (a `PATT` under the particle's `PTCL`: the carried `.prt`, a start-percent range, whether it dies with the particle, and whether it spawns on creation, death, a percent of the particle's life or on hitting the ground) are converted into the same pack, all the way down a chain, and each attachment records the converted `file` (or `failed` with the reason); the manifest entry gains `attached` with how many were converted.

`water <dir> <planet>|all <out-dir>` writes what the planet's water looks like into the pack (`snapshot` and `terrain` do it as well): `water.json` and, for each reflection map, six PNGs under `water/`. The terrain rules name a water shader for the global sea and for every lake, pool and flow; each one is a `.sht` over `effect\water.eft` whose MAIN texture gives the surface its colour (its mean taken in linear light) and, through the alpha, its opacity by the client's own formula `0.5 + a/2`; whose NRML normal map gives how rippled it is (its mean slope against the reference map, so 1 is the ordinary sea); whose first TSNS scroll rate gives how fast those ripples drift; and whose CUBE slot names a reflection map, written at 128 px with its faces swapped and mirrored like the sky's. Each entry also records how many tables use it, which water types they are and whether the global table is one of them, so the game can tell a lake from a sea. The shaders over `effect/water_lava*.eft`, and any table the terrain marks as water type 1, are written as `kind: "lava"` with no colour and no cube: that is what tells lava from water even where the terrain's own type says 0. A shader that is not in the archives is still listed, marked `missing`, and still reads as lava if its name says so. A planet with no water at all gets a `water.json` with no shaders, so `status` only has to see that the file is there.

A lava shader over a lava effect also gets a `lava` block: its MATL's emissive group (loopTime, then the flow) and specular group (colorScale, colorBias, tcScale), the bloom factor from its TFNS entry tagged BLUM (the red of the value, 0..1, null without one), the colour ramp (LKUP) inline as base64 RGBA so its alpha survives, the crust (TEXT) as `water/<name>.png` written opaque, and the noise volume (NOIS, 8-bit luminance) as `water/<name>.r8` with its size. Each file is written once per planet however many shaders name it; a slot whose file is missing or does not decode is null with a note, and a MATL that cannot be read leaves the block null. For Mustafar the log reads `water: 3 shaders (0 water, 3 lava), 0 cubes, lava files 3 -> water.json`. `status` shows the lava count beside the shaders and asks for this command when a lava entry was written before the lava look (a lava effect and no `lava` block).

`sounds <dir> <out-dir>` writes the sound bank into `<out-dir>/sounds/`. A sound template (`.snd`) is `FORM SD2D > 0003` for a sound with no place in the world or `FORM SD3D > [FORM SD2D > 0003] + 0001` for one that has a place; 528 of the 7,171 are an `SD2D` form with a stray empty chunk after it at the top level, which the generic parser refuses, so the reader takes the first root form (every one of those is a voice-over line, which is 2D). The `0003` chunk is an int32 sample count, that many sample paths, then exactly 112 bytes of settings in every file: the random start delay, the fades, the loop count (−1 for ever) and the gap between loops, the category, the play order, how volume and pitch vary (pitch in semitones, which is how the alpha bolma and the baby bol share their samples), the priority and the metres within which the sound plays at full volume. How loudness falls off beyond that is the client's audio library's and is not in the archives. `sounds.json` holds every template but the background music and the instrument parts, with a line per sample (its rate, channels, length, and loop points for the three that loop part of themselves; an MP3's length comes from its frame count where the encoder wrote one and from its bit rate otherwise, which is marked `estimated`). Music the world places in a room (the cantina bands, the organs, an event's theme) is kept all the same and marked `placedMusic`, because it is a thing standing somewhere rather than a score; so are the three sounds `scene/hyperspace.iff` names for the jump's stages, which the client files under music although they are a ship's own noise (`keptMusic: "scene"`, and they do not belong on the ambience slider). The samples are copied as they are under `sounds/samples/<archive path>`, about 856 MB, and a second run copies nothing. Twenty-seven templates name their sample by the absolute path of the machine that built it, as some shaders do; the tail from the deepest `sample/`, `music/` or `voice/sample/` folder finds 22 of them, three of which are Kashyyyk's ambience beds. A template whose every sample is missing is kept and marked `silent`, so a lookup never throws. `sounds.json` also holds `aliases`: names the game writes that differ from the file only in where the underscores fall (`amb_kashyyk_ryratt_trail_lvl01` against the archives' `..._lvl_01`, five creatures' voices with an extra underscore in the species name), each pointing at the one template whose letters match; where two templates would match, neither is claimed.

`sounds.json` is the sounds; `events.json` is where they are used. Client data (`clientdata/**`, `FORM CLDF > 0000`) names a sound or an effect per event: `CEFT`, `CSND` and `EVNT` are an event name then a path (`footstep`, `footstep_sand`, `vocalize`, `hitlight`, `attackheavy`, `hitground`, the emote voices), `ASND` is the object's own looping sound, a `DAMA` form is a damage band with its own effect and loop, a `VTHR` form's `VSND` is a name then eight paths (the idle, speed-up, slow-down and run loops, then the four sounds of the damage that state stands for), a `VGEF` form's `INFO` is a byte that is 1 over water then the sound, the effect's name and its appearance, and `ENGS > INTS > INFO` (a ship engine part) or a top-level `INTS > INFO` is a slot name, the sound and six floats that are not decoded. Every client effect (`clienteffect/*.cef`) is written as the sounds and the particle it plays, and every scene (`scene/*.iff`) as the sounds it names. `events.json` also lists three kinds of hole: `dangling`, the 168 sounds the game names that have no file in the archives at all; `leftOutButNamed`, the 27 that are there but were left out as music, which is a rule to check rather than a surprise; and `packGaps`, the sounds an already converted pack under the same out-dir asks for and the bank has not got, each with the pack file that asks. `sources.json` holds the tables: the room table (`datatables/interior/interior.iff`, 265 rows over 166 buildings with each room's day and night bed, what the floor is and its room type, 7 on Mos Eisley's cantina and the four capitol lobbies and 22 everywhere else), the interface table, the melee and ranged weapon effect tables, the door styles, a ship's power and hit sounds (the fallback row of each is called `default`), each chassis's flyby sound, and the nine terrain surface templates with the surface under a foot and how much of the ground it covers. `--only=<text>` converts just the templates whose path holds that text and `--no-samples` writes the JSON without the audio; both write a narrowed `sounds.json` over whatever was there, leaving the 856 MB of audio on disk but the index short, so they are for a quick look and `status` asks for the command to be run again in full after either.

A planet name (or `all`) after the out-dir also writes `<out-dir>/<planet>/sounds.json`: where that planet's sounds are. It reads the world snapshot and the buildout tables the way `snapshot` and `audit` do, so nothing but the planet's own pack has to exist first and nothing has to be reconverted after; all eighteen planets take under two seconds. A planet with no pack of its own is passed over rather than given a directory holding nothing but its sounds. `emitters` is every placed object whose template's client data carries an `ASND`, the object's own looping sound: the 491 `object/soundobject/*` objects the eight launch planets place (the cantina beds, the city crowds, the starport announcer, the bands; nine of the 491 carry no sound and are left out, two of them because their client data is empty or missing and one because it names none) and the 3,623 props that hum, which is most of them — 212 moisture harvesters and 184 mission terminals on Tatooine, 152 tiki torches on Endor. The sound objects come first in the list and `soundObjects` counts them, so a game that can hold only so many placed sources at once takes the ones the world placed for their sound alone rather than a prefix of the alphabet. An emitter inside a building carries which building's portal layout, which of its cells and where that building stands; a placed object is contained by a cell object, whose `cellIndex` is the room and whose transform is always identity, and that cell object is contained by the building. Positions are written exactly as `layout.json` writes an object's, in the snapshot's own coordinates, and the game mirrors X and takes the layout's centre off as it does for any placed object, so a pack whose centre moves needs no rerun here; the file says which frame it is in, so a reader that does not know it can leave the places alone rather than stand a town's crowds kilometres from the town. The emitters cover the whole planet, while a pack converted with a small `--radius` holds only what is near its centre, so such a pack carries emitters for buildings it does not hold; they are simply too far away to be heard. `pobs` maps each placed building's template to its portal layout's name without its folder or extension, which is the key the room table uses; `rooms` is the room table's rows for the layouts that planet places, keyed `<pob>|<cell>`, with the table's own `default` row for anything with none. `surfaces` maps a placed template to what standing on it sounds like, from the template's own `surfaceType`: metal, stone, wood, acid, ice, molten or obsidian. Type 0 is by far the commonest (765 of the 1,170 templates Tatooine places) and means the thing has no surface of its own, so those are left out and the absence is the answer; over all eighteen planets only metal, stone and wood ever appear, which are three of the names a body's own client data steps with. `status` lists how many planets have their places and asks for `sounds <swg-dir> <out-dir> all` for any planet that has a pack and no `sounds.json` of its own.

`audit <dir> <out-dir> [planet]` is the completeness check: for every converted planet it lists every object the archives place (snapshot plus buildouts, and server spawns when `--core3` is given) against the pack's `layout.json`, and reports what is missing with the reason (a skipped kind such as sound objects, a creature the server spawns, a skeletal prop that needs a reconvert, or an older conversion), with an example position, plus manifest models whose files are gone. In game, `__debug.near(r)` in the console tables the placed objects within `r` metres of the player with their model, tier, and whether the model and its region are loaded, for telling a conversion gap from a streaming one.

Particle effects come along with the snapshot: a template whose appearance is a `.prt` (`object/static/particle/...`: campfires, smoke, sparks, steam, Mustafar's plumes) becomes a `fx_<name>` entry in the manifest with `particle: true`, its description written as `particles/fx_<name>.json` and the textures its quads draw as PNGs under `particles/`, and it is placed in `layout.json` like any object. A mesh with an effect among its parts (a candlestick's flame, a lamp's glow, a fountain's spray) keeps the effect in its manifest entry's `effects` list with the part's transform, and the game plays it at every placed copy. The description follows the client's loaders exactly: every emitter curve is a waveform over the emitter's age (spawn rate, speed, shape size, spread, life, weight) or the particle's age (size, rotation, colour, alpha), each with a random band; the texture's shader effect decides the blend (additive for fire and glows, alpha for smoke). Emitters that draw meshes rather than quads, and attachments (effects spawned when a particle dies or hits the ground), are read and kept in the JSON but not drawn yet. In game, `__debug.particles(r)` in the console tables the effects within `r` metres with whether they are playing and how many particles they hold.

The archives that are not in the retail manifests (Legends' own `*.tre`/`*.toc` files) are skipped by `--retail-only`, so anything they replace or add is invisible to the converter. `extras <swg-dir>` lists them and, for every file whose winning copy comes from one of them, says whether it replaces a retail file or is new, grouped by category. World snapshots, buildout tables, terrain rules and heightmaps, sky and environment files and named regions are listed in full; other categories show a few examples. It is a listing only; nothing from those archives is converted.

Later publishes replaced some snapshots outright: the final Rori snapshot has no Restuss at all, because SOE's server placed the ruined city after the Battle of Restuss, while the launch snapshot held the intact town. `stat <dir> snapshot/rori.ws --all` lists every archive that carries the file, oldest first, and `--ws-add=<archive>@x1,z1,x2,z2` on `snapshot` (also honoured by `why` and `audit`) adds whatever that archive's copy placed inside the rectangle, so the intact city can stand where the ruins would be.

`status <out-dir>` needs no archives: it lists what every planet pack, the creatures, the mobile catalogue and the player under `<out-dir>` hold, and prints the command that fills each gap. A mobile model that failed with "no mesh survived" (its appearance stripped at every detail level in the game's own archives, so every rerun fails it again) is listed on a line of its own and not counted as work; it counts again when the failure was recorded from other archives than the catalogue's, or for another signature than the unit plans now. A sky whose effects carry an effect the pack holds no file for (converted before the converter converted what particles carry) asks for `sky` again.

`creatures <dir> <out-dir>` converts the creature each planet spawns (bantha, kaadu, durni, bol, kimogila, boar-wolf, rancor, mawgax, kahmurra, torton) and every creature the mount tables list as mountable into `<out-dir>/creatures/<id>.glb` with the clips the game drives (idle, walk, run, a light attack, a light hit, incapacitation) and writes `creatures/manifest.json`; the game swaps its procedural creature bodies for these when the file exists. A creature's body hardpoints (`SKMG > <version> > FORM HPTS`: a mount's `saddle`, the basilisk's `player`) are written as `hp:<name>` nodes under their joints, mirrored as the joints are, and read from the mount tables' own appearance (the `_hue` one) when the template's lacks the saddle and both share a skeleton. Every saddle the tables name (`appearance/mnt_saddle_*.apt`) is converted once into `<out-dir>/creatures/saddles/`, and each mount's manifest entry gains `hardpoints` and `saddle` (`appearance`, `file`, the `joint` its hardpoint hangs from or null where the back is guessed, the `.sat` it was read `from`, and the saddle's `player` point). `status` prints how the mounts are saddled (`saddles: 22 on the creature's own hardpoint, 25 where the back is guessed, 1 on its own rider point, 4 with none in the tables`) and asks for this command when the pack predates saddles.

`wardrobe <dir> <out-dir> [--gender=male|female] [--template=object/creature/player/shared_<species>_<gender>.iff] [--kind=wearables,hair] [--match=<regex>] [--limit=N] [--no-icons]` converts every wearable and hairstyle built for the species' skeleton into `<out-dir>/wardrobe/<species>_<gender>/`: a GLB per worn mesh, the live colour recipes, and `wardrobe.json`, whose items carry what the backpack shows. `name` and `description` are the template's string ids (`objectName`, `detailedDescription`: the first along the chain whose table and key are both set, read through `string/en/<table>.stf`; failing that for the name, the chain's table with the item's id as key; null when neither resolves, about one item in ten, which name a table the client never had). `slots` is the template's arrangement (`arrangementDescriptorFilename`, each `ARG ` chunk one alternative of body slots: `ring_either` is `[["ring_l"],["ring_r"]]`), null without one. `icon` is `icons/<id>.png`, a 96 px picture drawn at conversion by a small software rasterizer (`thumbnail.mjs`) from the item's meshes in their bind pose, from the front and a little above, the textures at their default colours, a pair worn far apart (gloves) drawn side by side; none for hair, a repeated id, or with `--no-icons`. Who may wear it is `datatables/appearance/appearance_table.iff`: a row per `shared_<id>`, a column per species and gender, each cell `:default`, `:block` (cannot wear), `:hide` (worn, takes its slots, nothing drawn) or that species' own appearance. The folder's own column decides the mesh converted (the men's bracelets, the Ithorians' own cuts); a path the archives lack, a misspelt one (`.satx`) or one whose meshes will not convert falls back to the template's own. The other species of the folder's gender are written as `fit` (`block`, `hide`, `own`); `fit.own` never names the folder's own species, which wears the entry's `sat`. Where the folder's own column says `:hide` and the item cannot be built for its skeleton (172 in each Ithorian folder), it is written worn unseen: `sat` null, no parts, `fit.hide` naming the folder. The run's summary counts the names, slots, pictures, species rules, worn-unseen entries, the items whose mesh the table changed and the repeated ids, and names any slot an arrangement uses that the player's slot descriptor (`abstract/slot/descriptor/player.iff`) lacks.

`weapons <dir> <out-dir> [--limit=N] [--no-icons]` converts every weapon the game can hold into `<out-dir>/weapons/` with `manifest.json`: each weapon's class, model, bounds, reach, blade and client effects, and, read as for the wardrobe, its `name`, `description` and `slots` (a pistol `[["hold_r"]]`, a rifle and every lightsaber `[["hold_r","hold_l"]]`) and an `icon` per model, drawn side on with its far end (the extreme of its longest axis farther from the grip, as the game reads it) up and to the right. `status` counts the named, slotted and pictured items of the weapons and of every wardrobe folder, and asks for the command again for a pack converted before they were written.

`ships <dir> <out-dir> [--limit=N] [--match=<regex>] [--glass=<regex>]` converts every ship a player can fly (`object/ship/player/`) into `<out-dir>/ships/` with `manifest.json`, and the game's projectile table as `projectiles.json`. What hangs on each hull is written as a tree in its `attachments` (`tools/swg/shipparts.mjs`): the ship's client data (each WING's DATA, then PSOR, the wing's own place in its parent's frame and the hinge it turns about, or HARD, a hardpoint of the part that lists it; the carriers the client keeps as chunks beside the forms, HOBJ and IHOB an appearance on a hardpoint, CHL2 a template and CHLD an appearance at a place; and the ONOF appearances), every part's own client data in turn to a depth of four, and the stock parts: each slot's stock component's look in the hull's `datatables/space/ship_chassis_<chassis>.iff` (the look the most components the slot accepts show, which on every retail hull is the column's most common `attachment:hardpoint` cell; the chassis is the template's own name, a decorated YT-1300's the plain one's, the corvette's `player_corvette`; a `modification_*` slot, one reward look, has no stock part; `tools/swg/shipfit.mjs`). Each entry has `kind` (`wing`, `carrier`, `engine` for an on/off appearance, `component` for a stock part), `source`, `file`, `template` or `appearance`, `parent` (the index of the entry it hangs on, null for the hull), `hardpoint` (on that parent; null for its origin) and `place` (x, y, z and three angles in degrees, the client's own numbers, or null), and as they apply a wing's `turn` (`angle`, `time`) and `sound`, an on/off appearance's `on` (`engine`, or `booster` when a booster lists it), a stock part's `slot` and `sharedWith` (other slots whose identical part it stands for), `owner` (the stock part whose own client data produced the entry) and `standInFor` (an empty slot's `…_<slot>_none` stand-in, which the game leaves out while a component fills that slot). A hardpoint a part's client data names is looked for on that part, then on what already hangs under it (a turret's barrels are on its body), then on the whole ship; a part nothing carries is noted and left off, never put at the origin, and the same file on the same hardpoint at the same place is hung once. Each ship also has `chassis` and `wingOpenSpeedFactor` (the chassis table's `wing_open_speed_factor`: 0.95 on the X-wing, advanced X-wing, B-wing and V-wing, 1 elsewhere), and the manifest has `assembly: 2`; the log gives each ship's wings, carriers, on/off appearances and parts, and its `notes` what was left off and why. `status` adds how many parts are hung over all the ships and how many ships have wings that open to its `ships` line, and asks for this command again while any ship lacks `chassis` (converted before); a `--match` run keeps the older format for the ships it did not redo.

What each hull can be fitted with is its `fit` (`tools/swg/shipfit.mjs`), read from the game's tables rather than guessed: `datatables/space/ship_chassis.iff` gives each slot (reactor, engine, two shields, two armours, capacitor, booster, droid interface, bridge, hangar, targeting station, cargo hold, two modifications, weapons 0 to 7) the compatibility classes it takes, `ship_components.iff` every component's type and class, and the hull's looks table which model each component shows there. `fit.slots` lists every slot with its classes (`compat`), its `looks` and its `stock` component. Each look has the `parts` it hangs, `{ file, hardpoint, template, children? }`: `children` is the part's own client data as `expandPart` writes it, parents relative to the part, and without `parent` what the part does not carry itself, hung by name over the whole ship. Each look also has the `components` that show it (indices into `components.json`), and `noModel` when it hangs nothing, as the TIE engines. The stock component is the best-ranked of the look the most accepted components show, with the ship's usual gun preferred; a `modification_*` slot has none and starts empty. A looks column the chassis row gives no class is a `fixed` slot, always its one look (the Star Destroyer's 92 turret bases). `fit.droid` is `astromech` on the eight hulls with `hp:astromech`, else `computer`. `fit.paint` lists the hull's paint shaders (every customizable shader on the hull, its wings and carriers and every look's parts, a hologram's left out) and one variable list: `index_texture_1`, the pattern, with its largest and smallest count; `index_color_1` and `index_color_2`, each with its 64-colour palette and default. It is null on the 22 hulls with none. `components.json` holds every component a slot can take: its name as the game shows it (from `space/space_item`, else its template's `objectName`, else made from its key), its type, class and template, and for a gun the bolt from `ship_weapon_components.iff`. It also holds the droids: the six flight computers, and the astromechs in `datatables/space_command/programmable_droids.iff` whose model the mobiles pack holds (R2 to R5; R2-D2 has none), each with the heads a hull draws it as instead (the N-1's, from `ship_droid_appearance_override.iff`, converted here). `customize.json` and `customize/` hold a recipe per paint shader for the game to repaint with: the shader's passes and the textures they read, every pattern and palette, `staticMain` (the static shader's own main texture), and `glow` when the converted material glows. Every paint shader is baked into the models at its defaults, every pass, so a hull nobody painted looks as the client drew it; the bake's alpha is the chosen pattern's own, which keeps its gloss mask. Each ship's `weapon` is its first gun slot's stock bolt. The manifest has `fitFormat: 1`. `status` adds the ships with loadouts and paint and the astromechs to its `ships` line, and asks for this command again while the ships have none; a `--match` run keeps the other ships' recipes and numbers its new images past theirs. `materials --ship=<id>` shows a paint shader as the ships command bakes it, with its variables.

The same command writes `combat.json`, the NPC ships (`tools/swg/npcships.mjs`). Every tiered NPC template (`object/ship/shared_<family>_tier<1..5>.iff`; the `nova_orion_*` quest line's, tiers up to 10, is not the tier ladder and is dropped) resolves to the same appearance as the player ship of its family, so each type is written in `types` with the garage hull whose template has that appearance (the one whose id is the family when several do): `id`, `name` (`string/en/space/space_mobile_type.stf`, another tier's line when a tier has none), `family`, `base`, `style`, `tier`, `hull`, `chassis` (the type's own `ship_chassis.iff` row, else the row without its style: `blacksun_light_s01_tier1` reads `blacksun_light_tier1`), `faction` (Imperial, Rebel, Black Sun, pirate or neutral by family, an invented table since the server decided it), `taunts` (the table it reads) and `template`. A type no hull draws is listed in `skipped` with the appearance missing: on the retail archives 170 types in 34 families fly on 34 hulls and 105 are left out (the gunboats, the shuttles, the freighters, merchant cruisers and transports, the droid fighter, the escape and probe droid pods, the Kessel mine turret, the smuggler warlord's ship, and the `_npc` YT-1300, YKL-37R, Y-8 and Decimator). `chassis` holds, for every tier chassis and every player hull's chassis, the filled slots with their classes, hit weights and targetable flags, and the hit-sound group; a tier chassis also has its `fit`, made exactly as a player hull's (`looksToParts`: its looks table is the same at every tier and lists every component that shows a model; which components an NPC carries is the game's pick at run time) with `paint` null, since an NPC wears the paint baked into the models. `formations` are the arrow, claw and wall tables (20 slots of X, Y, Z in metres in the leader's frame, row 0 the leader, and X2D, Z2D as `flat`; X mirrored), `taunts` the ten taunt tables (imperial, rebel, blacksun, hutt, generic and each one's `_low`) by event (`entercombat`, `gothit`, `hityou`, `death`, with `%TU` and `%NU` left in), `hitEffects` the shield, armour, component and chassis hits and events by weight (`ship_hit_effects.iff`), `hitSounds` the sound names by group, `target` the targeting effects (`ship_target_appearance.iff`: the default row, and any chassis whose row differs), and `hulls` every garage hull's explosion and damage bands (from its client data, positions mirrored); every effect is converted into `particles/`. The log prints `combat: … NPC ship types in … families on … hulls …, … tier fits, …`, and `--verbose` adds its notes and the types left out. A tier fit's parts are converted after `manifest.json` is written, so a part only an NPC carries (one on the retail archives, a Grievous starship gun) is a model file the manifest does not list. A `--limit` run writes no `combat.json` and keeps the one there (its manifest has only some hulls); when the NPC step fails, `combat.json` is removed, since it would index the `components.json` the run just wrote. `status` adds the NPC ships to its `ships` line and asks for this command while the pack has no `combat.json`, or one with no tier fits.

`space <dir> <zone>|all <out-dir>` converts a space zone into `<out-dir>/<zone>/`, or every zone with `all`: the nine planets' orbits (`space_tatooine` ... `space_kashyyyk`) and three systems that are no planet's orbit, `space_light1` (Kessel), `space_heavy1` (Deep Space) and `space_ord_mantell`. Each pack has the stations (the zone's station table, drawn as the faction station the client has), the asteroid fields (each scattered from its own seed through its style table), the planets and moons of its terrain file, its sky (`sky.json`), `layout.json` and `manifest.json` as a planet pack has them, and `space.json` (version 3; every coordinate is in the client's frame and the game mirrors X, except the nebulae, the fields and the docking lanes, which the converter mirrors once because they are drawn rather than jumped to). Version 3 adds five blocks. `nebulae` is `datatables/space/nebula/<zone>.iff` row by row: the name, the centre (mirrored), the radius, the density, `facingShare`, the four colours as `[alpha, red, green, blue]` exactly as the table stores them, the camera shake, which of the two nebula shaders `shaderIndex` picks (`glow` is the additive `pt_nebulae_gas_4_2.sht`, `mist` the blended alpha one; the pairing is inferred from the order the client's executable lists them in), the ambient sound, and `lightning`, which is null unless the row both names a `.ltn` and has a non-zero frequency — 171 of the 250 retail rows do, from 4 of Endor's 41 to all 33 of Naboo's, and six rows that name a frequency and no file (all of them doing no damage) get none. `nebulaLook` gives each kind its sheet shader, its effect, its blend and the image the converter wrote (`nebula/glow.png`, `nebula/mist.png`), with the near shell's `_no_z` shader and effect beside it pointing at the same image, because both shaders name the same texture. `lightning` is the one appearance a zone's rows name (every retail zone names `appearance/pt_nebulae_white_02.ltn`), read from `FORM LEFX > 0002`: its `flipbook` (the `FORM PTEX` particle texture: a 2x2 sheet of 4 frames at 10 a second), its picture as `nebula/lightning.png`, its two waveforms through the particle reader, the float its data chunk opens with, the two particle effects it plays at a bolt's start and end converted into the pack, and `trailingBytes`, the 81 bytes after those names that are not read. `fields` is each asteroid field's shape for the map (centre and spline mirrored, radius, count, sound, both view distances, and `FlattenDepth`/`FaceTowards` kept unread); the table's `Name` column is filled on 70 of the 214 retail rows and is a designer's note as often as a label, so it is carried as it stands and anything shown to a player names the field itself. `lanes` is the docking data by model id: `approach_<lane>_<n>`, `dock_<lane>`, `dockradius_<lane>`, `exit_<lane>_<n>`, the drydocks, and the hangar mouths as `bays`, read off the model's hardpoints and mirrored with its meshes. Each approach and exit point keeps the number its hardpoint carries and also says how far it is from its dock, because the number rises outward along a path and one station numbers more than one path under a single letter, so where one path ends and another begins is the game's reading and not the converter's. Only five station models carry any: the neutral station (lanes a to c, c a bare dock, and seven hangar mouths), the Imperial station (a to f, twenty-four mouths), the Imperial outpost and the rebel station (a to d), and the Star Destroyer (a to d, and the one hardpoint in the archives that says where its hangar is); the CorSec, RSF and rebel outpost stations have no hardpoints at all. `dockEffects` is what a dock plays; every one of the six client effects names a sound and no particle, so there is nothing to draw. The command also writes the zone map's six icons once per out-dir as `space_ui/zone_*.png`. `space.json` carries the system's `title` (`string/en/planet_n.stf`, without the server's "(PvP Enabled)"), its `stations` (each with the `title` and `description` of the point strings, `<planet>_station_0`, the "Land Here" promise dropped since landing is not built, and `approachClearance`, how far a jump to it from the arrival ends from anything placed), `scenery`, `planets` (each body's `direction`, its place from the camera in the client's frame, its `distance`, the `radius` its planet appearance's SURF chunk gives, `size` in the game's unit, the radius over the distance times 2600/240 so that a body of size 1 is drawn 240 m in radius at 2600 m, `sizeFrom`, `angles`, `halo` and `texture`), the `arrival` (an orbit's is the origin, `kind: 'launch'`, where a ship climbing out of the planet comes out; any other system's is its first point, `kind: 'point'`) and `hyperspace`: its `points` (the rows of `datatables/space/hyperspace/hyperspace_locations.iff` for the zone, named and described by `hyperspace_points_n`/`_d`, each with `source` and `clearance`), the jump `scene` (`scene/hyperspace.iff`), the two warp effects converted into the pack with the `timing` the converter reads from their emitters (`enterPeak`, `tunnelAt`, `exitBurstAt`, `exitClearAt`), the client's `alreadyAtPoint` line, and `frameCheck`. The contract other code reads: `pack.hyperspace?.points ?? []`, `pack.scenery ?? []`, `pack.stations`, `pack.arrival ?? null`; `hyperspace` is an object, never an array.

`maps <dir> <out-dir>` writes each converted planet pack's own map (`texture/ui_map_<planet>.dds` as `map.png`, with `map.json` saying how wide a ground it covers) and `galaxy.json` beside the packs: every planet's ground width (`datatables/travel/planet_width.iff`: 16384 m, Mustafar 8000, `kashyyyk_main` 4096) and the game's shuttle routes (`datatables/travel/travel.iff`, 30 of them over 12 planets), each as `{ from, to, price }` because the table is not symmetric, with a planet's own cell kept apart in `local` as the price of travelling within it. The names are the tables' own, which are the planet packs' ids. Where a system hangs in the galaxy is not in the archives and is not written here. `status` prints the route count and asks for `maps` while `galaxy.json` is missing or older.

The hyperspace table is in the station tables' frame: each point's description gives its distance to the system's stations, and every run checks those distances against both pairings (the point as it is, and with X mirrored), logging `hyperspace frame: N of N distances fit the unmirrored pairing (mean ... m; mirrored ... m)` per zone with table points and a `warning:` line if the mirrored pairing ever fits better; the result is `frameCheck`. What the client never had is made up in `tools/swg/space.mjs` and marked in the pack: Kessel's and Deep Space's four point positions (`INVENTED_POINTS`, `source: 'invented'`; the client names them but its table places none), Deep Space's two fields (`INVENTED_FIELDS`, "(invented)" in their names; the client has no field table for it) and the Star Destroyer hung 2.3 km from Deep Space's first point, broadside to it (`INVENTED_SCENERY`, `invented: true`; the plain `object/ship/shared_star_destroyer.iff`, the exterior only). Ord Mantell has no row of its own: its one point is its sister scene's, `space_nova_orion_0` (`BORROWED_POINTS`, `source: 'borrowed'`), whose station, fields and sky are Ord Mantell's. Any point, the arrival or a station's approach end within 300 m of a placed object is logged as a `warning:` with the object's template. `status` prints one line per zone (title, stations, scenery, objects, hyperspace points with how many are made up or borrowed, and the arrival) and asks for `space <swg-dir> all <out-dir> --retail-only` while any zone is missing or older.

`mobiles <dir> <out-dir> [--only=creatures,droids,npcs,dressed,specials] [--match=<regex>] [--limit=N] [--skip-existing] [--core3=<dir>|none] [--max-variants=32] [--plan]` converts every creature, droid and NPC the client's mobile templates describe (`object/mobile/**`, about five thousand) into `<out-dir>/mobiles/` for the spawner, and writes `mobiles/catalogue.json`.

**The catalogue.** Every entry has a display name (the template's `objectName`, else the same key in the other name tables, else a name made from the file name), its template's collision size, scale range and speeds, its colour values and body shape from its client data, what it wears, and stats for the game: health, damage, reach, aggression and whether it shoots. These are estimated from its size, family and name, or read from Core3's scripts with `--core3`.

**Models.** Each appearance is converted once, without animations. Those whose templates wear clothes become parts characters (a folder with one GLB per mesh, a skeleton and live colour recipes), which the game dresses from the wardrobe the way it dresses the player. Each other colour combination the templates use is converted as a whole model under `variants/`, unless it comes out identical to the base.

**Animations.** They go into packs shared by every appearance with the same skeletons and animation table (`anims/<pack>.glb` with `anims/<pack>.json`), including one per player body for the NPCs dressed on a player species. A creature's pack holds every animation its table names, on the unmounted and calm branch. A humanoid's or droid's pack holds a combat set: stances, attacks, the pistol and rifle shots, hits, knockdown, incapacitation, getting up and ten emotes. Each pack's JSON names the clip to play for each role (idle, walk, run, attack, hit, down, get up), so the game never guesses by name. Joints a clip leaves at their bind position get no track, and joints that hold still get two keys, which halves the packs.

**Outfits.** A dressed NPC's worn meshes are matched to the wardrobe's parts by mesh name; the meshes no wardrobe has are converted into wardrobe-format folders under `wearables/`. Run `wardrobe` (both genders, and the Ithorians) and `species` first.

**Options and records.** Each model, pack and wearable folder writes a small record beside it (`models/<id>.json`, `anims/<id>.json`, `wearables/<folder>.json`) with what it was made from, including which archives were mounted, and what the conversion found. `--plan` prints what would be converted and each pack's roles without writing anything. `--match` and `--only` convert part of it, while the catalogue always lists everything with a `ready` flag. `--skip-existing` keeps every unit whose record is current, so a stopped run resumes; a unit made from other archives (a run without `--retail-only`) is never kept. `creatures` still converts the planets' creatures and the mounts for the garage. If the process runs out of memory, run it as `node --max-old-space-size=6144 tools/swg/cli.mjs mobiles ...`. A unit whose conversion fails keeps whatever was already on disk: it is listed under `failed` in the catalogue and in the run's last lines, and it stays usable until a later run converts it. Only a failure after the old record has been deleted — a folder that cannot be replaced because something is holding it open — leaves the unit with no record, which the next run treats as missing.

`why <dir> <planet> <pattern>` explains a missing building: it lists every snapshot object whose template matches the pattern with its count, size and position, resolves it to its appearance file, says which archive holds that file, and converts it on the spot, printing the failure if there is one.

`terrain-check` (Node 22.18 or newer, since it runs the game's TypeScript directly) runs the ported terrain generator (`src/swg/terrain/`) over the pack: it prints the template's header and layer counts, applies each building's layer at its snapshot position and heading, then samples the ground under every top-level object and compares it with the height the snapshot recorded (objects were placed on the ground in the original editor, so the difference measures how faithful the port is). Expect a median well under half a metre; the worst offenders are listed with their templates so a wrong affector type can be tracked down.

`pack` converts the highest-detail mesh of every family matching a spec (see `packs/`) and writes `manifest.json`. The game looks for `assets-private/<planet>/manifest.json`, scatters the `rocks`, `debris`, `vaporators` and `flora` categories across the terrain in place of the primitive props, and places the structures listed in `src/data/outposts.ts` near the spawn on flattened ground with triangle-mesh collision.

Flags: `--retail-only` mounts only archives named in the retail manifests, `--events` places buildout areas the game only shows during an event (`why` and `planets` list them, with the event each needs), `--core3=<dir>` (or the `CORE3` environment variable) reads SWGEmu's `MMOCoreORB/bin/scripts` for the static objects its screenplays spawn (placed like buildout objects; server template names get the client's `shared_` prefix) and its creature and NPC spawn points (written to the pack's `spawns.json` with each mobile's client templates), `--no-flip` keeps left-handed coordinates, `--no-textures` skips DDS decoding.
